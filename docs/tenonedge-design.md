## 0. Agent 先读：不可偏离的约束

1. 开发的是可以独立安装、独立使用、方便二次开发的开源网关产品，不是演示页面。
2. 核心任务是：接入数据、必要的格式处理、输出数据。优先把真实输入到真实输出做通。
3. 首版为一个 .NET 服务，自带 Web 界面（前端为独立工程，构建产物由该服务提供）。本地配置和发送缓存使用 SQLite，二者分为两个文件，不强制部署第二个服务。
4. 首版仅参考 Node-RED 的拖拽、连线、参数配置和调试体验，继续使用 TenonEdge 自有画布和执行逻辑。本期不嵌入、调用或安装 Node-RED，不建设其节点包或流程文件兼容层。官方嵌入方式仅按第 20 节记录为待评估选项，不授权实施，也不是永久排除。
5. 不引入 SQL 流计算、eKuiper、脚本引擎、复杂规则引擎、窗口聚合、插件市场、微服务集群或分布式调度。
6. SQLite 是内部存储，不是面向用户的 SQL 功能。不提供 SQL 编辑器、数据库查询节点或 SQL 数据分析。
7. 网关不依赖 TenonAdmin 或其他管理框架，自带最小管理能力：本地账号、固定三种角色、首次设置、审计日志。不建设菜单管理、自定义角色、组织与数据范围或多租户。
8. TenonIoT 是可选输出目标。未安装平台时，网关也必须能够完成初始化、设备配置、采集、编排和通用输出。
9. 首版平台联动只做：连接认证、设备关联、数据上报、状态上报。不做平台远程编辑网关配置，不做设备写入和远程控制。
10. 参考项目不是依赖清单。成熟协议库和画布组件可以复用；不得因为参考项目具有某功能，就自动扩大本方案范围。
11. 先阅读实际工作区的 AGENTS.md、项目结构和依赖版本；没有核实的第三方库接口和平台接口不得自行假设存在。
12. 未经明确授权，不修改其他仓库、不覆盖用户未提交改动、不推送远程仓库。缺少平台源码时交付连接器、契约和测试接收端，不伪称已经完成真实平台联调。
13. 第 4 节 G0/L0 属于开源版完整能力，不因企业版规划被删减或增加商业激活要求。企业版复用同一核心，不维护第二套采集、转发、画布或权限实现。
14. 商业化首期只落实版本边界、发布记录、许可清单和整机交付规范。不自动开发授权服务器、在线激活、计费、设备商城、批量远程运维或企业插件市场。
15. 只在有明确需求、可验证的交付价值和合法分发权时增加企业扩展。不得擅自更改已有 LICENSE、将第三方代码改署为自研，或向公开仓库提交商业 SDK、客户资料和企业密钥。
16. 第 20 节是候选技术记录，不属于 G0/L0、T0—T5 或首版验收项。不得因此新增 Node.js 运行服务、Node-RED 包依赖、认证桥接、双运行引擎、空适配工程或兼容格式；未来启动评估须另获明确授权。
17. LoRa／LoRaWAN 按第 21 节接入已由上游处理的业务数据，优先复用 MQTT、HTTP 拉取或已实现的 Modbus TCP。不得自动实现无线驱动、网络服务器、入网密钥管理、原始包转发协议或下行控制；ChirpStack 不是默认依赖。通用接入的样例与测试可随 T2/T5 交付，新增能力与实物适配按 G1 和条件验收管理。

## 1. 产品定位和边界

TenonEdge 是基于 .NET 的边缘接入与转发网关。用户在产品自己的界面中配置设备、数据来源和输出目标，用简单画布连接数据路径。

典型使用方式：

```text
Modbus TCP 设备 ───────────────→ MQTT 输出
MQTT 订阅 ──→ 字段映射 ───────→ HTTP 输出
HTTP 拉取 ──→ 字段映射/换算 ──→ TenonIoT 输出
```

同一份数据可以分发到多个输出目标，字段处理节点可以省略。网关不是 PLC、硬实时控制系统、通用 ETL 平台或长期历史数据库。

### 1.1 两个产品的职责

| 产品 | 首版职责 | 不承担的职责 |
|---|---|---|
| TenonEdge | 本地配置、接入、格式处理、转发、有限缓存、运行诊断 | 集中历史分析、远程设备控制、完整物联网业务 |
| TenonIoT | 网关登记、设备关联、数据接收、设备状态及平台侧数据展示 | 直接操作网关数据库、代替网关轮询设备 |

TenonEdge 作为独立仓库维护。TenonIoT 可以是已有或后续的独立仓库。二者通过接口协作，不互相引用宿主工程，不共享数据库。

TenonEdge 规划 Community（开源版）与 Enterprise（企业发行版）两种软件版本；预装工控主机是交付形式，不是第三套软件。企业版不是使用 TenonIoT 的前置条件。具体边界见第 15—18 节。

### 1.2 首版明确不做

- Node-RED 运行时、官方嵌入集成、外接 Node-RED、Node-RED 节点兼容层；本期不做，候选说明见第 20 节。
- SQL 查询节点、流式 SQL、复杂脚本、任意 C#/JavaScript 执行。
- 条件规则引擎、时间窗口、跨设备关联计算、复杂告警编排。
- 流程回环、子流程、动态修改正在运行的节点图。
- 网关集群、跨机任务调度、全局消息总线、Kafka 等强制基础设施。
- 内置 MQTT Broker（写进网关进程）、内置 OPC UA Server、设备写入、RPC 控制。设备需要直连时，在同一台机器上附带独立的 Broker（第 3.1 节）。
- 平台远程改点位、改画布、远程 Shell、网关自动升级。
- 菜单管理、自定义角色、组织与数据范围、多租户；首版只提供固定三种角色（第 3.3 节）。
- LoRa 射频收发驱动、LoRaWAN 网络服务器、入网管理、无线原始报文处理、下行控制；不因支持应用层数据接入而把 ChirpStack 等系统打入默认安装包。
- 长期遥测数据库、历史报表、大屏设计器、AI 功能。
- 商业授权服务器、强制在线激活、收费平台、远程停机、插件商城和按版本人为限制基础设备数/点位数。

本地错误状态、发送失败提示和运行统计必须保留，但不扩展成告警产品。

## 3. 技术方案

### 3.1 首版架构

```text
浏览器：TenonEdge 前端（独立工程，产物由宿主提供）+ 自有画布节点
                              |
                    TenonEdge.Host 单进程
                 管理 API（认证、三种角色、审计）/ 运行时宿主 / 静态文件
                              |
          接入适配器 -> 简单映射 -> 输出报文生成 -> 发送缓存 -> 输出适配器
                              |
                       config.db（SqlSugar）+ queue.db（Microsoft.Data.Sqlite）+ 密钥环
```

- 后端使用 .NET 10。前端是独立工程，放在本仓库 web/：React 19、TypeScript、Vite、shadcn/ui + Tailwind CSS 4、React Flow、TanStack Table、react-hook-form + zod、react-router、zustand、react-i18next。API 客户端用 openapi-typescript + openapi-fetch 从 OpenAPI 生成；测试用 Vitest 与 Playwright，静态检查用 oxlint。新建精简工程，沿用 TenonAdmin React 模板的这套工具链，不复制其页面。构建产物由 .NET 宿主作为静态文件提供，与管理 API 同源，不需要 CORS。
- 界面文案一律经 i18n，首版只提供中文。浏览器最低 Chrome/Edge 111、Safari 16.4、Firefox 128（Tailwind 4 的要求），不支持 Win7 上的 Chrome 109；T3 用最低支持版本的浏览器做一次冒烟测试。
- 首版 Node.js 只用于前端构建，发布后浏览器资源由 .NET 宿主提供；产品运行时不要求 Node.js。第 20 节候选记录不改变这项部署约束。
- 网关无强制外部数据库、Redis、消息服务器或中心平台依赖。用户选择 MQTT 时可以使用现场已有的 Broker。现场没有 Broker、又有只支持 MQTT 的设备时，在同一台机器上附带一个现成的独立 Broker（默认 Mosquitto）。它和网关是两个进程：网关重启或升级期间，Broker 继续接收消息，并在其积存上限、会话过期和持久化设置的范围内为网关的持久会话暂存（部署检查项见第 8.5 节）。附带的 Broker 禁止匿名登录，每台设备使用单独账号，并开启消息持久化。也可以换成其他 Broker，只要满足五项要求：MQTT 3.1.1 与 QoS 1 持久会话；用户名密码认证与主题权限，能禁止匿名；消息持久化；能在 Linux x64 上运行；许可允许随安装包和整机镜像分发。备选为 NanoMQ（MIT）；它是否满足第一、三项（持久会话下的离线 QoS 1 消息落盘）没有找到官方文档依据，社区 issue 中还有相关缺陷报告，采用前须按第 8.5 节实测。EMQX 5.9 起采用 BSL 1.1，禁止以嵌入方式提供给第三方，不能附带；客户已有 EMQX 时可以直接连接。附带 Broker 是可选项，不改变下一条“默认只启动一个服务”的约定。
- 默认只启动一个服务；运行模块和界面在代码上隔离，不要求拆进程。
- 默认本地保存配置、有效版本、凭证和待发数据：配置在 config.db，待发数据在 queue.db，两库分开。实时值只做有界内存缓存，不做完整历史库。
- 数据目录显式配置为绝对路径（容器内为挂载卷），不依赖进程工作目录；以 Windows 服务运行时，工作目录默认是 System32。启动时对数据目录加独占锁，同一数据目录上的第二个实例拒绝启动。

### 3.2 代码结构

```text
TenonEdge/
  TenonEdge.sln
  src/
    TenonEdge.Abstractions/    数据契约及少量可替换接口
    TenonEdge.Runtime/         接入调度、连接管理、路由校验、转换、发送缓存与发送任务
    TenonEdge.Adapters/        Modbus、MQTT、HTTP、TenonIoT 适配器
    TenonEdge.Host/            ASP.NET Core 宿主、认证与角色、管理 API、配置存储
  web/                        前端工程（React + Vite），发布时构建产物并入宿主
  tests/
    UnitTests/
    IntegrationTests/
    TestPlatform/             仅用于平台契约测试的接收端
  deploy/                     Dockerfile、启动与数据目录说明
  docs/
  samples/                    模拟器配置、示例路由、测试报文
```

不继续为每个目录机械拆成 Domain/Application/Infrastructure 多层。若工作区已有同等职责结构，沿用现有结构，不为匹配目录名重构。

依赖方向：

```text
Host -> Runtime / Adapters / SqlSugar + Microsoft.Data.Sqlite（配置库）
Runtime -> Abstractions / Microsoft.Data.Sqlite（发送缓存）
Adapters -> Abstractions / 必要协议库
Abstractions -> .NET 基础类型
```

- Abstractions 不引用 ORM 实体、ASP.NET Core、MQTTnet 或 NModbus 类型。
- Runtime 不读取 HttpContext，不伪装成超级管理员执行采集。Host 把有效快照编译为不可变的 RuntimePlan（定义在 Abstractions 中）交给 Runtime，这是二者之间唯一的配置契约；Runtime 不读取 Host 的配置实体。
- 运行中会变化、不进入快照的数据——凭证、平台设备绑定状态、出站白名单，以及配额、保留期、存储保护阈值等运行参数——由 Abstractions 中的只读接口（如 ICredentialResolver）提供，Host 实现，Runtime 在建立连接、路由或发送时查询。运行状态则由 Runtime 通过只读查询接口提供给 Host，再由 Host 转为 API。
- 驱动返回数据或错误，不操作页面、平台数据库和发送重试表。
- 只有会替换、需要隔离或需要测试替身的边界才定义接口；不要给每个实体建立空接口。发送缓存直接用真实 SQLite 临时文件测试，不为它另建替身接口。
- 驱动和节点采用编译期模块加依赖注入注册。新增扩展后重新发布/重启，不提供上传任意 DLL 或热加载。
- 企业扩展仅通过第 11 节现有扩展点和显式宿主装配接入。开源核心不反向引用企业包，默认构建不需要私有仓库；第 16 节的企业目录是将来有实际模块后的组织规则，不要求现在创建空工程。

### 3.3 自带的最小管理能力

网关不依赖 TenonAdmin 或其他管理框架。认证、角色、审计和管理 API 约定由本产品实现，范围保持最小：

- 账号与角色：本地账号，固定三种角色——管理员、配置人员、只读。管理员新建用户或重置密码时设置的是临时密码，用户首次登录必须先修改。权限按角色在代码中集中定义（第 10.3 节）；角色以字符串保存，将来需要可配置的角色时不必改数据模型。不做菜单管理、自定义角色、组织与数据范围、多租户。
- 会话：同源 Cookie 认证（HttpOnly、SameSite=Strict；Secure 标志跟随请求协议，HTTPS 下设置；HTTP 与 HTTPS 的 Cookie 分开命名，请求协议的判定见第 10.3 节），写操作校验防 CSRF 令牌，滑动过期（空闲 2 小时）。用户改密码、改角色或被禁用时，通过安全戳让旧会话立即失效；开启“只允许 HTTPS”或恢复备份时，会话代次加一，全部会话失效。安全戳和会话代次缓存在内存中，校验会话不写库。不做刷新令牌。
- 密码：PBKDF2 哈希，使用 Microsoft.Extensions.Identity.Core 的 PasswordHasher，不引入完整的 ASP.NET Core Identity 和 EF Core。密码至少 8 位且同时含字母和数字，拒绝常见弱口令；同一账号名连续 5 次失败锁定 15 分钟（不存在的账号名同样计数，统一提示“尝试次数过多”），登录接口按来源 IP 限流。
- 首次设置：见第 10.3 节。
- 审计：config.db 中的 audit_log 表，记录登录、首次设置、应用与回滚、凭证写入、发送测试报文、配置导入、平台设备同步、重置网关身份、API 令牌的创建与吊销、备份下载与恢复、导出诊断包、清空队列、迁移待发记录、手动暂停与恢复目标、导出失败区记录、清理失败区、放弃草稿、信任服务器证书、解除平台映射、导出审计记录、主机侧管理员重置，以及用户与角色、出站白名单和系统设置的变更，默认保留 180 天（满足《网络安全法》对网络日志留存不少于六个月的要求），可调长，过期清理。存储保护状态下，审计写入失败不阻断登录，改写到标准输出。
- 运行事件：config.db 中的 runtime_event 表，只记录状态变化，包括连接断开与恢复、设备离线与恢复、目标退避与暂停、存储保护、应用成败、时钟未同步、服务启停。同一对象的同类事件合并计数；保留 7 天，最多 1 万条；与审计分开。存储保护状态下写入失败时，改写到标准输出。
- 日志：应用日志写标准输出，由 systemd（journald）或容器日志驱动收集；部署说明为其设置轮转与大小上限（Docker 默认的 json-file 驱动不限大小）。不自建文件日志；内容按第 10.3 节脱敏。日志和运行事件都不记录报文正文和点位的值，需要看数据时用调试面板。
- API 令牌：供脚本和第三方系统使用。由管理员创建，绑定一种角色，可以设置有效期，可以吊销。令牌只在创建时显示一次，库里只存哈希。请求用 `Authorization: Bearer` 携带；因为不走 Cookie，所以不做 CSRF 校验；不能用于首次设置和登录接口。用令牌执行的写操作记审计，并标明令牌名称。令牌只能经 HTTPS 创建和使用（第 10.3 节）；认证失败单独按来源 IP 限流；停用或删除用户时，提示是否一并吊销该用户创建的令牌。
- 管理 API 约定：见第 10.1 节。

不使用通用 Cron 任务为每个点位单独建任务。采集由本产品运行时调度。

| GW-23 | G1 | 进程内 MQTT Broker | 仅在现场只能运行单个进程，或需要在网关界面统一管理设备账号时评估。前提：设备账号与主题权限、TLS、连接数与报文大小限制、会话持久化，写入发送缓存后才向设备确认，并通过安全审查；可基于 MQTTnet.Server |
| GW-24 | G1 | 运行事件推送 | 把运行事件推送到 MQTT 主题或 Webhook，由客户自己的系统发送短信、邮件；不做告警规则 |
| GW-25 | G1 | 管理员双因素认证 | TOTP 验证器 App，含绑定、恢复码和丢失手机后的重置流程；客户要求等保三级时实施 |
| GW-26 | G1 | 扩展项目模板 | `dotnet new` 模板，生成带测试的输入或输出适配器项目 |

L0 不要求把完整 TenonIoT 一起开发。平台工作区缺失时，完成连接器、OpenAPI 契约和测试接收端，并明确真实联调尚未完成。

GW-21 不是一种新的无线协议驱动，也不是强制企业版功能。现有 G0 能覆盖的单设备应用报文，随 T2/T5 提供映射样例和软件测试；不因缺少 LoRa 实物阻塞基础版本。额外适配以明确型号、固件、协议和报文样本为前提，测试状态单独记录。

## 5. 页面和用户操作

| 页面 | 主要内容 |
|---|---|
| 总览 | 输入数、输出数、当前运行状态、待发数据、最近错误 |
| 连接管理 | MQTT/HTTP/Modbus/平台连接；凭证写入但默认不可读回 |
| 设备与点位 | 设备（带分组）、数据来源、点位或字段；表格内编辑、批量导入、复制设备、一次读取预览 |
| 数据路由 | 左侧节点、中间画布、右侧参数、底部预览与错误 |
| 平台连接 | 作为连接管理的专用视图；关联设备、同步结果和状态 |
| 运行诊断 | 连接错误、发送状态与队头阻塞时长、缓存统计与可覆盖时长、目标暂停状态；恢复被暂停的目标、重试、清理和迁移操作 |
| 系统设置 | 网关名称、用户与角色、运行参数、HTTPS 证书与“只允许 HTTPS”开关、有效配置、导入导出、出站白名单、数据目录（只读）、审计记录 |
| 首次设置 | 仅在尚无管理员、且处于设置窗口内时显示，用于设置管理员密码（第 10.3 节） |

平台连接只是已有 Connection 的一种类型，不再实现第二套凭证存储和 HTTP 客户端。

复制设备：连同采集组和点位复制到草稿，一次可复制多份；副本自动生成不重复、且符合第 6.5 节规则的 deviceKey，默认停用，启用前按需修改 UnitId 或连接。

标准操作：创建连接 -> 创建设备/输入 -> 配置点位 -> 选择输出 -> 连线 -> 用样本预览 -> 保存草稿 -> 应用配置 -> 查看运行状态。

预览默认不访问输出目标。真实采集预览和“发送测试报文”必须分别由用户显式触发，并使用与运行相同的权限、地址校验和超时。预览与测试连接通过运行时的连接管理进行：Modbus 预览排入该连接的串行执行器，不另开连接；MQTT 测试连接使用独立的 ClientId。发送测试报文只对通用 MQTT/HTTP 输出提供，TenonIoT 输出不提供，因为平台会把测试报文当作真实数据保存（`docs/functional-spec.md` 第 4.4 节）。预览读取和显示的外部响应内容限制长度，同时进行的预览与测试有数量上限（第 8.7 节）。

## 6. 输入、字段和输出设计

### 6.1 Modbus TCP 与 RTU over TCP

- 主机、端口和连接/读取超时属于 Connection（物理通道）；设备和采集组只持有 UnitId。多个 UnitId 共用同一 host:port 时（例如串口服务器后面挂多台设备），共享一个连接和一个串行执行器。
- 连接的帧格式可选 Modbus TCP（MBAP 头）或 RTU over TCP（带 CRC 的 RTU 帧，用于透传模式的串口服务器）。RTU over TCP 后面是串行总线：同一连接严格一问一答，通常需要配置请求间隔，超时按波特率留足余量。RTU 帧没有事务号：超时后进入静默间隔（默认 500 毫秒，待实测，可按连接调整），期间收到的字节全部丢弃，静默间隔内不再有字节到达才发送下一个请求；持续有字节、排不净时立即重连一次（不按退避，也不改变其他从站的状态）。应答还要校验从站地址、功能码、字节数和 CRC；但同一从站、同一功能码、同样长度的迟到应答能通过这些校验，所以静默间隔不能省略。Modbus TCP 按 MBAP 事务号匹配应答：较旧事务号的迟到应答跳过，不当作本次结果；两个候选库的默认行为都不完全满足这一点（第 2.3 节），由适配器保证。从站地址限 1–247。串口直连（Modbus RTU）仍属 G1。
- 采集组配置周期；点位配置唯一 key、显示名称、功能码、零基地址、数据类型、字节序、单位。
- 首版支持只读功能码 01/02/03/04，以及 bool、寄存器取位（从 16 位寄存器中取指定的一位，如状态字）、int16、uint16、int32、uint32、float32、int64、uint64、float64。其他类型（字符串、BCD 等）按需求增加。32 位类型支持 ABCD、CDAB、BADC、DCBA 四种字节/字序，64 位对应 ABCDEFGH、GHEFCDAB、BADCFEHG、HGFEDCBA；寄存器取位的位号 0 为最低位。64 位整数的表示与精度按第 6.4 节处理；浮点寄存器读到 NaN 或无穷时判为 nonFinite。界面只列出适配器实际支持的类型。
- 界面明确零基地址与设备手册编号的差别，不把 `40001` 等显示编号直接当成协议偏移量。每台设备可以选择地址写法，表格同时显示两种写法（`docs/functional-spec.md` 第 3.3 节）。
- 同一物理连接上的请求串行执行，不对不支持并发的设备无条件并行读取。连接可配置请求间隔（两次请求之间的最小间隔，默认 0），用于串口服务器后面的慢速设备和对请求频率敏感的 PLC。
- 可使用简单连续区间批量读取，不实现复杂优化器；遵守所选协议库和设备的读取长度约束。合并区间不得跨越未配置的地址。
- 采集周期超时则跳过本周期并计一次 overrun。某个读取块超时后，该设备（UnitId）本周期剩余的块直接判为失败，不逐块等待超时；同一连接上的其他设备不被判为失败，额外等待的上界见本条末尾。出现连接级错误（连接断开、套接字异常），或同一连接上每个启用设备的最近一次请求都超时，才按退避重连。被判为离线的设备（第 8.4 节）按退避降低读取频率，最长 60 秒读一次（默认值），读取成功后恢复正常周期；这样一台不应答的从站在每个周期给同一连接上其他设备增加的等待不超过“读取超时 + 静默间隔”，判为离线后只在退避到期时增加。
- 显式设置协议库的读写超时，库内重试设为 0 或 1，由调度器负责重试；每个连接循环使用专用线程，停止时通过释放连接打断阻塞中的读取。
- 超时后的旧值只作为“最后成功值”显示，并显示时间和过期状态；不得当成新采集成功值继续发送。
- 无映射节点时，只发送本次成功读取的字段，失败字段从 values 省略，并在消息的 quality 中标为 bad；整组读取失败不伪造一条正常数据，改为更新设备采集状态。必填映射失败则按第 6.4 节阻止该路径本条输出。
- 用具有已知数值的测试寄存器验证字节/字序，不以连通成功作为读取正确的证据。测试证据至少包括：每种类型在四种字节序下的已知值（含超过 2^53 的 64 位整数、负数、NaN 与无穷的浮点位型、位号 0–15）；不应答的从站在超时后快速失败，同一连接上的其他从站不被判为失败，额外等待不超过“读取超时 + 静默间隔”；超时之后才应答的从站，其迟到应答不会被下一个请求取走；读取阻塞时停止单元，在停止超时内退出且不产生第二个实例。模拟从站只证明协议逻辑，实物测试另行记录（AT-02、AT-13）。
- 点表 CSV 导入导出：提供模板。导入的范围是所选设备在草稿中的点位，分两种模式：覆盖（同 key 的点位按文件更新，新 key 新增，文件里没有的点位保留）和增量（只新增，已存在的 key 跳过）。逐行报错并带行号；整批在一个事务内写入草稿，有错误则整批不写。导出使用带 BOM 的 UTF-8，导入兼容 UTF-8 与 GBK（.NET 需注册 CodePagesEncodingProvider）；导出的文件修改后可直接再导入。

### 6.2 MQTT 输入

- 连接外部 Broker，首版按 MQTT 3.1.1 交付，支持 QoS 0/1 和 TLS；其他版本只在明确测试后声明支持。客户端须显式指定 3.1.1：MQTTnet v5 默认使用 5.0，而在 5.0 下仅设置 CleanSession=false 不能保留会话。
- 同一 Connection 在运行时只对应一个客户端，由连接管理按引用计数共享，多个输入的订阅复用它（第 8.1 节）。
- QoS 1 订阅默认使用持久会话（CleanSession=false）和稳定的 ClientId；ClientId 可在连接上配置，默认由 NodeId 短码与连接 ID 组成。连接后检查 SessionPresent：为 1 时会话中的订阅仍在，不重复订阅没有变化的 Topic Filter（重复订阅会让 Broker 重发保留消息）；为 0 说明会话已丢失（例如 Broker 没有持久化就重启、会话过期），重新订阅全部 Topic Filter，并记运行事件“MQTT 会话丢失，断线期间的消息可能已丢失”。
- 订阅随配置协调：应用第 3 步先停止接收，此后到达的消息不处理、不确认；已收到的消息排空、提交并按到达顺序确认之后，才断开所有带输入的 MQTT 连接（与输出共用的连接同样断开，输出的在途发送取消、记录保持待发）。应用期间到达、未被确认的 QoS 1 消息，由 Broker 按持久会话保存并在重连后重投。第 5 步等该连接的输入都已启动或已判为启动故障之后才重新连接，按新版本计算每个 MQTT 连接需要的 Topic Filter 集合，补订新增的，退订不再使用的，否则持久会话会让 Broker 继续为已删除的输入积存消息。激活之后，收到不匹配新版本任何输入的消息，才计数后确认。修改 ClientId 时，应用过程中先用旧 ClientId 以 CleanSession=true 连接一次来清除旧会话，失败只记运行事件；Broker 端另按第 8.5 节设置会话过期作为兜底。
- 保留消息：收到 RETAIN=1 的消息，说明它是 Broker 因为（重新）订阅而补发的最后一条保留消息，不一定是新采样；通过已建立的订阅转发的消息 RETAIN 为 0（MQTT 3.1.1 第 3.3.1 节）。默认不为保留消息生成投递，计入“保留消息已忽略”后确认；它可以作为“抓取一条实时消息”的样本，界面标明“保留消息”。输入可以开启“处理保留消息”，前提是已映射上游时间字段，使 collectedAt 反映真实时间。
- QoS 1 消息关闭自动确认，写入发送缓存并提交后按到达顺序确认。不产生任何投递记录的消息——超限、非法报文、所有路径映射都失败、设备未绑定或字段待同步而跳过、保留消息被忽略、因配额或存储保护被拒绝入队——计数后即可确认，不等待提交，但确认仍排在此前到达的消息之后。其中配额与存储保护造成的拒绝是明确的丢弃策略，分类与计数见第 8.5 节。存储写入失败时不确认，并断开该连接、按退避重连，由 Broker 在持久会话中重投未确认的消息。QoS 0 输入为 at-most-once，界面明确标注。
- 接收回调只做大小校验与解析，然后写入有界通道；该通道使用等待模式（满时 TryWrite 返回 false），不用丢弃模式。通道满时，QoS 0 消息直接丢弃并计数；QoS 1 消息在回调中等待空位，最长 5 秒（第 8.4 节），超时按存储写入失败处理。等待必须有上限：MQTTnet 用一个任务依次执行回调，等待期间同一客户端后续收到的消息（包括不受 Broker 在途窗口限制的 QoS 0）都积压在库内的无界队列里。回调变慢不影响保活。
- 上游须以 QoS 1 发布，持久会话才能在断线和应用配置期间保留消息；此外还取决于 Broker 的会话保留、队列上限与持久化设置，超出这些前提的消息由 Broker 丢弃，网关无法计数（第 8.5 节）。LoRa 场景见第 21.4 节。
- 只支持 MQTT 的设备发布到附带的或现场已有的 Broker（第 3.1 节），按本节规则接入：JSON 载荷，每台设备使用自己的主题并对应一个输入，建议以 QoS 1 发布。设备在线状态按最后接收时间显示。
- Topic Filter 支持协议允许的订阅通配；每个输入配置绑定一个逻辑 deviceKey。
- 首版不根据任意 Topic 自动创建设备，不解析二进制或脚本载荷。多设备使用多个显式输入配置。
- LoRaWAN 应用上行沿用一输入一设备：优先使用含具体 DevEUI 的精确主题，而不是把所有传感器通配订阅后写进同一个 deviceKey。共用主题中混合多设备的情况，按第 21.3 节列为需单独适配的范围。
- 对消息体设置大小限制；非法 JSON、解析失败、超限必须计数和显示错误，不能导致宿主退出。
- 若提供上游时间字段，必须显式映射和校验；保留原时间，否则使用网关接收时间，并在消息的 timeSource 中注明来源。重连后补收的积压消息同样按第 6.4 节的时间规则处理。
- 防止订阅主题与本机输出主题形成反馈：应用时检测明显重叠；不允许已知自反馈路线上线。

### 6.3 HTTP 输入

- 首版定时 GET，地址和方法来自受控连接配置；不允许数据报文修改目标 URL。
- 查询参数、非秘密请求头与凭证分开保存。支持固定 Bearer/Basic/API Key 凭证引用，不实现 OAuth 授权平台。
- 每个输入只有一个执行循环，上一次请求未完成不叠加下一次请求。
- 首版处理单个 JSON 文档；可用字段定位选择固定数组下标。不自动分页、拆分任意数组、增量游标同步。
- HTTP 拉取与接收上游 HTTP 推送不是同一能力。只有推送接口的无线网关不能直接当成已兼容；本地 Webhook 接收仍属 GW-20 的 G1，不因第 21 节自动增加。

### 6.4 统一消息与字段处理

内部消息至少包含：

| 字段 | 说明 |
|---|---|
| sourceMessageId | 一次输入采样/接收的本地稳定 ID（建议 UUIDv7）；发往多个目标时保留 |
| inputId / deviceKey | 输入配置及逻辑设备身份，不使用名称代替身份 |
| collectedAt | 数据所代表的时刻，UTC：映射了上游时间字段时取该字段（timeSource 为 device 或 upstream），否则等于 receivedAt（timeSource 为 gateway 或 gateway-unsynced） |
| timeSource | collectedAt 的来源：device（设备报文给出的采样时间）、upstream（上游事件时间，如 ChirpStack 的 time）、gateway（网关接收时间，不代表采样时刻）、gateway-unsynced（系统时钟未同步时的网关时间，不可信） |
| receivedAt | 网关拿到这条数据的时间，UTC：轮询类为本次读取完成的时刻，推送类为收到消息的时刻 |
| payload | 原始或处理后的 JSON 数据；数值、布尔、字符串不混转 |
| quality | 取值为 good、uncertain、bad，并附原因码；稀疏表示：values 中出现的字段默认为 good，只列出异常字段；缺值不静默转成 0 |
| source | 只读的来源元数据：实际 topic、HTTP 状态码、Modbus UnitId 与功能码等，供预览、诊断和映射读取 |
| fieldTimes | 可选的字段级时间，稀疏表示：只列出时间与 collectedAt 不同的字段；首版不生成，为 OPC UA 等 G1 协议预留位置 |

**时间规则。**

- 轮询类（Modbus、HTTP 拉取）由网关发起读取，receivedAt 可以近似看作采样时刻。推送类（MQTT）的消息可能早已产生：重连后 Broker 补发的积压、保留消息（第 6.2 节）、上游自身的缓冲，都会让接收时间晚于真实采样时间。没有映射上游时间时，这类消息的 collectedAt 只是接收时间，不能据此认定是新采样；MQTT 输入没有映射时间字段时，配置页提示这一点。
- 上游时间字段须显式映射，并声明格式（RFC 3339，或注明单位的 Unix 时间戳）。某条消息的该字段缺失、无法解析，或超前网关时间 5 分钟以上（即未来时间，网关时钟已同步时才判断）：该条改用接收时间，timeSource 按网关时钟状态记为 gateway 或 gateway-unsynced，并计入“上游时间无效”，不因此丢弃数据。早于网关时间的上游时间照常采用，重连后的积压本来就会如此。
- 网关不按 collectedAt 重排消息；下游按 collectedAt 判断新旧（第 8.2 节）。
- 推送类设备的状态只显示最后接收时间（receivedAt）。MQTT/HTTP 连接正常不代表传感器仍在上报（第 9.4、21.4 节）；按周期判断数据新鲜度属于 GW-21（G1）。

字段选择使用 JSON Pointer，例如 `/data/temperature`、`/values/0`。采用 RFC 6901 的定位语法，不提供查询表达式和脚本。依据：https://www.rfc-editor.org/rfc/rfc6901 。

首版映射规则只包含：目标字段名、来源位置、目标类型、单位、是否必填、比例、偏移、保留小数位、可选固定值。数值转换为 `y = x * scale + offset`，不是执行用户表达式。

处理约定：

- 来源合法 JSON 已经符合输出格式时，可以直接转发，不能强制增加映射节点。
- 必填字段缺失或转换失败：该路径本条消息失败，不发送半成品；其他路径不受影响。
- 可选字段缺失：默认省略，并在预览中提示；不擅自复用旧值。
- 映射把来源字段的 quality 带到目标字段：来源为 bad 的可选字段，同样从 values 省略并在 quality 中标为 bad，不能变成“未携带”。
- 字段重名、无效数字、溢出、非有限浮点数必须可见地失败；可选字段或无映射时的点位因此失败，同样从 values 省略并在 quality 中标为 bad（原因码见下文）。
- 必须有单位/类型测试。输出 schema 反映换算后的类型与单位，而不是照抄原始寄存器类型。输出字段的 schema 可以来自 Modbus 点位、映射节点或 InputDefinition 的字段描述；三者都没有时，不能向平台同步设备字段。
- 数值换算：整数寄存器按 decimal 计算；未经换算的 float32 按单精度、其余浮点按双精度的最短往返格式序列化（见下文“数值与类型”）；映射规则可选“保留小数位”。
- 多分支对消息使用独立的处理结果，不共享可变 JSON 对象造成相互污染。

**数值与类型。** 输出字段只有四种类型，由配置确定：点位类型给出默认值，映射规则的目标类型可以改写。同一字段始终使用同一种 JSON 形式，不随数值大小在数字和字符串之间切换。

| 输出类型 | 内部表示 | JSON 形式 | 来源举例 |
|---|---|---|---|
| boolean | 布尔 | true / false | 功能码 01/02、寄存器取位、JSON 布尔 |
| integer | 有符号 64 位整数；只有未经换算的 uint64 寄存器保留无符号 64 位范围 | 十进制整数字面量，逐位精确，不经过 double | int16—int64、uint16—uint64 寄存器；字段描述声明为整数的 JSON 字段（按有符号 64 位解析） |
| number | decimal：整数寄存器经比例或偏移换算、字段描述声明为数字且能用 decimal 精确表示的 JSON 数；double：浮点寄存器及其换算结果、超出 decimal 表示范围的 JSON 数 | 数字字面量：decimal 逐位输出、不用指数；未经换算的 float32 按单精度、其余 double 按双精度的最短往返格式 | 换算后的寄存器值、浮点寄存器、声明为数字的 JSON 字段（样本推测的“数字”默认归入此类） |
| string | 字符串 | JSON 字符串 | JSON 字符串；目标类型设为 string 的数值（十进制文本） |

- 转为 integer：“保留小数位”为 0 时先按四舍五入（远离零）取整；结果不是整数为 conversionFailed，超出有符号 64 位范围（未经换算的 uint64 为无符号 64 位范围）为 overflow。例如 uint16 寄存器加偏移 −40 得到负数，仍在有符号 64 位范围内，不算溢出。
- 转为 number：decimal 超出范围为 overflow；浮点运算得到 NaN 或无穷为 nonFinite，JSON 中不出现 NaN、Infinity。
- 转为 string：数值取上表 JSON 形式的文本，布尔为 "true" 或 "false"。转为 boolean 只接受整数 0/1 和字符串 "true"/"false"。字符串转数值按与地区无关的格式解析。其余情况为 conversionFailed。
- 64 位整数：JSON 文本本身可以精确表示，但按 IEEE 754 双精度解析数字的接收方（例如 JavaScript 的 JSON.parse）超过 ±(2^53−1) 就会丢精度（RFC 8259 第 6 节）。网关不替接收方改变类型：来源为 int64、uint64 的字段在配置页提示这一点，需要时由用户把目标类型设为 string，此后该字段始终是字符串（RFC 7493 第 2.2 节的做法）。网关自己的界面同样不能丢精度：管理 API 返回点位值时以原文字符串附类型，返回报文时返回原文，前端只显示、不把数值重新解析为 JavaScript 数字（第 10.1 节）。TenonIoT 对 integer 字段须按 64 位整数解析（第 9.4 节）。

**质量与原因码。** 首版只产生下列原因码；uncertain 暂不产生，留给 OPC UA 等 G1 协议。

| 情形 | 输出 | 原因码 |
|---|---|---|
| 读取超时 | 从 values 省略，quality 标 bad | readTimeout |
| 设备返回异常（如 Modbus 异常码，异常码在诊断中显示） | 同上 | deviceException |
| 其他读取错误（连接中断、响应校验失败） | 同上 | readError |
| 超出目标类型范围 | 同上 | overflow |
| 浮点值为 NaN 或无穷 | 同上 | nonFinite |
| 类型无法转换 | 同上 | conversionFailed |
| 来源字段已是 bad | 目标字段沿用来源的原因码 | 同来源 |
| JSON 输入中的可选字段不存在 | 从 values 省略，也不列入 quality，即“未携带” | — |
| 必填字段属于以上任一情形 | 该路径本条消息不生成投递，计入“必填字段失败” | — |

### 6.5 通用输出

MQTT：固定 Broker 连接、Topic、QoS 0/1；Topic 只允许白名单占位符，例如 `{deviceKey}`，不执行字符串表达式。会拼进 Topic 的标识（deviceKey 等）只允许 ASCII 字母、数字和 `-`、`_`、`.`，长度 1–64，首字符为字母或数字，创建时校验；拼接后再校验 Topic 不含 `+`、`#` 和空字符（U+0000）。实时遥测默认不使用 retained 消息。

HTTP：固定连接与路径、POST JSON、超时、必要的静态请求头。成功规则默认是 HTTP 2xx；明确提供业务码判断时，只做固定字段等值判断，不引入规则语言。

输出报文支持“直接 JSON”与“配置式字段组装”。通用 MQTT/HTTP 输出默认使用标准信封（schemaVersion、messageId、sourceMessageId、deviceKey、collectedAt、timeSource、values、quality，与第 9.4 节的平台报文结构相同），也可以改为只发数值，或配置式字段组装（`docs/functional-spec.md` 第 5.5 节）。字段组装通过 JSON 序列化生成，不能用字符串拼接把输入内容插入 JSON。

通用 HTTP 接收方若不支持幂等，重试可能造成重复；通用 MQTT 的确认仅按协议保证，不代表下游平台已持久化。界面与文档必须明确区分“发送确认”和“业务处理成功”。MQTT QoS 与确认语义依据：[OASIS MQTT 3.1.1](https://docs.oasis-open.org/mqtt/mqtt/v3.1.1/os/mqtt-v3.1.1-os.html)。

通用 HTTP 输出默认携带 `Idempotency-Key: <deliveryId>` 请求头；报文组装提供 `{messageId}`、`{sourceMessageId}`、`{collectedAt}` 白名单占位符，便于接收方去重。MQTT 3.1.1 没有用户属性，编号只能放在报文中。

### 7.2 首版连接规则

- 只支持有向无环图；支持一对多分发，也支持扇入：一个处理或输出节点可以有多个上游，每条消息独立处理，设备身份取自消息自带的 deviceKey。不支持多输入合并（join）。
- 输入节点无输入端口；输出节点没有下游。本文中“路线”指一个图文档，“路径”指从一个输入到一个输出的一条链路。运行时编译器从每个输入出发展开可达路径，不假设图为树形；消息处理的成败以路径为单位。
- 至少包含一条输入到输出的完整路径，不接受悬空节点、环、未知类型或缺少引用的配置。
- 同一 inputId 只建立一个实际接入实例，然后在内部分发给引用它的路线，不因连了两个输出就采集两次。
- 一个输入节点可以引用多个同类数据来源（类型相同、字段描述一致）。编译时展开为多个输入，汇入同一个下游节点，每条消息保留自己的 deviceKey。这是评审中列为 G1 的“输入集合节点”的最简版本，提前到首版。
- 同一台设备经多条路径发往同一个平台连接时，各路径可以发送不同字段，但同名字段的类型和单位必须一致，否则按路线错误处理，不能应用。
- 每条启用路线设置节点上限，默认 50。该值是防误配置限制，不是性能承诺。多来源输入节点按一个节点计算，一个节点最多包含 500 个数据来源（默认值）。
- 路径上限：编译器把全部启用路线合并展开后，每个数据来源（多来源节点展开后的单个输入）的可达路径数不超过 32，整个运行计划的路径总数不超过 20,000（默认值，待实测）。同一数据来源被多条路线引用时合并计算。每条路径成功时生成一条投递，所以单条源消息最多生成 32 条投递。两条路径到达同一个输出节点（例如两个映射节点汇入同一输出）时各自生成投递，不去重。其他全局上限见第 8.7 节。
- 有界计数：先扇出再扇入的结构（菱形）会让路径数随深度成倍增加，因此不能先展开全部路径再检查。编译器按逆拓扑序做饱和计数，超限即拒绝，通过后才枚举；计数的耗时只与节点、连线和数据来源的数量成正比：

```text
输入：全部启用路线合并后的有向无环图 G；输入节点 n 展开后的数据来源集合 S(n)
上限：P_src（每个数据来源的路径数）、P_total（运行计划的路径总数）

1. 对 G 做拓扑排序；有环则拒绝（见本节第 3 条）。
2. 按逆拓扑序计算饱和路径数，不枚举：
     v 为输出节点：paths(v) = 1
     其他节点：    paths(v) = min(P_src + 1, Σ paths(w))，w 取 v 的全部下游
3. total = 0；对每个数据来源 s：
     cnt(s) = min(P_src + 1, Σ paths(n))，n 取引用 s 的全部输入节点
     若 cnt(s) > P_src：拒绝，报告 s 及其所在路线和节点
     total += cnt(s)；若 total > P_total：立即拒绝，报告已累计的数量
4. 全部通过后，才为每个数据来源枚举路径（每个最多 P_src 条），写入运行计划。
```

- 首版不做条件分支节点；多条连线代表复制分发，不表示条件判断。

### 7.3 自有流程格式

执行定义和布局分开。下面是格式示例，相关连接/采集组需先创建；不是可直接运行的完整设备配置。

```json
{
  "schemaVersion": 1,
  "id": "route-meter",
  "name": "电表转发",
  "enabled": true,
  "nodes": [
    {"id": "n1", "type": "input.modbus", "version": 1, "config": {"inputId": "group-meter-1"}},
    {"id": "n2", "type": "output.tenon", "version": 1, "config": {"connectionId": "platform-main"}}
  ],
  "edges": [{"source": "n1", "target": "n2"}],
  "layout": {
    "nodes": {"n1": {"x": 80, "y": 120}, "n2": {"x": 380, "y": 120}}
  }
}
```

后端不认识画布组件的私有状态；前端负责转换。未知 schemaVersion 或节点版本应拒绝导入/应用，不能猜测后执行。软件升级后，已保存快照的旧 schemaVersion 由逐版本升级器（vN 到 vN+1，纯函数，带测试）转换；不支持降级，升级前自动备份。

### 7.4 配置应用

首版使用“全局草稿 + 不可变快照”。连接、点位和路线一起编译为一致的快照：revision 单调递增、不复用（分配时也不低于 SystemState 中记录的下限，第 10.4 节），附内容哈希。界面按钮为“应用全部变更”，不假装支持细粒度无中断发布。数据库保存 effectiveRevision、previousRevision、pendingRevision 三个指针。保存只更新草稿，不影响运行；草稿带版本号，保存时做乐观并发检查，避免多人编辑互相覆盖。

**激活边界**：新版本在 effectiveRevision 提交之前，只允许构建运行单元，不启动任何输入、不生成投递、不向外发送；提交之后才启动。提交之前的任何失败或中断，运行配置都仍是原版本；提交之后的故障属于新版本的运行故障，不自动回滚；唯一的例外是进程反复非正常退出时，启动保护自动回滚一次（见下文）。“回滚”只指配置：不撤回已经发出的数据，也不改写已经入库的待发记录。不为此引入跨库事务或分布式事务。

应用分六步，同一时刻只允许一个应用或回滚操作：

| 步骤 | 做什么 | 运行中的版本 | 期间的投递 | 失败时 |
|---|---|---|---|---|
| 1 冻结 | 请求携带用户在变更清单中确认的草稿版本号。服务端确认草稿仍是该版本，校验全部引用、节点图、字段、权限、目标地址和第 7.2 节上限（不以外部设备暂时断线作为静态配置无效的依据），编译出 rN+1，在同一事务中写入快照与 pendingRevision | rN | 只有 rN | 草稿版本已变：返回冲突，要求刷新变更清单；校验失败：不生成版本 |
| 2 准备 | 按 rN+1 构建全部运行单元，只做本地计算：快照升级与解析、类型与模块注册、凭证存在且可解密、静态资源冲突（如两个 MQTT 连接使用同一 ClientId）、第 9.4 节字段结构比较；与 rN 对比得出要停止和新增的单元；做第一次第 8.3 节目标变更检查 | rN，不停止 | 只有 rN | 结构性失败：放弃 rN+1，rN 没有任何中断 |
| 3 静默 | 停止 rN 的全部输入单元（有超时）：MQTT 输入先停止接收，此后到达的消息不处理、不确认；排空输入通道和分发器，由写者提交，并按到达顺序发出应有的确认；然后断开带输入的 MQTT 连接（第 6.2 节）；再做一次第 8.3 节检查 | rN 的输入逐个停止；发送者照常，只有与这些 MQTT 连接共用客户端的发送暂停到第 5 步 | rN 的在途消息仍按 rN 处理 | 停止超时、目标检查拦截或提交失败：放弃 rN+1，已停止的输入按 rN 重新启动；未退出的单元按下文单实例规则处理 |
| 4 提交 | config.db 单事务：previous = effective，effective = rN+1，清空 pending，记录应用人和时间；回滚操作按下文同时处理草稿；登记第 8.3 节的迁移意图 | 无输入运行 | 无新投递 | 事务失败（如存储异常）：同第 3 步 |
| 5 激活 | 先协调发送者（新连接启动；参数有变化的连接重建客户端，在途发送取消、记录保持待发；不再被引用且没有待发数据的连接停止），再启动 rN+1 的输入和分发；带输入的 MQTT 连接等它的输入都已启动或已判为启动故障之后，才重新连接并协调订阅（第 6.2 节） | rN+1 | 按 rN+1 | 单元启动异常：只该单元故障，由监督者退避重启；不自动回滚，界面显示故障单元并提供回滚 |
| 6 稳定 | rN+1 连续运行满稳定时间（第 8.4 节）后记为“已稳定”，记运行事件 | rN+1 | 按 rN+1 | — |

- 放弃的版本在历史中标为“未生效”并注明原因，不能作为回滚目标，版本号不复用；只有生效过的版本计入保留数量。
- 适配器构建和启动都不做阻塞式网络 I/O；连接失败异步上报为“降级”，不构成应用失败（第 11 节）。
- **单实例规则**：同一运行单元 ID 同一时刻最多有一个实例存活；上一个实例的循环没有退出前，不创建新实例。停止超时的单元显示“停止超时，需重启服务”，循环退出后才按当前有效版本重新启动。因此停止超时、旧输入未退出都不会造成重复采集；进程重启时旧线程随进程结束，第 3.1 节的数据目录锁保证不会出现第二个进程。
- **草稿**：冻结之后，本次应用只使用 rN+1；应用期间草稿可以继续编辑，这些修改留给下一次应用。回滚要求开始时草稿与生效版本一致（`docs/functional-spec.md` 第 6.4 节）；提交时若草稿版本号未变，在同一事务中把草稿替换为回滚后的内容，否则保留草稿并提示。
- **启动恢复**：重启只加载有效快照，不加载未应用草稿。启动时若 pendingRevision 非空，说明上次应用在提交前中断：丢弃它，标为“未生效：进程中断”，按 effectiveRevision 启动。
- **启动保护**：只针对从未达到稳定运行的有效版本，只统计非正常退出。
  - 每次激活有效版本（应用第 5 步或进程启动）时先落盘一个“运行中”标记，按第 8.1 节停机顺序正常退出时清除；该版本连续运行满稳定时间（第 8.4 节）后记为“已稳定”，此后不再计数。
  - 进程启动时先检查、后计数：上次的“运行中”标记仍在（崩溃、被强制终止或断电），且有效版本从未稳定，则把它的非正常退出次数加一并落盘；达到上限（第 8.4 节）即触发保护，否则照常激活。正常重启、已经稳定过的版本上的退出都不计数。
  - 触发保护时，若上一生效版本曾经稳定运行，系统自动回滚到它一次：除了“开始时草稿须与生效版本一致”这一前提，与人工回滚走同一流程并生成新版本，操作人记为“系统”，不改动草稿，记审计与运行事件。草稿中仍保留引起回滚的修改，变更清单和页面提示这一点，避免下次原样再应用。回滚被第 8.3 节拦截、上一版本从未稳定，或自动回滚生成的版本再次触发保护时，进入“运行失败”：不启动输入，界面说明原因，有应用权限的用户可以回滚或重试（第 10.3 节）。
  - 人工“重试”把次数清零并激活一次；恢复备份后次数清零（第 10.4 节）。
  - 这一机制取代了评审 P1-2 “启动成功或稳定运行后才切换指针”的做法：保留“新版本起不来时自动退回上一版本”，但只在进程反复非正常退出时触发；单个运行单元启动失败只降级该单元，不整体回滚（上表第 5 步）。
- 启动时加载有效快照，若某个运行单元出现结构性失败（例如密钥丢失导致凭证无法解密、缺少模块），只停止该单元并告警，其余照常运行。有效快照损坏（内容哈希不符）时不启动运行时，报告错误，保留管理界面用于回滚或恢复，禁止静默清空配置。
- **运行失败**：输入全停，输出继续清空队列（有效快照损坏时发送者也无法启动），`/readyz` 返回 503，界面告警。

崩溃与中断的处理（“按新版本的投递”指按 rN+1 的路线生成的待发记录）：

| 中断点 | 重启后加载 | pendingRevision | 是否可能已有按新版本的投递 | 用户看到 | 测试方法 |
|---|---|---|---|---|---|
| 第 1、2 步 | rN | 丢弃，rN+1 标“未生效：进程中断” | 否 | 版本历史中的该标记和运行事件 | 在准备阶段注入进程终止 |
| 第 3 步（部分输入已停） | rN | 同上 | 否 | 同上 | 停止第 k 个输入后终止进程 |
| 第 4 步事务返回前 | rN | 同上 | 否 | 同上 | 提交前终止进程 |
| 第 4 步返回后、第 5 步中 | rN+1 | 已空 | 可能（已启动的输入） | 生效版本为 rN+1，运行事件记录重启 | 提交后立即终止进程 |
| 第 5、6 步反复非正常退出 | rN+1；达到启动保护上限后，rN 曾稳定则自动回滚到 rN 的内容（新版本号），否则或回滚后仍反复退出则“运行失败” | 已空 | 是 | 运行事件与审计：“启动保护：已自动回滚”或“运行失败”及原因 | 用启动后令进程退出的测试适配器；另测正常重启、已稳定版本上的崩溃不计数 |

快照保留最近 20 个生效过的版本（默认值）。可以回滚到其中任一版本：回滚生成一个内容与目标版本相同的新版本，走同一应用流程并先校验。回滚只改变此后的采集和发送：

- 不撤回已经发出的数据；上一版本期间已经入库的待发记录，按冻结的报文和目标继续处理，目标指纹不符时按第 8.3 节隔离。
- 同样受第 8.3 节约束：回滚会改变仍有待发或失败区数据的连接的接收方时，照样被拦截。
- 目标版本引用的连接或凭证已不存在时，阻止回滚并说明原因。凭证和平台设备的绑定状态不在快照中，不随回滚恢复；回滚造成的字段结构变化按第 9.4 节处理。

应用前显示变更清单和影响范围（`docs/functional-spec.md` 第 6 节）。

首版允许短暂采集暂停，不承诺零中断：应用配置时整体停止并重启输入。运行计划中的每个运行单元都有确定性 ID 与配置哈希，以后可以升级为只重启有变化的单元。待发记录保留已经生成的报文，不按新流程重新处理。凭证不进入快照，修改立即生效；被有效快照或上一快照引用的凭证不可删除。

## 8. 运行与有限缓存

### 8.1 运行组织

只注册一个运行时宿主（BackgroundService），由它内部的监督者管理全部运行单元：每个连接或输入的循环、分发器、发送缓存写者、每个目标的发送者和清理任务。每个单元有独立的取消令牌；异常在单元边界捕获，记录最后错误并按退避重启，不冒泡到宿主（.NET 默认会因后台服务的未处理异常而停止整个宿主）。同一运行单元同一时刻最多一个实例（第 7.4 节单实例规则）。禁止 async void 和未等待的回调。

输入到处理的缓冲有明确容量，并受全局在途字节预算约束（第 8.7 节）；输出 I/O 不阻塞整个采集循环。缓冲满时，轮询类输入（Modbus、HTTP）等待，到本周期截止仍无空位则跳过本周期并计一次 overrun；推送类输入（MQTT）按第 6.2 节处理。所有丢弃都计数可见，分类见第 8.5 节。

连接由运行时的连接管理统一持有：每个 Connection 一个客户端或会话，按引用计数供输入、输出和预览借用。同一物理连接串行访问；不同连接可在明确上限内并发。轮询类连接（Modbus、HTTP）的状态按最近一次实际读写的结果判定（共享 Modbus 连接上单个 UnitId 超时只计入该设备状态），不采信协议库的 IsConnected（.NET 的 TcpClient.Connected 也只反映上一次 I/O 时的状态）；MQTT 连接空闲时没有读写，以保活和断开事件为准。所有 I/O 有超时、取消和资源释放；停止单元时，等待其循环退出后再释放资源。库不支持真正取消时，设置传输超时并通过释放连接打断，不依靠不断 Task.Run 避免阻塞。

停机顺序：停止输入，排空通道，由发送缓存写者做最后一次提交，再停止发送（在途发送取消，记录保持待发）。宿主的停机超时与容器的停机宽限期对齐。

进程内调度（退避、周期、超时）使用单调时钟（注入 TimeProvider，便于测试）。网关检测系统时钟是否已同步（检测方式在 T1 核实），在诊断页显示；未同步时，由网关生成的 collectedAt，其 timeSource 记为 gateway-unsynced。输出按目标独立处理。计数器每 10 秒采样一次，内存中保留最近 1 小时的数据，用于界面上的趋势图，重启后清空。简单计数器和最后错误即可，不建设追踪平台或自定义分布式调度器。

### 8.2 发送缓存的最小实现

发送缓存使用独立的 SQLite 文件 queue.db，由 Runtime 直接通过 Microsoft.Data.Sqlite 读写；配置库 config.db 由 Host 通过 SqlSugar 访问。两库分开，写入争用、损坏范围和备份策略互相隔离。不要同时实现文件队列、Redis 队列和多个持久化引擎。

投递目标即 Connection，也就是 Broker、HTTP 服务或平台连接。队列分区、发送者、退避与暂停状态、配额、第 8.3 节的身份指纹都以 connectionId 为单位；路线节点只作为统计标签。

发送记录包含：

- seq（FIFO 顺序）、deliveryId：入库时生成，作为该目标下这次投递的稳定编号。
- sourceMessageId、deviceKey、routeId 与节点标签、生成该记录的配置版本号、connectionId。
- 已转换的报文，冻结的 topic/path、QoS 和非秘密请求头。凭证不写入记录，发送时从当前 Connection 解析。
- 目标指纹及其可读摘要（第 8.3 节）、创建时间、失败次数（用于毒消息判定，计数规则见下）、状态（待发、失败区、隔离及隔离原因）、最后错误、迁移编号。退避到期时间和暂停状态属于目标，按 connectionId 保存在内存中；重启后，每个目标先用一条记录探测，成功后再恢复正常发送。管理员的手动暂停是例外：它保存在 config.db 中，重启后保持，只能手动恢复；暂停期间数据照常入队，按配额和保留期处理（`docs/functional-spec.md` 第 8 节）。

写入组织：只有一个写者任务，入库、删除和状态变更都经由它，按短间隔（如 50–100 毫秒）或条数分组提交。journal_mode=WAL，synchronous=FULL。读连接只开短事务。一条源消息扇出到多个目标时，各目标的记录在同一事务中插入；超出配额的目标只记拒绝计数。

流程：生成目标报文 -> 分组提交 -> 发送 -> 获得约定确认 -> 在下一次分组提交中删除，并更新计数。

- 承诺范围从包含该记录的分组提交返回时开始（本文称“接管”）。输入内存阶段、设备未被采集的变化及磁盘硬件损坏不在此保证内；断电后仍然保留，前提是存储设备如实执行 fsync。各阶段的含义、丢弃分类和故障矩阵见第 8.5 节。
- 同一进程内，已确认但删除尚未提交的记录由发送者在内存中标记，不再发送。进程在发送后、删除提交前退出，恢复时会重发：可能重复的记录限于最后一个提交间隔内已确认的记录，加上退出时正在发送的记录（不超过各目标的在途上限）。TenonIoT 依靠稳定编号识别重复；不得宣称全链路 exactly-once。
- 输出适配器返回四类结果：
  - Ack：删除记录。平台返回 accepted 或 duplicate 都视为 Ack。
  - Retry（网络错误、超时、HTTP 408/429/5xx、无法识别的响应）：按目标整体退避（指数加抖动，最高 60 秒；遵守合理的 Retry-After 并设上限），只用队头的一条记录探测。
  - SuspendTarget（认证失败 401/403、TLS/证书错误、平台身份冲突、重定向 3xx，以及本节未列出的其他 4xx，例如 404、405）：暂停整个目标，记录保持待发、不计入失败。该连接的凭证更新，或连接配置变更并应用后，自动重新探测；其他情况由管理员手动恢复。路径错误造成的 404/405 不能靠改配置解决：待发记录冻结了原路径，而第 8.3 节在有待发数据时禁止改路径，须先清理。
  - RejectMessage（400/413/422 字段错误、409 内容冲突，即报文级确定性错误）：只把该条移入失败区；修正后允许人工重试。同一目标连续 20 条被拒、其间没有成功时（第 8.4 节），视为目标级问题，按 SuspendTarget 暂停该目标，后续记录保持待发。问题若出在网关侧的映射或请求头，已生成的待发记录不会按新配置重新生成，恢复后仍会被拒。
- 未知异常按 Retry 处理。毒消息判定：
  - 计数：只有目标已给出响应的非临时失败（502、503、504 以外的 5xx，以及无法识别的响应）和本地未知异常，计入记录的失败次数。连接失败（包括读取响应途中连接中断）、超时、408、429 与 502、503、504 只触发目标退避；网关主动取消的发送（停机、应用配置）不计数。
  - 判定：队头记录的失败次数达到阈值后，探测改用其后第一条未达阈值的记录。它成功，说明目标可用，随即重试队头；队头仍出现计入的失败，就把队头移入失败区，防止毒消息卡住队头。它失败，则照常计数并继续退避。其后没有未达阈值的记录时，继续用队头探测，这时队头的失败只计数、不移入失败区。连续多条毒消息因此会逐条被识别。
  - 局限：超时与 408 不计入，所以每次都超时的记录（例如慢速上行链路上的大报文）不会被识别为毒消息，会阻塞该目标直到过期；诊断页显示队头阻塞时长。
- 失败区按目标计数，按目标和全局分别设上限，单独设保留期，不挤占待发配额；失败区满时，新的失败记录不再保留，只计数。
- 确认必须是真实的协议确认：MQTT QoS 1 以 Broker 的 PUBACK 为准，发布操作必须带超时；超时、未连接和连接中断都以异常出现，按 Retry 处理；MQTT 5 的 PUBACK 原因码由 MQTTnet 放在返回结果中、不抛异常，须检查结果（3.1.1 的 PUBACK 没有原因码）。QoS 0 只能按本地发送完成判断，可靠性较弱。二者都不等于最终业务存储确认。
- 每个目标有在途上限（默认值见第 8.4 节）。通用目标在重试和并发下可能乱序，接收方应以 collectedAt 判断新旧；积压补传按 FIFO，毒消息探测会让被探测的记录先于队头送达。
- 单目标缓存满时，只拒绝该目标的新记录并增加丢弃计数；不能拖垮整个进程或悄悄挤掉其他目标的数据。
- 过期记录可清理，但必须累计过期数量并提示，计数持久化。人工重试的记录，保留期从重试时重新计算。过期判断有时钟跳变保护：创建时间落在未来，或与启动时刻的差距异常时，标记“时钟异常”而不是清理。人工清理要权限、确认和审计。
- 可用磁盘空间低于阈值时进入“存储保护”：拒绝新的入队并计数，为删除、检查点、管理界面和日志保留余量；空间恢复后自动退出。数据库写入失败（如 SQLITE_FULL）时显式回滚，不绕过持久化假装成功，显示“存储异常”，统计无法入库的数据，不无限占用内存。

### 8.3 配置变更与缓存

首版采用简单规则：存在待发送或失败区数据时，不允许把对应连接切换成其他服务器或接收方，也不允许修改会改变接收方的输出 Topic 或路径。用户先发送完毕、显式清理，或由管理员选择“迁移待发记录”后再改。更换凭证不被阻止，由下文的目标指纹和凭证规则保护。

- 检查在第 7.4 节第 2 步做一次，停止输入之后（第 3 步）再做一次，避免校验与停止之间新产生的记录漏检。
- 删除连接、设备绑定和输出配置前检查引用及待发数据。不得把旧数据自动转发到新客户或新平台。

**目标指纹。** 每条记录入库时保存目标指纹（哈希），以及一段不含秘密的可读摘要，供诊断和迁移时核对。指纹由决定“数据交给谁”的参数组成；超时、ClientId、保活间隔等不改变接收方的参数不计入，DNS 解析结果也不计入：

| 连接类型 | 指纹组成 |
|---|---|
| MQTT | 是否 TLS、主机（小写）、端口、账户标识、账户标记 |
| HTTP | scheme、主机、端口、基础路径、账户标识、账户标记 |
| TenonIoT | scheme、主机、端口、基础路径、平台返回的 GatewayId |

账户标识取凭证中不属于秘密的部分：MQTT 与 Basic 的用户名、客户端证书的主题；Token、API Key 没有可见标识，只记凭证类型。账户标记是连接上的一个随机值，只在用户声明“更换了接收账户”时重新生成；用随机值而不用递增计数，是为了恢复旧备份后不会重新出现已经用过的值。

真正的保证在发送时：发送者比较记录的指纹与连接当前的指纹，不一致就不发送，把记录转为“隔离”。隔离记录单独存放，不阻塞后续记录，不占该目标的待发配额（仍计入全局配额），按原保留期过期并计数；目标详情显示其数量，管理员可以清理、导出（格式同失败区）或迁移。隔离原因有三种：目标已变化（指纹不符）、目标不存在（连接已删除，或恢复配置后不存在）、配置库来源不同（第 10.4 节）。

**更换凭证。**

- TenonIoT：更换凭证后，该目标先停止发送，用新凭证调用 /connect、更新指纹后再恢复。GatewayId 不变，是同一接收方的凭证轮换，待发记录照常发送；GatewayId 变化，是接收身份变化，旧记录被隔离，设备须按新的 GatewayId 重新同步。
- 通用 MQTT/HTTP：网关无法验证凭证背后的账户属于谁，不以“地址相同”推定接收方相同。账户标识（用户名、证书主题）变化时，指纹随之变化，旧记录被隔离，保存前提示将被隔离的条数。账户标识不变或没有可见标识（Token、API Key、同主题的新证书），且该连接有待发或失败区数据时，保存凭证必须明确选择“同一账户的凭证轮换”（记录照常发送）或“更换了接收账户”（重新生成账户标记，旧记录被隔离）；没有默认选项，所作选择记审计。没有待发和失败区数据时不询问。

**迁移待发记录。** 管理员把待发、失败区或隔离记录交给指定的目标连接。有两种形式，规则相同：

| 形式 | 场景 | 改变什么 |
|---|---|---|
| A. 同一连接换地址 | 修改连接的接收方被本节规则拦截时，管理员在应用的变更清单中对该连接选择“迁移到新地址” | 只改指纹 |
| B. 迁移到另一个连接 | 在目标详情中选择另一个已生效的同类连接 | connectionId 和指纹都改 |

- 权限与审计：仅管理员；二次确认；审计记录发起人、源与目标的可读摘要、条数和结果。
- 组合：只允许同类型之间迁移（MQTT→MQTT、HTTP→HTTP、TenonIoT→TenonIoT）。目标连接须在有效配置中且已启用，出站校验照常适用。
- 接收方核对：TenonIoT 目标连接最近一次 /connect 返回的 GatewayId 必须与记录指纹中的相同，否则拒绝，所以数据不能迁到其他平台身份。通用 MQTT/HTTP 无法在技术上核对：界面并排显示源与目标的地址、账户标识和 TLS 证书主题，管理员须勾选“新接收方与原接收方属于同一数据所有者”。这是记入审计的人工声明，不是技术保证。
- 配额：目标连接剩余的待发配额（条数与字节）须容纳全部所选记录，否则整体拒绝并显示缺口，不做部分迁移。
- 保持不变：deliveryId、seq（先进先出的位置）、sourceMessageId、deviceKey、路线标签、冻结的报文（含 messageId 和 collectedAt）、冻结的 topic/path/QoS/非秘密请求头、创建时间（保留期照常计算）。HTTP 的冻结路径拼接到目标连接的基础地址之后。
- 改变：connectionId（形式 B）、指纹与摘要、状态（待发和隔离记录变为待发，失败区记录仍留在失败区）、失败次数清零、迁移编号。
- 在途请求：执行前暂停源和目标的发送者，等待在途发送结束或取消（不超过发送超时）；在途结果为确认的记录已被删除，不参与迁移，其余照常迁移。
- 执行：由写者在 queue.db 的一个事务中更新全部所选记录，并在同一事务中写入完成记录（迁移编号、条数），再恢复发送者。config.db 中的迁移状态随后同步；两者不一致时以 queue.db 的完成记录为准。
- 形式 A 的意图：变更清单按当前配额和连接类型预检，不满足的不能选择“迁移到新地址”。意图在第 7.4 节第 4 步随配置一起提交，记下旧指纹；目标取得新指纹后执行（TenonIoT 须先用新地址完成 /connect，完成前意图保持等待，页面显示“迁移等待目标连接”），执行时再检查一次配额和接收方核对规则。执行只处理指纹等于所记旧指纹、状态为待发、失败区或因目标变化而隔离的记录；执行之前这些记录处于隔离状态，既不发往旧地址，也不发往新地址。检查不通过（例如配额不足、GatewayId 不同）时意图标为“已拒绝”，记录保持隔离，记审计与运行事件；管理员可以在条件满足后重新执行该意图（记审计），也可以清理、导出或改用形式 B。等待中的意图不阻止之后的应用；同一连接之后再次换地址时登记新的意图，多个意图按登记顺序执行，各自只处理自己记下的旧指纹。
- 中断恢复：迁移事务要么全部生效，要么全部不生效。启动时按 queue.db 的完成记录核对：等待中的形式 A 意图继续等待或执行；审计中只有“开始”没有结果的迁移，补记实际条数，或补记“未执行：进程中断”。

### 8.5 可靠性口径：接管、确认与丢弃

本节是设计文档、功能需求和验收中可靠性表述的唯一口径。其他位置引用本节，不另写“不会丢失”“零丢失”“保证补传”之类没有前提的承诺。

**四个阶段**

| 阶段 | 含义 | 能抵御 | 不能抵御 |
|---|---|---|---|
| 内存接收 | 数据已进入进程（协议库队列、输入通道、分发、写者批次），尚未提交 | — | 进程退出：轮询类丢失这一次采样，MQTT QoS 0 丢失；MQTT QoS 1 因未确认而由 Broker 按会话重投（前提见下文） |
| 接管 | 包含该记录的分组提交已返回（queue.db：WAL + synchronous=FULL） | 进程崩溃、操作系统崩溃；断电，前提是存储设备如实执行 fsync（带易失写缓存又没有掉电保护的 SD 卡、部分 eMMC 不满足，按 HW-05 实测） | 存储损坏、磁盘硬件故障 |
| 协议确认 | MQTT QoS 1 的 PUBACK；HTTP 2xx（配置了业务码时还须业务码相等）；TenonIoT 的 accepted 或 duplicate | 此时才删除本地记录 | PUBACK 只表示 Broker 已接手，是否持久化取决于 Broker 的配置，也不表示订阅者已收到；HTTP 2xx 的含义由接收方定义 |
| 业务持久化 | 接收方已把数据写入其可靠存储 | 只有 TenonIoT 契约要求 accepted 即已持久化（第 9.4 节） | 通用 MQTT/HTTP 接收方是否持久化，网关无法判断 |

**各类输出的承诺（从接管开始）**

| 输出 | 删除本地记录的时机 | 语义 | 可能出现的情况 |
|---|---|---|---|
| MQTT QoS 0 | 本地写出成功 | 至多一次 | 连接中断时可能丢失，不重试 |
| MQTT QoS 1 | 收到 PUBACK | 至少一次 | 重复：PUBACK 丢失后重发，或确认后、删除提交前进程退出 |
| 通用 HTTP | 2xx（加业务码判断） | 至少一次 | 重复；请求带 Idempotency-Key，接收方可以去重 |
| TenonIoT | accepted 或 duplicate | 至少一次；同一 deliveryId 在平台去重窗口内只保存一次，前提是平台按第 9.4 节在同一提交中保存数据和幂等记录 | 输入侧重投会生成新的 deliveryId，平台识别不了；超出去重窗口的人工重放可能重复 |

所有输出都受保留期、配额、失败区和人工清理约束，这些是下文丢弃表中的明确策略。

**各类输入的承诺（到接管为止）**

| 输入 | 语义 | 前提 |
|---|---|---|
| Modbus、HTTP 拉取 | 采样语义：接管之前丢失的只是那一次采样，不补采 | — |
| MQTT QoS 0 | 至多一次 | — |
| MQTT QoS 1 | 从 Broker 到接管至少一次（入库后按序确认，第 6.2 节） | 上游以 QoS 1 发布；网关的会话仍在 Broker 上（未过期，未因 ClientId 改变而被弃用）；Broker 为该会话积存的消息没有超过队列上限；Broker 自身没有丢失这些消息（见故障矩阵）；消息没有被网关按下文丢弃表中的策略丢弃（这类消息计数后照常确认） |

**去重边界**

- 发送侧：重试沿用同一 deliveryId（即平台报文的 messageId、HTTP 的 Idempotency-Key），接收方可以识别重复。
- 输入侧：Broker 重投的 QoS 1 消息被当作新消息，生成新的 sourceMessageId 和 deliveryId，平台的去重识别不了。重投只发生在“已收到、尚未确认”的消息上，数量受 Broker 在途窗口和输入通道约束。用上游事件 ID 派生投递编号属于后续候选（第 21.4 节）。

**丢弃与计数**

| 情形 | 性质 | 处理 | 计数范围 |
|---|---|---|---|
| 待发或隔离记录超过保留期 | 策略 | 清理 | 按目标 |
| 单目标待发配额满 | 策略 | 拒绝该目标的新记录，其他目标照常 | 按目标 |
| 全局配额满 | 策略 | 拒绝全部目标的新记录 | 全局 |
| 存储保护 | 策略（保护） | 拒绝新的入队 | 全局 |
| 失败区满 | 策略 | 新的失败记录只计数、不保留 | 按目标 |
| 管理员清空或清理 | 策略（人工） | 删除，记审计 | 按目标 |
| QoS 0 输入通道满、在途字节预算用尽 | 策略 | 丢弃 | 按输入 |
| 轮询周期超时 | 策略 | 跳过本周期（overrun） | 按输入 |
| 设备未绑定、字段待同步、已解除映射；保留消息被忽略 | 策略 | 不生成投递 | 按设备与目标；保留消息按输入 |
| 非法报文、超限、必填字段失败 | 数据错误 | 该路径不生成投递 | 按输入与路径 |
| SQLite 写入失败（存储保护以外） | 故障 | 显式回滚本批，显示“存储异常”；MQTT QoS 1 不确认并断开，由 Broker 重投；其他输入的本批数据丢失 | 全局 |
| queue.db 损坏 | 故障 | 移到一旁并新建空库，记运行事件；旧库可读时统计其中条数，否则记为数量未知 | 全局 |
| 进程退出时内存中的数据 | 故障 | 丢失，QoS 1 输入由 Broker 重投 | 无法计数，在文档中说明 |

- 计数由发送缓存写者随分组提交保存在 queue.db，最长 10 秒写一次，是安装以来的累计值；进程异常退出最多丢失最近一次落盘之后的增量。queue.db 重建后计数从零开始，并记运行事件。
- 策略性丢弃在界面上显示为“按规则丢弃”并注明规则；故障显示为“异常”，同时记运行事件。两类都不静默。
- Broker 在网关之外丢弃的消息（超出积存上限、会话过期）网关收不到，也无法计数，只能从 Broker 日志和第 6.2 节的“会话丢失”事件中发现。

**故障矩阵**

| 事件 | 已接管的待发记录 | 进程内存中的数据 | 附带 Broker 中尚未被网关确认的 QoS 1 消息 |
|---|---|---|---|
| 只有网关进程重启（包括被强制终止） | 保留；最后一个提交间隔内已确认的记录和退出时正在发送的记录可能重发一次 | 丢失；QoS 1 由 Broker 重投 | 保留，受 Broker 积存上限和会话过期约束 |
| Broker 异常退出 | 不受影响 | 网关断开后重连，未确认的 QoS 1 消息重投 | 只剩 Broker 最近一次持久化保存的内容，两次保存之间收到的消息会丢失 |
| 整机断电 | 保留（前提：fsync 如实） | 丢失 | 同上 |
| 存储损坏 | 可能丢失；queue.db 损坏按上表处理 | — | 可能丢失 |

config.db 写入量小，同样使用 WAL 和 synchronous=FULL，使配置提交（包括第 7.4 节第 4 步）在断电后仍然有效；SqlSugar 连接上执行 PRAGMA 的方式在 T0 核实。Microsoft.Data.Sqlite 默认带的原生库编译时已把 synchronous 默认值设为 FULL，但仍显式设置并在启动时回读，不依赖所加载原生库的编译选项。config.db 损坏时运行时不启动，从备份恢复（第 10.4 节）。

**附带 Broker 的部署检查**

附带的 Broker（第 3.1 节）是 MQTT QoS 1 输入可靠性的一部分。安装模板和整机出厂检查逐项确认，实测结果写入部署文档；换用其他 Broker 时按同样的项目核对。Mosquitto 的默认值不满足下表：默认不开启持久化；传统持久化每 1800 秒整库快照一次；每个客户端最多积存 1000 条消息（不含在途），超出后丢弃新消息，只记一次日志。模板必须显式设置各项，所用版本和持久化方式（传统快照，或 2.1 起官方推荐的 persist-sqlite 插件）在 T0 至 T2 实测后选定（来源见 `docs/development-readiness.md` 第 5.1 节）。

| 检查项 | 要求 |
|---|---|
| 持久化 | 开启；持久化文件位于持久挂载的数据卷，不在容器可写层 |
| 持久化间隔 | 显式设置并记录。Broker 异常退出或断电时，最近一次落盘之后收到的消息会丢失，这个间隔就是丢失窗口：传统持久化是快照间隔，persist-sqlite 插件是批量提交间隔（断电时还取决于其同步级别）。间隔越短写入越频繁，按存储寿命权衡 |
| 每个会话的积存上限（条数、字节） | 不小于“上游消息速率 × 网关最长计划停机时间（重启、升级、应用配置）”；超出后 Broker 丢弃新消息 |
| 报文大小上限 | 不小于设备报文与网关的输入上限（第 8.4 节）；Mosquitto 2.1 起默认限制为 2,000,000 字节 |
| 会话过期 | 足以覆盖计划停机，同时让废弃的会话（例如改过 ClientId 的旧会话）最终被清理 |
| 在途窗口 | 记录取值；网关 QoS 1 输入的吞吐约为“在途窗口 ÷ 分组提交间隔” |
| 认证与授权 | 禁止匿名；每台设备单独账号，只能发布自己的 Topic；网关账号只订阅 |
| 实测 | 网关重启期间设备持续以 QoS 1 发布，恢复后补收完整；超过积存上限时的丢弃行为；Broker 被强制终止后的实际丢失窗口（AT-27） |

### 8.6 缓存容量估算

某个目标断网期间能积存多久，同时受四项限制，取最小值：

```text
r = 该目标每秒新增的记录数；s = 平均每条冻结报文的字节数
T_条数 = (单目标条数上限 − 当前待发条数) ÷ r
T_字节 = (单目标字节上限 − 当前待发字节) ÷ (r × s)
T_全局 = (全局上限 − 全部待发与隔离字节) ÷ Σ(正在积压的各目标的 r × s)
T_磁盘 = (可用空间 − 存储保护阈值) ÷ (Σ(r × s) × k)，k 为 SQLite 页、索引与 WAL 的放大系数（待实测）
可积存时长 = min(T_条数, T_字节, T_全局, T_磁盘)
```

保留期决定数据最多在队列里停留多久，不决定能积存多久：断网超过保留期，最早的数据开始过期；断网短于保留期，数据也可能因为上面任一限制先被拒绝。所以“保留 24 小时”不等于“能缓存 24 小时的数据”。

示例（全部为假设，不是实测结果或承诺）：10 台 Modbus 设备，每台每 5 秒一条消息，同时发往 TenonIoT 目标 A 和 MQTT 目标 B；每条冻结报文约 5,500 字节（约 100 个点位、稀疏 quality 的估计）；使用默认上限；只有 A 断网，B 正常发送、没有积压。

| 项目 | 计算 | 结果 |
|---|---|---|
| A 的速率 | 10 × (1 ÷ 5) | 2 条/秒 |
| T_条数 | 10,000 ÷ 2 | 5,000 秒，约 1.4 小时 |
| T_字节 | 64 MiB ÷ (2 × 5,500 字节) | 约 6,100 秒，约 1.7 小时 |
| T_全局 | 256 MiB ÷ 11,000 字节/秒 | 约 24,400 秒，约 6.8 小时 |
| 保留期 | 24 小时 | 不起作用 |
| 可积存时长 | 取最小值 | 约 1.4 小时，由条数上限决定 |

要让 A 积存 12 小时，约需 86,400 条、约 475 MB（2 × 43,200 × 5,500 字节）：单目标的条数与字节上限、全局上限都要相应调高，磁盘按放大系数 k 和存储保护阈值留足余量；A、B 同时断网 12 小时，全局上限至少要容纳约 950 MB。调高之前，在目标硬件上实测写入和清理的开销（HW-06）。

### 8.7 资源保护上限

下列上限防止误配置或异常输入耗尽进程资源。默认值待实测，管理员可以在运行参数中调整；开源版与企业版相同，不作为版本差异或收费门槛（第 15.2 节）。配置超限在应用前的校验中拒绝；运行中超限按下表处理并计数。

| 资源 | 默认上限 | 超限时 |
|---|---|---|
| 路线节点、多来源节点的数据来源、路径 | 见第 7.2 节 | 校验失败，不能应用 |
| 运行计划中的数据来源 | 合计 2,000 个 | 校验失败 |
| 连接 | 合计 500 个，其中 Modbus 连接 256 个（每个占一个专用线程） | 校验失败 |
| 每个输入通道 | 100 条待处理消息 | 轮询类等待，到本周期截止仍无空位则跳过并计 overrun；推送类按第 6.2 节 |
| 在途消息字节：从接收到入库提交（或确定不入库）为止，含由它生成、尚未入库的报文 | 全局 64 MiB | 同上；单条消息本身超过预算时按超限拒绝 |
| 调试缓存 | 见下文 | 淘汰最早捕获的条目 |
| 同时进行的预览与测试：读取一次、抓取实时消息、现场读、测试连接、发送测试报文 | 全局 4 个，每个会话 2 个 | 立即返回“当前预览任务过多”，不排队 |
| 后台操作：应用或回滚、手动设备同步、迁移、配置导入、备份、恢复、诊断包导出 | 每一类同时只运行一个；应用、正在执行的迁移与恢复三者互斥（等待中的形式 A 迁移意图不算，第 8.3 节） | 立即返回“正在进行”，不排队 |
| 预览读取的外部响应 | HTTP 拉取最多读 1 MiB（同输入上限）；发送测试报文的响应最多读 64 KiB；界面最多显示 64 KiB | 超出部分不读取，并标注已截断 |
| 配置导入文件、点表 CSV | 见第 8.4 节 | 拒绝导入 |
| 管理 API 请求体 | 按接口设置；默认 1 MiB，导入和恢复接口单独放宽 | 返回 413 |

调试缓存：

- 持续记录运行中各输入、输出的最近消息，与调试面板是否打开无关；面板只影响界面刷新。只存内存，不落盘。
- 单条在捕获时截断，只保存前 64 KiB（按 UTF-8 字符边界截断，不拆开多字节字符），同时记录原始字节数和“已截断”标记。界面显示的就是保存的内容，显示截断与存储截断一致，不会出现“界面只显示 64 KiB、内存里保存 1 MiB”。
- 每个输入、每个输出最多 100 条且合计不超过 1 MiB，全局不超过 32 MiB；超出任何一项，淘汰最早捕获的条目（全局超出时跨对象按捕获时间淘汰）。
- 应用新版本后不再存在的对象，其条目立即释放；重启后全部清空。
- 路线预览的第一种样本来源（运行中输入的最近消息）取自这里；该输入的条目已被淘汰或被截断时不能用作样本，提示改用“现场读一次”。

## 9. 与 TenonIoT 的联动

### 9.1 已确定的交付边界

首版网关本地配置是唯一配置来源。平台仅接收关联信息、数据和状态，不反向改网关配置。

平台的存在不影响通用输出。TenonIoT 连接器复用 HTTP 输出的凭证、请求和缓存基础，但额外处理平台身份、设备映射和业务确认。

### 9.2 使用流程

1. 平台管理员创建网关及专用凭证。
2. 用户在 TenonEdge 新建 TenonIoT 连接，输入地址和凭证，测试连接。
3. 用户选择需要同步的设备及最终输出字段。平台按授权创建新设备，或由平台管理员关联已有设备。
4. 画布中使用 `output.tenon`，引用该平台连接。
5. 网关发送数据与心跳。平台分别显示网关在线状态、设备采集状态和数据时间。

没有平台源码时，使用 `tests/TestPlatform` 验证以下接口，不搭建完整云平台。测试端只用于研发，发布包默认不包含它。

### 9.3 身份与设备映射

- NodeId：网关首次初始化生成的本地身份，重启保持不变。复制部署不能复制身份，须有明确的重置操作：管理员在系统信息中执行“重置网关身份”，需二次确认，并记审计；还有发往平台的待发记录时不能重置。
- GatewayId：平台登记的网关身份，由凭证确定，不由任意请求体中的字段决定。
- deviceKey：网关内稳定逻辑设备标识，字符集见第 6.5 节。设备改名不改 key。
- PlatformDeviceId：平台设备 ID。
- 绑定关系：平台连接 + GatewayId + deviceKey -> PlatformDeviceId，附同步状态（已绑定、待关联、被拒绝、字段待同步、已解除；字段待同步时另记原因：应用判定或平台拒收）和最近一次同步成功的字段结构标识（第 9.4 节）。

平台凭证首次连接可绑定一个 NodeId；另一个实例用同一身份连接应拒绝或要求管理员明确重新绑定，不静默顶替。网关在 `/connect` 和心跳中携带 bootId：每次进程启动时随机生成，不持久化。平台在一个心跳窗口内看到同一身份的两个 bootId 交替出现，即判定为身份冲突。

平台只接收被授权设备的数据。网关不能通过提交其他组织 ID、其他网关 ID 或任意 PlatformDeviceId 越权。

同步的是设备和输出属性描述，不是 Modbus 地址、密码或整个画布。比例换算或重命名后的字段，以最终输出类型、key 和单位为准。

### 9.4 最小接口契约

以下接口为 TenonEdge/TenonIoT 拟定协议，不是参考项目已有接口，也不意味着 TenonIoT 当前已经实现。

统一路径前缀：`/api/edge/v1`。所有请求使用 HTTPS，凭证放 `Authorization: Bearer <gateway-token>`，不得放 URL、Topic、导出文件或普通日志。

| 方法与路径 | 用途 | 核心请求内容 | 成功结果 |
|---|---|---|---|
| `POST /connect` | 验证并绑定网关 | nodeId、bootId、agentVersion、protocolVersion | gatewayId、serverTime、去重窗口 |
| `POST /devices/sync` | 幂等更新所选设备清单 | catalogVersion、deviceKey、名称、字段定义 | 每项 created/bound/pending/rejected 状态及映射 |
| `POST /telemetry` | 单设备数据上报 | messageId、deviceKey、collectedAt、timeSource、values、quality | accepted 或 duplicate |
| `POST /heartbeat` | 当前运行状态 | sentAt、bootId、agentVersion、设备采集状态摘要、失败/待发计数 | 平台当前接收时间 |

成功响应统一为：`{"code":"ok","data":{...}}`；失败响应包含稳定的字符串 code、message 和可选 fieldErrors，并配合正确 HTTP 状态码。若实际平台已采用统一响应封装，以生成的 OpenAPI 统一调整双方，不允许一边手改后不同步。平台为 `/api/edge/v1` 单独实现本约定，不沿用“业务错误返回 HTTP 200”的通用封装。网关同时校验 HTTP 状态码和响应中的 code；无法识别的响应按重试处理，不当作成功。

#### 设备同步

- `/devices/sync` 是 upsert，不是删除接口；本次未出现的设备不得自动删除。
- 不以名称相等自动合并客户设备。关联已有设备在平台受权限控制的界面完成。
- 平台可设置该网关是否允许自动创建新设备；关闭时返回 pending，不能开放任意创建权限。
- 重复同步同一 deviceKey 不重复创建。字段类型冲突返回 rejected 并说明，不能静默改变历史属性含义。
- 未绑定设备不得当作其他设备上传。网关在路由阶段不为未绑定设备生成投递，只计数并提示；平台对误发的数据返回明确错误。关联完成后恢复发送。
- 同步内容只从有效快照计算；catalogVersion 取有效快照的 revision。字段定义包含 key、类型（第 6.4 节的 boolean、integer、number、string）和单位；平台对 integer 须按 64 位整数解析，不得经过 double。
- 待关联（pending）的设备每 5 分钟自动重新同步一次，直到被关联或被拒绝，也可以手动刷新；关联之前的数据不补发。
- 字段结构：设备发往某个平台连接的字段结构，是有效快照中从该设备的数据来源到引用这个连接的 `output.tenon` 节点的全部路径输出字段的并集（key、类型、单位；同名字段已按第 7.2 节保持一致）。绑定关系保存最近一次同步成功时平台接受的结构标识（规范化后的哈希）。
- 每次应用配置时（第 7.4 节第 2 步），按新版本逐台比较已绑定或字段待同步设备的新结构与已同步结构，重新确定状态。相同或只减少了字段，为“已绑定”：由之前的应用判定为“字段待同步”的设备随之恢复，但因平台返回 schema_mismatch 而进入“字段待同步”的设备，只有手动同步成功后才恢复；只减少字段是兼容变化，照常发送，平台保留这些字段原有的最新值（见下文“数据报文”），页面提示可以重新同步。新增字段，或已有字段的类型、单位变化，是不兼容变化，提交后该设备在这个平台连接上为“字段待同步”。变更清单事先列出状态将要变化的设备，并提供“应用成功后立即同步这些设备”的选项，勾选即视为手动同步，记审计；不自动同步全部设备（`docs/functional-spec.md` 第 11 节）。
- “字段待同步”期间：网关在路由阶段不为该设备向这个平台连接生成投递，计入“字段待同步跳过”；这期间的数据不入队、不补发，与未绑定设备的处理一致。同一连接上的其他设备，以及该设备发往其他目标的路径，都不受影响，连接也不因此暂停。
- 手动同步成功（平台返回 created 或 bound）后，更新已同步结构，恢复为“已绑定”，从之后的消息开始发送。平台因类型冲突返回 rejected 时保持待同步并显示原因：已有字段不能改变类型或含义，需要换一个字段 key，或由平台管理员处理。
- 应用之前已经入库的记录仍按原结构发送；同步是 upsert，不删除平台上已有的字段，所以这些记录照常被接受。回滚造成的字段变化按同样规则处理。每 5 分钟的自动重新同步只处理待关联设备，不替代对“字段待同步”设备的手动同步。
- 可以解除某台设备在本地的平台映射（不删除平台上的设备）；解除后不再向平台发送该设备的数据，记审计。自动重新同步不记审计，结果有变化时记运行事件。

#### 数据报文

`messageId` 采用本次目标投递的 deliveryId。重试不重新生成；不同目标各有自己的投递编号。

```json
{
  "schemaVersion": 1,
  "messageId": "a4b5e193-090d-4a88-8d19-5b6b7d21f053",
  "sourceMessageId": "071529ee-c6ad-4c56-b9b6-34b0e72e5120",
  "deviceKey": "meter-001",
  "collectedAt": "2026-09-28T08:30:00Z",
  "timeSource": "gateway",
  "values": {"voltage": 220.5},
  "quality": {"current": {"status": "bad", "reason": "readTimeout"}}
}
```

quality 采用第 6.4 节的稀疏表示：voltage 未列出即为 good；current 读取超时，从 values 省略并标为 bad。

values 可以只含部分字段：某字段既不在 values 中，也不在 quality 中，表示本条未携带该字段，平台保留它原有的最新值和时间。这条语义也为以后的按变化上报（GW-22）预留，届时契约无需再改。

```json
{
  "code": "ok",
  "data": {
    "messageId": "a4b5e193-090d-4a88-8d19-5b6b7d21f053",
    "status": "accepted"
  }
}
```

平台处理约束：

- 以凭证获得 GatewayId，以 `(GatewayId, messageId)` 作为幂等键；保存记录与幂等结果在同一可靠提交边界内完成。
- 相同编号、相同内容重复请求返回 `duplicate`；相同编号而内容不同返回 HTTP 409，不覆盖原数据。
- `accepted` 必须意味着已持久保存或进入平台可靠存储，不是仅放入临时内存。
- 首版单设备消息整体校验、整体确认，不做批量部分成功。后续需要批量再扩展协议。
- `/telemetry` 的 schema 预留可选的 fieldTimes（第 6.4 节），首版网关不发送；平台不得因该字段出现而拒绝报文。
- 断网补传保留 collectedAt。旧数据可记入历史，但不能把最新值倒退到旧采样时间（最新值按字段比较时间）。
- 检查时间格式与明显未来时间；首版可拒绝超过平台时间 5 分钟的消息并明确提示校时。
- timeSource 为 gateway-unsynced 的数据仍按上一条检查时间；通过后照常保存，平台展示时标注时间不可信。
- 去重记录保留时间必须大于网关允许重试/保留时间及时间容差。初始可取 7 天；超期人工重放不声明仍有去重保证。平台在 `/connect` 响应中返回去重窗口，网关把本地保留期上限钳制在该窗口之下。

典型错误：401 凭证无效，403 无权，409 身份/内容冲突，422 设备未绑定或字段不合法，429 超限，5xx 临时服务异常。401/403/409/422 不无限自动重试。错误响应使用稳定的字符串 code。网关先按 HTTP 状态分类，再在该状态允许的范围内按 code 细分，区分目标级、设备级和报文级；code 缺失或不认识时，按该状态的默认处理。结果仍是第 8.2 节的四类：

| HTTP | code | 级别 | 网关处理 |
|---|---|---|---|
| 2xx | 响应为 accepted 或 duplicate | — | Ack |
| 2xx | 其他或无法解析（包括“HTTP 200 + 业务错误”） | — | Retry，按无法识别的响应处理 |
| 401、403 | 任意 | 目标级 | SuspendTarget |
| 409 | gateway_identity_conflict | 目标级 | SuspendTarget |
| 409 | message_conflict | 报文级 | RejectMessage |
| 422 | device_not_bound | 设备级 | RejectMessage；该设备的绑定转为“待关联”，不再为它生成投递，按待关联规则自动重新同步 |
| 422 | schema_mismatch | 设备级 | RejectMessage；该设备转为“字段待同步” |
| 400、413、422 | 其他 code 或没有 code | 报文级 | RejectMessage |
| 408、429 | 任意 | 临时 | Retry，遵守 Retry-After 并设上限 |
| 3xx，以及上面没有列出的 4xx（包括 409 的其他 code） | 任意 | 目标级 | SuspendTarget，同第 8.2 节 |
| 5xx | 任意 | 临时 | Retry（是否计入失败次数见第 8.2 节） |
| 连接失败、超时 | — | 临时 | Retry |

- 设备级拒绝只影响对应设备：该条进入失败区，设备转入相应状态后不再为它生成投递。队列中该设备已经入队的记录照常发送，被拒时同样进入失败区，条数不超过已入队的数量；设备恢复为已绑定后，之后的记录照常发送。设备级拒绝对第 8.2 节“同一目标连续 20 条被拒”的计数透明，既不累加也不清零，一台设备的问题不会暂停整个平台连接。通用 HTTP 输出没有设备语义，仍按第 8.2 节计数。
- 同一平台连接上的设备共享目标级状态：退避、自动与手动暂停、在途上限、配额、保留期和目标指纹。设备级状态（待关联、被拒绝、字段待同步、已解除）只决定是否为该设备生成投递。
- 具体 code 与 HTTP 状态的映射写入 `docs/platform-api.yaml`，TestPlatform 按同一份契约实现（第 12 节 T4）。

#### 心跳与状态

- 默认每 30 秒发送一次心跳，平台超过 90 秒未收到则显示网关离线；这是可配置初始策略。
- 在线判断使用平台接收时间，不使用补传遥测中的旧时间。
- 网关在线但部分设备读取失败时，分别显示设备错误。网关离线时，下挂设备状态显示未知或过期，不宣称设备物理损坏。
- 心跳不进入历史补传队列：只发送最新状态，丢失后等下次；不能重放旧心跳伪装在线。
- 上述 30/90 秒策略只用于 TenonEdge 与平台的连接，不用于 LoRa 传感器。MQTT/HTTP 上游连通也不代表传感器正在上报；传感器按最后报文时间与已确认的上报周期展示。未配置周期时显示最后接收时间或未知，不套用网关心跳判定掉线，见第 21.4 节。

### 9.5 平台侧最小实现清单

| ID | 平台侧工作 |
|---|---|
| PL-01 | 网关登记、启停、凭证生成/撤销、NodeId 绑定 |
| PL-02 | 设备同步、待关联处理、创建/关联权限与稳定映射 |

## 10. 管理 API、数据和安全

### 10.1 本地管理 API 分组

管理 API 由本产品自行约定：前缀 `/api/edge-admin/v1`，与平台接入协议区分；错误使用 RFC 9457 ProblemDetails，并配合正确的 HTTP 状态码；OpenAPI 文档由 .NET 内置的 Microsoft.AspNetCore.OpenApi 生成；队列、审计等大表使用键集分页；枚举按字符串序列化。

config.db 的实体主键用 64 位雪花 ID，复用 TenonAdmin 的 SnowflakeIdGenerator（拷贝源码，按第 17 节记录来源，不引用其程序集）。沿用它的位布局：41 位毫秒、6 位机器号、6 位序列，ID 恒小于 2^53，前端按数字解析不丢精度；不得加宽低位，否则须改为字符串序列化。机器号固定；唯一性依赖第 3.1 节的数据目录锁（主机侧的管理员重置命令也须持有该锁），不需要原实现的机器号文件锁和库表租约。边缘设备开机时时钟可能不可靠，因此与原实现有以下不同：启动时保证新 ID 大于 config.db 中已有的最大 ID 和 SystemState 中记录的下限（恢复备份后写入，第 10.4 节），且时间戳不早于本版本的构建时间；时钟落后时沿用逻辑时间戳，序列用尽即加 1 毫秒，不等待时钟；时钟读数达到 2^41 毫秒时视为不可信，沿用逻辑时间戳并告警；只有逻辑时间戳本身达到 2^41 毫秒时才拒绝发号。雪花 ID 只在一个配置库内唯一（机器号固定），不能假定跨网关唯一；导入导出、备份恢复都不以它作为跨网关的身份（第 10.4、10.5 节）。

点位值、预览结果和调试记录中的数值，按第 6.4 节以原文字符串附类型返回；报文正文返回原文，服务端和前端都不重新解析其中的数值。

健康检查：匿名的 `/healthz`（进程存活）和 `/readyz`（运行时已启动；尚无有效配置时也视为就绪，处于“运行失败”状态时返回 503），只返回状态，不返回配置、版本或错误细节。

| API 分组 | 能力 |
|---|---|
| connections | 新增/编辑/禁用、连接测试、凭证更新；不返回秘密明文 |
| devices / groups / points | 基础配置、导入导出、复制设备、一次读取预览 |
| routes | 草稿 CRUD、静态校验、用样本预览、发送测试报文（仅通用输出） |
| configuration | 查看变更清单、应用全部草稿（请求携带草稿版本号）、查询应用进度与结果、放弃草稿、版本历史与对比、回滚到任一保留的版本、运行失败后重新启动 |
| runtime | 状态、当前值、错误、计数、趋势、运行事件 |
| deliveries | 待发和失败统计、失败区逐条查看与导出、人工重试、立即重试、明确确认后的清理、手动暂停与恢复目标、迁移待发记录、隔离记录的查看、导出与清理 |
| platform-links | 复用连接模型，提供连接测试和设备同步操作 |
| auth / users | 首次设置、登录、登出、修改密码；用户与角色管理、重置密码、解锁、强制下线、API 令牌管理（仅管理员） |

| system | 网关名称与运行参数、HTTPS 证书、出站白名单、系统信息、配置导入导出、备份下载与恢复、诊断包导出、重置网关身份（权限见第 10.3 节） |

所有“测试”“预览”“导入”“重试”都必须做与正常操作一致的授权和目标校验。不能只保护 CRUD。每个需要单独授权的操作使用独立的方法和路由；除只读状态查询外，接口都声明所需角色。

- 秘密与普通配置分离，使用 ASP.NET Core Data Protection：固定调用 SetApplicationName("TenonEdge")，密钥环显式持久化在数据目录并保护访问权限，永不清理旧密钥。显式持久化后不会回退到临时密钥，风险来自数据目录本身不持久（例如容器没有挂载数据卷）；框架没有公开的检测接口，由网关自行检查：在容器中运行时，数据目录须位于已挂载的卷上，否则拒绝启动运行时并提示挂载数据卷。
- 数据库、密钥和备份放在受限目录；日志和预览脱敏。只做可逆编码、只靠 UI 星号遮盖不算秘密保护。Linux 上密钥环默认不加密落盘，这套机制只防“只拿到数据库文件”的泄露，不防整盘被获取；含密钥的备份按秘密级别保管。
- Data Protection 密钥丢失会影响解密；迁移时必须处理密钥，不能只复制数据库。参考：https://learn.microsoft.com/en-us/aspnet/core/security/data-protection/configuration/overview?view=aspnetcore-10.0 。
- HTTPS/TLS 证书校验默认启用。连接工业内网所需的明文协议须明确标注风险，不通过全局关闭证书校验解决问题。不提供“忽略证书错误”选项；遇到不受信任的证书时，由管理员核对指纹后信任（`docs/functional-spec.md` 第 2.6 节）。
- 固定可访问目标；目标的 scheme、主机、端口、DNS 解析结果均校验。私网地址（10/8、172.16/12、192.168/16，IPv6 fc00::/7）默认放行；公网目标须由管理员加入出站白名单（CIDR 加端口）后才能使用，配置人员不能自行放行。校验在建立连接时执行：HTTP 在 SocketsHttpHandler.ConnectCallback 中检查实际连接的 IP，默认不使用系统代理（需要代理时作为连接的显式参数）；MQTT 和 Modbus 在建立 socket 前做同样的检查。默认拒绝回环（包括本机管理端口）、链路本地、未指定和组播地址，以及它们的 IPv4 映射 IPv6 形式；管理员可以放行本机的指定端口（本机管理端口除外），附带 Mosquitto 时预置 127.0.0.1:1883。本机管理端口无论经回环还是本机网卡地址访问，一律拒绝。细节见 `docs/functional-spec.md` 第 2 节。
- 默认不跟随 HTTP 重定向（HttpClient 默认会跟随，须显式关闭；重定向时自定义请求头会被带到新主机），不将数据字段作为 URL；防止访问云元数据、宿主管理接口等非授权地址。参考：https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html 。
- 管理页不匿名暴露到公网；不硬编码公共密码，不存在默认或演示账号。
- 首次设置：SystemState 记录设置状态，取值为未初始化、已初始化、重置待设置（附账号）。设置页只在状态为“未初始化”或“重置待设置”、且处于设置窗口内时可用；提交时以比较并交换的方式原子地把状态改为“已初始化”：未初始化时创建管理员，重置待设置时只为该账号设置新密码，其他启用的管理员不受影响。设置窗口为服务启动后 30 分钟，过期关闭；状态不是“已初始化”时，重启服务或设备断电重启后重新开放；已初始化后不再因重启开放。主机侧的管理员重置命令把状态改为“重置待设置”，供售后使用。首次设置与重置后的设置都记审计（时间、来源 IP），并在首页显示。每台设备首次启动时生成独立的 NodeId 与本地密钥。
  - 残余风险（“首次访问时设置”是维护者确认的决定，见第 22 节与评审 Q19、Q24）：窗口内能访问管理端口的任何人都可能抢先完成设置，重置命令之后重新开放的窗口同样如此；经 HTTP 提交时，管理员密码以明文传输。
  - 保留这一决定时的最小保护：设置接口只在上述状态和窗口内可用，状态变更是原子操作；窗口开放期间记运行事件，并在服务日志输出一行不含秘密的提示；首页和系统信息持续显示首次设置的时间与来源 IP，安装人员核对是否为自己的地址，不是则立即按重置流程处理并检查审计；部署文档要求在接入生产网络之前、或在点对点连接的隔离网络中完成首次设置。
  - 推荐调整（待确认，`docs/development-readiness.md` 第 4 节）：重置命令生成一次性设置码，网页设置必须输入；首次设置按部署方式可选启用同一机制。设置码解决的是“谁能初始化”，不解决链路安全：经 HTTP 提交时，设置码和密码同样可能被截获或被中间人替换。
- 管理访问（“默认 HTTP”是维护者确认的决定，见第 22 节）：
  - HTTP（默认 8080）和 HTTPS（默认 8443）同时开放，默认用 HTTP 访问；两者的端口和监听地址可以分别配置，部署参数可以关闭 HTTP 监听。HTTPS 首次启动使用自签证书，可上传正式证书替换。首版不发送 HSTS，因为它对整台主机生效，会让 HTTP 端口不可用。
  - HTTP 不提供保密性和完整性：同网段的被动监听可以得到密码、会话 Cookie 和录入的凭证，主动中间人可以篡改页面和请求。页面上的明文提示只是告知，不是防护措施。
  - 请求是否属于 HTTPS 按实际连接判定：来自受信任反向代理的请求，只看代理转发头中的协议，没有转发头按 HTTP 处理，与到达哪个监听端口无关；其他请求按到达的监听端口判定。受信任代理可以在系统设置中登记，也可以用部署参数预置；在反向代理之后部署时应当预置，否则首次设置记录的来源 IP 是代理的地址。没有配置受信任代理时忽略全部转发头（包括 X-Forwarded-For，限流和锁定按实际来源地址计算）。实现上，没有登记代理时不启用转发头中间件，登记后只信任所列地址；不使用 ASPNETCORE_FORWARDEDHEADERS_ENABLED 环境变量，因为它会清空信任列表、接受任何来源的转发头。“只允许 HTTPS”、Cookie 的 Secure 标志和 API 令牌的 HTTPS 限制都按这一判定执行。
  - 会话 Cookie 按协议分开：HTTPS 使用带 `__Host-` 前缀的 Cookie（Secure、Path=/、不带 Domain），HTTP 使用另一个名称，服务端只接受与请求协议相符的那一个；防 CSRF 令牌同样分开。经 HTTP 注入的 Cookie 因此不能冒充或覆盖 HTTPS 会话。
  - 管理员可在系统设置中切换为“只允许 HTTPS”，此后 HTTP 只做跳转，健康检查仍在 HTTP 上直接响应。开启时会话代次加一，现有会话全部失效；恢复备份时同样处理（第 10.4 节）。
  - API 令牌的创建（明文只在这时显示一次）和使用都只允许经 HTTPS；经 HTTP 的相关请求一律拒绝，不做跳转。
  - 不强制 HTTPS：默认 HTTP 的前提是管理网络可信。现场以内网为主，强制 HTTPS 的代价落在每次部署和每台电脑上：自签证书的警告、IP 变化后证书与地址不符、现场没有外网申请不到正式证书；而自签证书只防被动截获，用户点过证书警告后同样挡不住冒充。备份的下载与恢复也不限协议：HTTPS 端口默认开放，截获了管理员密码的人可以直接经 HTTPS 下载备份，只限制备份的协议防不住这种情况；经 HTTP 下载或恢复备份时，对话框提示备份密码和文件在同一个明文连接中传输。开发准备阶段曾推荐新安装默认“只允许 HTTPS”、备份只允许经 HTTPS，2026-09-29 讨论后撤回（`docs/development-readiness.md` 第 4 节）。管理网络与其他网络共用、经无线网络或跨网段访问，或客户有安全测评要求时，由管理员开启“只允许 HTTPS”并上传正式证书，或让管理端口只监听管理网卡的地址；部署文档说明这些情形。
  - 浏览器对 HTTP 的处理：按官方计划，Chrome 154（2026 年 10 月）起默认在访问 HTTP 公网站点前询问；局域网 IP、单标签主机名和非唯一主机名（如 `staging.local`）不询问，用公共域名下的内网主机名访问时可能询问，用户的选择保留 15 天、再次访问时续期。企业可用 HttpAllowlist 策略免除指定主机；用 HttpsOnlyMode 策略强制严格模式时，局域网 IP 也会询问（`docs/development-readiness.md` S-21）。经 HTTP 按网卡地址访问时，页面不属于安全上下文，前端的限制见 `docs/functional-spec.md` 第 1.2 节。
  - 细节见 `docs/functional-spec.md` 第 1 节。
- 识别敏感信息旁路：校验时识别常见的敏感请求头名、查询参数名和 URL 中的 userinfo，拒绝或强制转为凭证引用。凭证类型包括 password、token、apiKey（header 或 query）、clientCertificate（PKCS#12 或 PEM 加私钥）和 trustedCa。
- 不允许运行任意脚本或上传执行程序集。扩展模块是受信任的代码依赖，不声称插件机制具有安全沙箱。参考：https://learn.microsoft.com/en-us/dotnet/core/tutorials/creating-app-with-plugin-support 。

### 10.4 备份与恢复

备份包含 config.db、Data Protection 密钥环、身份与本地秘密文件（NodeId、HTTPS 证书与私钥等），不含 queue.db。管理员可以在界面下载加密备份（自设备份密码，使用标准的带认证加密，不自行设计算法）；网关每天在数据目录中自动生成本地备份，保留 7 份。恢复可以在界面上传，也可以停止服务后用命令行执行，两者步骤相同。

版本与标识：

| 组成 | 版本或标识 | 恢复规则 |
|---|---|---|
| 备份包 | 格式版本；清单记录软件版本、配置库 schema 版本、快照 schemaVersion、NodeId、configStoreId、备份时间、各文件的 SHA-256 | 格式无法识别、校验不通过，或软件、配置库版本新于本机：拒绝（不支持降级）；较旧：恢复后按迁移器升级 |
| config.db | 配置库 schema 版本；configStoreId（配置库首次创建时生成的随机标识，随备份恢复） | 用在线备份方式导出；恢复后执行迁移、quick_check 与快照哈希校验 |
| 密钥环 | Data Protection 密钥文件 | 恢复后的密钥环是备份与本机密钥环的并集（按密钥 ID 去重），不删除任何密钥；随后逐一试解密全部凭证，任何一个失败则整次恢复回退 |
| 身份与本地秘密文件 | 文件格式版本 | 采用备份中的内容；页面提醒不要让两台设备同时使用同一身份（第 9.3 节） |
| queue.db | 队列 schema 版本；创建时所属的 configStoreId | 不在备份内；恢复既不覆盖也不删除它，其中的记录按下文处理 |

恢复后的待发记录：

- 恢复后的 configStoreId 与 queue.db 所记相同（同一台网关较早的备份）：记录照常处理。连接已不存在的隔离为“目标不存在”，指纹不符的隔离为“目标已变化”，其余在运行时启动后照常发送，不另设等待。
- 不同（备份来自另一台网关，或本机曾经重新初始化）：启动时把 queue.db 中现有的全部记录隔离为“配置库来源不同”，并把 queue.db 改记为新的 configStoreId，之后的新记录照常处理。
- 隔离记录的查看、清理、导出和迁移按第 8.3 节；迁移到 TenonIoT 目标仍须 GatewayId 相同。

步骤与中断。每次恢复有一个恢复编号；“恢复标记”文件用“写临时文件、落盘、改名”的方式原子更新，记录恢复编号和最后完成的阶段：

1. 上传后用备份密码解密，校验清单、哈希和版本；到这一步为止不改变任何东西。页面显示备份时间、软件版本、网关名称和 NodeId，管理员二次确认。
2. 按自动备份的方式先备份当前状态。
3. 把备份内容写入 `restore/<恢复编号>/staged/` 并落盘，写入恢复标记（阶段：已暂存），然后按第 8.1 节的停机顺序以非零退出码退出，由服务管理器重启。部署须让服务管理器在进程退出后自动重启（systemd 的 Restart=always，Docker 的 restart: unless-stopped），第 12 节 T5 的安装包与编排按此配置。
4. 启动时持有数据目录锁、尚未打开任何数据库，发现恢复标记就从记录的阶段继续。每个阶段先检查自己是否已经完成，完成则跳过：
   - 保存：把当前的 config.db 连同它的 -wal、-shm 附属文件（存在时），以及密钥环和身份文件，复制（不是移动）到 `restore/<恢复编号>/previous/`，落盘后写入完成标志文件；完成标志已存在则跳过。此时没有打开任何数据库连接，这组文件就是一致的恢复前状态。
   - 替换：先删除正式 config.db 的 -wal、-shm 附属文件，再把暂存的文件逐个改名放到正式位置；哈希已与清单一致的文件跳过。暂存的 config.db 来自在线备份，是不带附属文件的完整单个文件。
   - 整理：以下各项在 config.db 的一个事务中完成，事务中已记有本次恢复编号则跳过这个事务：先执行迁移，把备份的配置库升到本机的 schema 版本；再用本机恢复前的审计记录、运行事件和 API 令牌整表替换这三张表，不做合并（本机配置库无法读取时，保留备份中的审计和运行事件，API 令牌全部作废，并在恢复记录中注明）；会话代次取恢复前与备份中的较大值再加一；此后的新配置版本号大于恢复前、备份中和 queue.db 记录中出现过的所有版本号，新生成的内部 ID 大于恢复前配置库中的最大 ID，这两个下限写入 SystemState；非正常退出次数清零；审计保留期取两者中较长的一个；写入本次恢复编号和恢复审计。事务之后合并密钥环（取并集，重复执行无影响），再做完整性检查和凭证试解密；这两步每次进入本阶段都执行。
   - 队列：按上文“恢复后的待发记录”处理 queue.db，隔离与改记 configStoreId 在同一个事务中完成并记下本次恢复编号，已记下则跳过。
5. 全部完成后删除恢复标记，再删除上一次恢复留下的目录；本次的 `previous/` 保留到下一次恢复成功，用于撤回。任何阶段失败：先把恢复标记的阶段改为“回退中”，再用 `previous/` 中的文件覆盖正式文件，并删除 `previous/` 中没有的附属文件（保存阶段未完成时正式文件还没有改动，不覆盖）；完成后删除恢复标记，按原状态启动，记审计和运行事件“恢复失败”，并在页面显示原因。
6. 恢复中途断电或进程退出：下次启动时恢复标记仍在；阶段为“回退中”就把回退做完，否则从记录的阶段继续，不会停在一半。

恢复后所有会话失效；备份中的用户和密码一并恢复，页面提示管理员检查用户列表。恢复不覆盖本机现有的审计记录、运行事件和 API 令牌，已吊销的令牌不会重新生效（`docs/functional-spec.md` 第 10.4 节）。

### 10.5 配置导入导出与标识

导出文件是 JSON，带自己的格式版本号，内容包括连接（不含凭证和受信任证书）、设备、数据来源、点位和路线（`docs/functional-spec.md` 第 10.2 节）。平台设备映射、NodeId 与 GatewayId、用户、API 令牌、系统设置、审计和版本历史不导出。

内部 ID 不作为身份：雪花 ID 只在一个配置库内唯一，不同网关可能生成相同的 ID，同一对象在两台网关上的 ID 也不同。导出文件中的对象和引用一律使用业务标识：

| 对象 | 标识 | 唯一范围 | 说明 |
|---|---|---|---|
| 连接 | connectionKey | 全网关 | 创建后不可修改，字符规则同第 6.5 节；名称只用于显示 |
| 设备 | deviceKey | 全网关 | 已有规则 |
| 数据来源 | inputKey | 设备内 | 创建后不可修改 |
| 点位、字段 | key | 设备内 | 已有规则 |
| 路线 | routeKey | 全网关 | 创建后不可修改；路线文档整体导入 |
| 路线内的节点 | 节点 id | 路线内 | 由前端生成，随路线文档整体导入 |

导出时，路线文档中对数据来源和连接的引用改写为 `deviceKey/inputKey` 与 connectionKey；导入时再解析为本机的内部 ID。

导入只写入草稿，分两步：

1. 预检：校验格式版本、schema、文件大小、文件内的重复标识（逐项报告 JSON 位置）、引用能否解析（文件中的对象；合并模式下再加上草稿中已有的对象），以及敏感信息旁路（第 10.3 节）。按用户看到的草稿版本号生成变更预览，逐项标出新增、更新、删除和需要重新填写凭证的连接。
2. 确认后在一个事务中写入草稿；草稿版本已经变化则返回冲突，要求重新预检。任何错误都不写入，原草稿保持完整。

- 合并（默认）：按标识匹配，已有的对象更新，没有的新建并分配本机新的内部 ID；不删除草稿中已有的对象；路线按 routeKey 整体替换。
- 替换：草稿变得与文件完全一致。按标识匹配上的对象保留原内部 ID，待发记录和平台映射因此仍然对应；文件中没有的对象从草稿中删除，删除在应用时照常做引用与待发数据检查（第 8.3 节）。
- 凭证：文件中从不包含凭证。匹配上的连接，只有接收方参数（scheme、主机、端口、基础路径、账户标识）都没有变化时才保留原凭证，否则标为“需重新填写凭证”，防止借导入把已保存的秘密指向新的地址。新建的连接若在导出方设有凭证，同样标为需要填写。补全之前不能应用。受信任证书不导入，由管理员重新信任。
- 显示名称可以重复，标识不能重复。从另一台网关合并时，deviceKey 相同即视为同一台设备，预览中以“更新”标出，由用户确认。

## 11. 二次开发要求

只设置三个主要扩展点：输入适配器、纯转换处理器、输出适配器。发送缓存属于 Runtime 核心，直接以真实 SQLite 测试，不作为扩展点，也不开展多存储引擎项目。

- 输入适配器：以“工厂 + 实例”实现。工厂校验配置（纯函数）并创建实例；实例启动时不做阻塞式网络 I/O，连接失败异步上报；停止有超时，等待循环退出后再释放。连接向运行时的连接管理借用，不自行持有。可选提供一次读取能力，供预览使用。
- 转换处理器：输入消息与配置，返回处理结果；默认不访问网络和数据库。
- 输出适配器：校验并生成目标报文（纯函数，结果入库）；发送已持久化的报文，返回四类结果之一：Ack、Retry、RejectMessage、SuspendTarget（第 8.2 节）。

参数面板先用少量类型化表单和复用组件实现，不先造通用表单设计器或动态 UI 平台。适配器工厂要声明参数描述，包括字段名、类型、是否必填、默认值、取值范围和说明；类型只有文本、数字、开关、下拉、凭证（只用于新连接类型的连接表单）、连接引用六种。界面据此自动生成表单，后端按同一描述校验，第三方适配器因此不用修改前端；内置适配器可以改用手写表单（`docs/functional-spec.md` 第 12 节）。添加一种驱动/输出只改注册和新增实现，不修改路由核心的大量类型判断。

必须给出至少一个模拟输入、一个已有输出的扩展说明和测试。不要把“可以 fork 源码随便改”当成二次开发文档。

## 12. Agent 实施步骤

每步提交内容应可构建、可测试；不要先创建大量空目录、空接口、静态页面再声称完成模块。

### T0：核实环境与依赖

- 阅读目标仓库指令、`docs/reviews/2026-09-28-architecture-review.md`（其正文针对 1.5，与本文不一致时以本文为准）和实际第三方接口实现（MQTTnet、NModbus、SqlSugar、Microsoft.Data.Sqlite、ASP.NET Core Data Protection）。
- 确认是新仓库还是已有 TenonEdge 工作区，保留未提交改动。
- 选择并锁定 MQTTnet（≥ 5.2.0）、Modbus 库（NModbus 与 FluentModbus 用同一组测试比较后确定，并核实是否支持 RTU over TCP）、SqlSugarCoreNoDrive、Microsoft.Data.Sqlite 的兼容版本，记录来源和许可。核实 SqlSugar 在打开连接时执行 PRAGMA 的挂载点；做不到时配置库使用长连接。
- 按 `docs/development-readiness.md` 第 5 节执行依赖验证清单，记录实际版本、来源、步骤和结果；未执行的项标“未验证”。T0 就是完成这些验证的阶段，验证尚未完成不妨碍开始 T0；不为使用“最新版”而升级已选定的依赖。
- 实现宿主骨架：本地账号与三种角色、首次设置窗口、Cookie 会话（按协议分开命名、受信任代理与请求协议判定、会话代次，第 10.3 节）、审计表、Data Protection 与首次启动预置（NodeId、configStoreId、本地密钥、自签证书）、config.db 的 schema 版本与迁移机制（WAL + synchronous=FULL）、雪花 ID 生成器与数据目录独占锁、健康检查端点；在 Abstractions 中定义 RuntimePlan 契约，运行单元带确定性 ID 与配置哈希，并区分“只构建”和“启动”两个阶段（第 7.4 节）。
- 从 T0 起，每个管理 API 在创建时即按第 10.3 节声明所需角色，T5 只做核查与补漏。
- 建立 `docs/implementation-status.md`：需求 ID、实现状态、测试证据、未完成项。
- 按第 15—17 节记录版本边界与真实依赖来源；已有许可保持不变，未确认的许可决定标为待确认。不搭建企业授权系统，也不创建空企业宿主。

完成条件：首次设置与登录在 API 层面可用（前端可后续接入），OpenAPI 文档能生成，测试框架可运行，不要求平台已存在；验证清单中属于 T0 的项都有结论（通过、未通过或阻塞原因），未通过项的影响已记入 `docs/development-readiness.md`。

### T1：打通第一条真实转发路径

- 实现统一消息、模拟输入和 MQTT 输出；运行时从种子文件加载 RuntimePlan。
- 使用真实测试 Broker 和独立订阅者验证消息，不用 UI 假数据冒充输出。
- 加入 queue.db 发送缓存（单写者、分组提交、四类结果、目标暂停、失败区、隔离记录、存储保护）、运行时监督者与停机顺序、超时、重启恢复和输入/输出计数；凭证存储随 T1 落地。
- 运行时骨架按第 7.4 节实现“只构建不启动”与“启动”两个阶段、单实例规则、启动保护（运行中标记、非正常退出计数、自动回滚一次）与“运行失败”状态；丢弃分类与计数持久化按第 8.5 节；在途字节预算、输入通道等运行时上限按第 8.7 节。

完成条件：关闭浏览器仍持续转发；断开 Broker 后缓存增长但有上限，恢复后可继续发送；强制终止进程后，已提交的记录不丢失；各类丢弃在重启后仍能查到计数；启动后立即令进程退出的测试适配器不会造成崩溃循环。

### T2：补齐接入和报文处理

- 实现 Modbus TCP（含 RTU over TCP）、MQTT 输入、HTTP GET 输入、HTTP POST 输出。
- 实现连接管理（引用计数共享）、MQTT 持久会话与入库后确认（含会话丢失事件、订阅协调和保留消息规则，第 6.2 节）、Modbus 调度（overrun、快速失败、RTU over TCP 的静默间隔）、出站白名单与建立连接时的校验。
- 实现字段提取、重命名、类型及比例换算，按第 6.4 节的输出类型、原因码和时间规则处理，不实现脚本和 SQL。
- 用已知寄存器值、JSON 样本、记录请求的 HTTP 接收端验证结果；Modbus 的测试证据按第 6.1 节。
- 增加第 21 节的单设备 LoRaWAN 应用 JSON 映射样例，仍使用通用 MQTT 输入，不新增 LoRa 运行时。无实物时用明确标记的样本经真实测试 Broker 验证接收、映射和输出；这只证明软件链路，不证明无线或厂商兼容。

完成条件：协议、地址、类型、时间戳和失败场景有测试，设备错误不会使进程退出。

### T3：完成产品自身的配置和画布

- 完成连接、设备、点位、输入配置、CSV 点表导入导出和复制设备。
- 实现自有图格式、节点配置、连线校验（允许扇入、按路径展开）、预览、保存与应用。

## 13. 验收场景

| ID | 场景 | 通过标准 |
|---|---|---|
| AT-01 | 无平台独立启动 | 不安装 TenonIoT/Node-RED，也能完成首次设置、登录、配置并使用通用输出；数据库中不存在默认或演示账号 |
| AT-02 | Modbus 已知数据 | 所选功能码、地址、整型/浮点、寄存器取位和字节序与模拟设备/实物值一致；Modbus TCP 与 RTU over TCP 两种帧格式都要测；同一串口服务器上一个从站超时时，其他从站不被判为失败，每个周期因它多出的等待不超过“读取超时 + 静默间隔”，它被判离线后按退避降低读取频率（第 6.1 节）；RTU over TCP 的迟到应答、Modbus TCP 较旧事务号的应答，都不会被当作下一个请求的结果 |
| AT-03 | MQTT 接收转发 | 外部发布、接收、映射、另一订阅者收到正确内容 |
| AT-04 | HTTP 拉取与 POST 输出 | 查询/请求头正确；外部接收端记录完整请求；超时不叠加请求 |
| AT-05 | 可视化真实运行 | 新建路线、保存应用后真实发送；关闭浏览器不停止 |
| AT-06 | 多输出 | 同一输入只建立一个采集实例；一个目标离线不拖停另一个 |
| AT-07 | 格式异常 | 必填缺失、非法 JSON、溢出、超限均可见失败，不发送伪造 0 或旧值 |
| AT-08 | 输入掉线 | 自动重连；轮询类输入显示最后成功时间和过期状态，推送类输入显示连接状态和最后接收时间；不上报旧值为新值 |
| AT-09 | 输出断网与恢复 | 已持久化记录按策略补传；旧时间不变；缓存有上限 |
| AT-10 | 进程重启 | 有效配置与 NodeId 保留，待发记录恢复；应用配置中途崩溃后按第 7.4 节中断点表加载（提交前中断加载原版本，提交后中断加载新版本）；已读入内存但未入库的风险按第 8.5 节如实说明；同一数据目录上启动第二个实例被拒绝 |
| AT-11 | 确认丢失 | TestPlatform 已保存但响应丢失时，重发同一编号返回 duplicate，不多存一份 |
| AT-12 | 缓存满/磁盘不足 | 显示故障和拒绝/过期计数，内存不无限增长；不静默清空；磁盘接近写满时仍能登录管理界面查看故障；queue.db 损坏时移到一旁并新建，记运行事件，配置不受影响 |
| AT-13 | 错误配置应用 | 环、缺引用、未知节点、错误字段不能替换有效配置；准备阶段失败时原配置不中断；停止失败不重复启动；新版本反复非正常退出时，上一生效版本曾稳定则自动回滚到它一次，否则或仍失败则进入“运行失败”，不形成崩溃循环；正常重启和已稳定版本上的退出不计入 |
| AT-14 | 目标变更 | 存在待发记录时切换接收方被阻止；目标指纹不符的记录不发送而被隔离；清理与迁移都有确认和审计；迁移按第 8.3 节执行：TenonIoT 的 GatewayId 不同则拒绝，配额不足整体拒绝，在途记录不重复发送，迁移中途终止进程后要么全部生效、要么全部不生效；通用目标更换凭证时须声明账户，选择“更换了接收账户”后旧记录被隔离 |
| AT-15 | 平台设备同步 | 重复同步不重复创建设备；改名不变身份；映射到正确设备 |
| AT-16 | 平台授权与时间 | 未绑定设备、其他网关身份、失效凭证被拒；补传不伪装当前在线 |
| AT-17 | 配置导入导出 | 不带秘密；导入仅成草稿；未知版本和不存在的凭证引用阻止应用；从另一台网关导入时按业务标识匹配并重新分配内部 ID；文件内标识重复或引用无法解析时整体拒绝，原草稿不变；接收方参数变化的连接须重新填写凭证（第 10.5 节） |
| AT-18 | 权限与出站访问 | 只读不能测试外发/应用/清理；配置人员不能清空队列、迁移待发记录、恢复被暂停的目标，也不能修改白名单、系统设置与用户；非授权目标与跳转被拒，DNS 解析变化与代理设置不能绕过校验；授权现场设备可连接 |
| AT-19 | 备份恢复 | 使用文档中的备份流程恢复配置、身份和可解密凭证；重启、更换安装路径、重建容器后凭证仍可解密；不复制活跃文件碰运气；恢复同一网关较早的备份后，指纹相符的待发记录照常发送、不符的被隔离；恢复另一台网关的备份后，原有待发记录全部隔离；恢复中途断电，下次启动完成恢复或回退到恢复前的状态；凭证无法解密时整次恢复回退（第 10.4 节） |
| AT-20 | 扩展与发布 | 按文档增加示例适配器并通过测试；从干净环境构建运行，不依赖开发机秘密 |
| AT-21 | 开源版独立性 | 仅用公开仓库和已声明的公开依赖即可构建；G0/L0 不需要企业包、激活码或厂商授权服务器，用户自己选择的外部输出服务不在此限制内 |
| AT-22 | 版本与许可记录 | 构建产物可追溯到核心版本与依赖版本；实际分发组件与许可清单一致；未包含企业秘密、客户配置或无分发授权的 SDK |
| AT-23 | 企业模块边界（条件执行） | 仅在企业模块实际交付时执行：开源核心不引用它；模块通过既有契约接入，核心回归仍通过；未实现时记“不适用”，不是“通过” |
| AT-24 | 首次设置窗口 | 未初始化的设备在服务启动 30 分钟后关闭设置页，重启后重新开放；初始化后入口关闭，重启也不再开放；初始化记审计，首页显示首次设置的时间和来源 IP |
| AT-25 | MQTT 会话与确认 | 上游以 QoS 1 发布、且在第 8.5 节列出的 Broker 前提之内时，应用配置和重启期间发布的消息在恢复后全部补收；通道满时 QoS 1 不确认，在上述前提内由 Broker 重投，QoS 0 丢弃并计数；不产生投递记录的消息计数后确认，不阻塞后续消息；存储写入失败时不确认并断开，重连后收到重投；会话丢失（SessionPresent=0）时记运行事件；重新订阅补发的保留消息不当作新采样 |
| AT-26 | 目标故障分类 | 凭证失效时目标暂停、记录保持待发，修复后恢复发送；404 等未列出的 4xx 暂停目标；单条报文被拒只进入失败区（失败区满时只计数），不影响其他记录与其他目标；同一目标连续 20 条被拒时暂停目标；毒消息达到阈值、其后记录探测成功且队头再次计入失败后移入失败区；连续多条毒消息逐条识别；队列只剩毒消息时仍继续探测；断网、429/503 退避和 5xx 故障恢复后不误判 |
| AT-27 | 设备直连 | 只支持 MQTT 的设备发布到附带的 Broker，经网关转发成功；网关重启期间设备以 QoS 1 发布的消息，在不超过 Broker 积存上限时于网关恢复后全部补收；超过积存上限、Broker 被强制终止两种情况下实际丢失的范围被测出并写入部署文档；Broker 拒绝匿名登录和错误账号 |
| AT-28 | 应用的激活边界 | 准备阶段失败时原配置不中断；提交有效版本之前，没有按新版本生成的投递（以记录上的配置版本号核对）；应用期间修改的草稿不进入本次应用；按第 7.4 节中断点表逐点终止进程，重启后加载的版本和历史中的“未生效”标记与表中一致；回滚不撤回已发数据，且受第 8.3 节约束 |
| AT-29 | 资源保护上限 | 先扇出再扇入使路径数超限的配置在校验阶段被拒绝，校验耗时不随路径数成倍增长；单条源消息的投递不超过路径上限；持续输入大报文时，调试缓存和在途字节不超过预算，界面显示截断标记；预览任务超过并发上限时立即返回提示（第 7.2、8.7 节） |
| AT-30 | 数值、时间与保留消息 | 超过 2^53 的 int64、uint64 从读取、映射、管理 API、预览到 MQTT/HTTP/TenonIoT 输出逐位一致；同一字段在不同数值下 JSON 形式不变；溢出、NaN、无穷按第 6.4 节标为 bad；保留消息默认不生成投递；未映射上游时间时 timeSource 为 gateway；上游时间无效时退回接收时间并计数 |
| AT-31 | 平台字段待同步 | 已绑定设备新增字段并应用后，只有该设备停止向该平台发送且计数可见，同一连接上的其他设备照常发送、连接不暂停；手动同步成功后恢复，等待期间的数据不补发；device_not_bound、schema_mismatch 不计入连续被拒计数；401 仍暂停整个目标（第 9.4 节） |
| AT-32 | 管理访问 | 没有配置受信任代理时，伪造的 X-Forwarded-Proto 和 X-Forwarded-For 不生效；经 HTTP 创建或使用 API 令牌被拒绝；HTTP 与 HTTPS 的会话 Cookie 不能互换使用；开启“只允许 HTTPS”或恢复备份后全部会话失效（第 10.3 节） |

自动化测试和真实设备测试分别记录。模拟器可以验证协议逻辑，但不能替代全部厂商设备兼容性测试。

LoRa 场景的 LR-AT 条件验收见第 21.6 节，不冒充已通过的 G0 协议能力。单设备结构化 MQTT 样本验证可复用 AT-03/07/15；无无线实物时，相应无线链路验证明确标为未验证。

## 15. 开源版、企业版与交付边界

### 15.1 两种软件版本，三种交付方式

| 交付方式 | 交付内容 | 当前安排 |
|---|---|---|
| 开源版自行部署 | 开源源码、公开依赖、通用安装包、G0/L0 功能、扩展与运行文档 | 当前开发主线 |
| 企业版软件部署 | 同一开源核心，加上有明确需求的商业模块及约定支持 | 有实际模块后交付；不维护第二套核心 |
| 工控主机整机交付 | 采购的标准主机、预装软件、已验证配置、出厂检查、交付与质保说明 | 软件可用后先在一种主机上验证，不立即自研硬件 |

整机可以预装开源版或企业版。预装开源版也可就硬件、配置和服务收费，但须履行所分发组件的许可要求，见第 17 节。不得因为用户购买整机，就在说明书中把开源部分原有的使用权改写成只能个人使用。

### 15.3 首期只记录，不自动开发

## 16. 企业扩展的代码、发布和授权规则

### 16.1 一套核心，不维护两个长期分支

当前只需要公共 `TenonEdge` 仓库。以后确有商业模块时，可建立私有的企业扩展仓库：

```text
公开 TenonEdge
  Abstractions / Runtime / Adapters / Host / Web
  普通用户仅使用这些内容即可构建和运行

以后按需求增加的私有企业扩展
  专用 Input/Output Adapter
  必要的模块参数组件
  企业发行版装配清单、已授权 SDK 和交付工具
      -> 引用固定版本的公开核心与扩展契约
```

约束：

- 开源核心不引用企业命名空间、私有包源或商业授权服务。公开 CI 不依赖企业仓库凭据。
- 企业扩展复用现有输入、转换、输出三类扩展点，不增加第二套用户、设备、画布、缓存和平台接口。
- 企业发行包仍是一个 .NET 服务和自带 Web 界面；装配发生在构建与依赖注入阶段，不建设在线 DLL 安装。
- 企业发行版可增加一个很薄的装配入口，但不复制 Host 实现；出现通用能力缺口时，经确认回到开源核心修复。
- 前端默认沿用原有参数面板。确实需要自定义组件时明确注册，不把私有代码打入公开包后只用菜单隐藏。
- 不在采集循环、发送路径和每个页面遍布 `if enterprise`。商业模块的可用性在装配/模块边界处理。
- 公开构建中缺少企业模块时应能正常运行。导入引用缺失节点的配置时报告缺失模块并拒绝应用，不静默删节点。
- 企业模块卸载或切换回开源包，遵守第 7.4、8.3 节停止、引用与待发数据检查；保留可导出的配置，不自动删除客户数据。启动时遇到缺失的模块，按第 7.4 节启动时按单元降级的规则处理：缺少模块的单元停止并告警，其余照常运行。
- 此依赖隔离是工程边界，不是第三方许可合规结论。

### 16.2 发布记录与兼容性

两种发行版使用同一核心版本号，企业模块另记录自身版本及兼容的核心版本。每个实际发布包至少记录：核心版本、扩展模块及版本、构建来源、目标 OS/架构、配置 schema 版本、依赖锁文件和包校验值。

首期用构建生成的 JSON 或文本清单即可，不新增版本管理平台。公开发行清单不泄露私有仓库地址、客户名、激活密钥或下载凭据。

企业模块集成测试必须复用开源核心的相关验收，不接受“企业版自己能启动”作为兼容证据。尚未存在企业模块时，仅验证公开构建不依赖它，不创建无用占位接口。

### 16.3 商业授权：先确定规则，暂不实现服务

以下是未来企业模块的产品约束，不是已签合同，也不授权 Agent 开发授权平台：

- 开源功能不需要商业授权。社区用户二次开发仍按开源许可证行使权利。
- 专有模块确需许可控制时，优先按网关实例/整机授权并支持离线验证，不强制工业现场持续连接厂商服务器。

## 18. 工控主机整机交付规范

### 18.1 产品形态和起步范围

首期采购已有工控主机，预装标准 TenonEdge，先验证一种确定的硬件与系统组合。不把自研主板、广泛硬件适配、自动 OTA 或远程维护平台作为当前任务。

这里的“一个服务”指 TenonEdge 应用本身；MQTT 输出仍需要用户选择的 Broker，可位于客户网络，不为了整机化额外内置 Broker。保持第 3 节的单服务、SQLite、自带页面架构。

首期以第 12 节实际验证的环境为准。原生部署与容器部署都是可选的交付形式，不要求同时维护多套安装器。宿主采用系统已有的服务自启动/重启机制，不另写一个守护平台。支持 Windows 服务、ARM64、串口设备或其他特定硬件前先补实测。

### 18.2 每个整机型号应有一张配置卡

| 字段 | 要记录的内容 |
|---|---|
| 型号与批次 | 整机 SKU、主机/主板/存储型号、硬件修订版本 |
| 系统与软件 | OS 版本、架构、核心版本、企业模块清单、镜像/安装包校验值 |
| 接口 | 物理网口、串口、外置转换器等实际配置；无实物不填已支持 |
| 支持设备 | 协议、被测设备型号/固件、支持的只读操作与数据类型 |
| 容量依据 | 测试设备/点位数、采样周期、消息大小、输出目标数、网络条件 |
| 交付内容 | 主机、电源、附件、文档、软件清单、初始化方式 |
| 售后说明 | 质保范围、支持时间、远程与现场服务、返修/换件及授权迁移规则 |

不填未经验证的“工业级认证”“全年无故障”“支持所有 PLC”等承诺。产品支持范围由硬件资料与本软件测试共同界定，不能只复制供应商宣传。

### 18.3 镜像、身份与凭证

- 通用镜像不包含客户数据、NodeId、平台 Token、生产管理员密码、商业签发私钥和测试环境密钥。构建期不生成可被整批复制的运行身份。
- 首次启动时为新设备生成独立 NodeId 与所需本地密钥；管理员凭证按第 10.3 节的首次设置流程设置；不使用所有设备相同的公共密码。出厂检查开机时不完成首次设置，设置窗口过期后自动关闭，到客户现场重新上电后再开放。
- 同一整机维护重装，应按受控恢复流程保留身份与业务配置；新整机部署则生成新身份，区分“复制部署”与“恢复原设备”。
- 迁移到替换主机时，明确旧机退役、凭证轮换和平台重新绑定，不能让两台设备同时使用同一身份。
- 备份包含受保护配置与必要密钥时，应限制访问和传输；不把含客户秘密的备份放入公开下载目录。
- 恢复出厂设置必须明确提示将清理哪些配置、缓存、凭证和绑定，需授权与确认；实施前完成受控备份，不加入隐蔽清理或远程擦除功能。
- 技术支持只在客户知情授权下进行。首版不预装远程 Shell、自动穿透或默认常开的厂商管理后门。
- 需要设备直连时预装独立 Broker 服务：禁止匿名，不预置公共账号，每台设备单独账号，开启持久化；Broker 的版本与许可写入整机配置卡。

### 18.4 验证清单：与软件验收分开记录

下面的 HW 项只在有对应硬件和测试权限后执行。模板不是测试证据，未执行必须标记“未验证”。生产设备上的停电、断网等试验须先确认不会影响生产；优先使用试验台与测试接收端。

| ID | 检查 | 通过条件与记录 |
|---|---|---|
| HW-01 | 首次初始化与重复部署 | 两台新实例身份与凭证不同；无平台也可完成初始化和转发 |
| HW-02 | 电源启动与服务恢复 | 开机后服务按预期运行；进程异常退出后按系统策略恢复，无重复采集实例 |
| HW-03 | 真实接口和设备读取 | 网口/适配器连接正常；采集值与设备已知值一致，记录型号和固件 |
| HW-04 | 上游断网与恢复 | 已持久化待发数据按规则恢复；缓存限制生效，断网不阻止本地配置查看 |
| HW-05 | 受控异常退出与存储恢复 | 在测试台验证异常终止后配置/缓存行为；记录未入库数据风险，不声称硬盘损坏也绝不丢数据 |
| HW-06 | 连续运行 | 首次建议至少一次 24 小时基准运行，记录实际负载、CPU、内存、存储增长、错误和计数；这不是可用性、寿命或环境适应性认证 |
| HW-07 | 空间不足和诊断 | 存储接近限制时产生可见错误/拒绝计数；journald 或容器日志驱动设置了大小上限，日志不无限增长 |
| HW-08 | 备份、恢复与升级 | 按交付文档验证恢复，凭证可解密、配置身份正确；升级失败有可执行的恢复路径 |
| HW-09 | 镜像和许可材料 | 镜像不含公共生产秘密，组件清单与实际一致；具备应附许可和交付材料 |
| HW-10 | 售后交接 | 客户拿到配置说明、支持范围、故障资料导出方式、质保与返修联系方式 |

`HW-06` 的时长只是验证起点，面向具体合同的验收时长与负载需另定，不能用短期测试外推多年运行保证。尚无硬件时，Agent 只准备 `docs/appliance-checklist.md`，不阻塞开源核心的软件开发，不将 HW 项标为通过。

## 21. LoRa／LoRaWAN 应用层数据接入

- 记录编号：INT-LORA-01；关联需求：GW-05/06/08/17—19、GW-21。
- 状态：接入方向已确认，具体网关、传感器、报文与兼容性尚未验证。
- 本期工作：复用 G0 输入、字段映射与输出，提供接入说明、单设备样例和软件测试；不增加无线运行环境。
- 扩展工作：需要新增接口、专用适配、多设备分流或按周期自动判断新鲜度时，先明确设备与验收，再按 G1 实施，不自动扩大 T0—T5。
- 版本归属：通用接入与公开配置样例归开源版。专有 SDK 或实际商业适配按第 15—17 节判断，不将 LoRa 整体划为企业专享。

### 21.1 范围与名词

LoRa 是无线调制技术，LoRaWAN 是建立在其之上的通信协议。仅有“LoRa”标识，不能证明设备采用 LoRaWAN 或与某个网关互通。[LR01]

无线网关负责接收和转发无线消息；LoRaWAN 网络及应用服务负责后续网络与应用处理。TenonEdge 的角色是接入已处理的数据，而不是替代这些无线组件。普通工控主机安装本软件不会获得无线收发能力。[LR02]

本方案只接入上游提供的结构化业务数据：不实现射频驱动、不接收原始 Packet Forwarder 消息、不管理 LoRaWAN 入网和根密钥，不增加阀门控制、无线下行或固件升级。

### 21.2 三类现场接入方式

| 上游情况 | 数据链路 | 本方案的处理 |
|---|---|---|
| 网关内置网络服务，且已输出结构化业务数据 | 传感器 -> 无线网关 -> MQTT/HTTP/Modbus 等 -> TenonEdge | 按实际接口复用已实现适配器；先检查通信方向、鉴权与字段，不按产品名称判断兼容 |
| 网关只转发 LoRaWAN 无线报文 | 传感器 -> 无线网关 -> 已部署的 ChirpStack 等网络/应用服务 -> 应用 MQTT -> TenonEdge | 消费应用上行事件，不直接订阅无线网关原始报文作为业务数据 |
| 厂商私有 LoRa、透传或专有报文 | 传感器 -> 厂商接收设备 -> 厂商接口 -> TenonEdge | 按接口协议处理；只有串口或私有二进制时需单独适配，不能称为 LoRaWAN 通用接入 |

ChirpStack Gateway Bridge 转换的是网关包转发协议，并不等于已完成传感器业务字段解码。[LR03] ChirpStack 在本产品中只是可选上游，不是默认依赖；客户另行部署它时也不改变 TenonEdge 单 .NET 服务的交付方式。

Milesight UG65 官方资料列有内置网络服务器、载荷编解码和 MQTT/HTTP/Modbus TCP 等集成能力，可作为第一类设备的接口案例。[LR08] 这不是本产品的采购选型、兼容承诺或整机认证；具体型号、固件、区域配置与实测结果仍需记录。

### 21.3 最小配置：一台传感器对应一个显式输入

优先链路：

```text
已解析的传感器上行数据
       -> input.mqtt
       -> transform.map（需要字段重命名或换算时）
       -> output.tenon / output.mqtt / output.http
```

不新增通用 `input.lora` 节点，也不建设第二套设备管理、凭证或输出服务。初期模板使用普通输入配置和映射规则即可，不实现模板商城。

以 ChirpStack 的默认应用 MQTT 主题为参考，可为已登记设备订阅：[LR04]

```text
application/{applicationId}/device/{devEui}/event/up
```

这里替换为实际 Application ID 与设备 DevEUI，不将 `applicationId` 当成 JoinEUI；MQTT 主题区分大小写，按服务端实际主题配置，不因本地规范化标识而修改主题。[LR04]

实施规则：

1. 保持第 6.2 节的固定 `inputId -> deviceKey`：每台传感器建立一个显式输入，使用精确设备主题；多个输入可引用同一个 Broker 连接配置，运行时共享同一个客户端（第 8.1 节）。
2. 不把 `application/+/device/+/event/up` 收到的全部数据都记到一台逻辑设备。未知设备不能因为出现于报文中而自动建档。
3. 若上游只向一个共用主题发送多设备消息，或一次报文包含多设备数组，记录为需要 G1 的设备筛选/分流适配。未完成前，不用错误的固定绑定冒充兼容。
4. 设备预先由用户建立，外部来源身份与本地 deviceKey 明确关联。LoRaWAN 优先使用来源系统/应用范围与 DevEUI；私有 LoRa 使用厂商定义的稳定节点编号。
5. DevEUI 不是无线接收网关的标识。不要把接收网关 ID 当作传感器 ID；同一传感器被不同无线网关接收时不应变成多个设备。[LR02][LR05]
6. 厂商仅提供 HTTP 推送时，先确认 GW-20 的受鉴权接收接口是否实际存在；HTTP 拉取和 HTTP 输出不能替代它。未实现则记录缺口，不向用户宣称已支持。

### 21.4 载荷、时间、状态和平台关联

**载荷。** 首版优先要求上游把业务载荷解码为 JSON。ChirpStack 可在设备配置中设置载荷编解码规则；这项处理在上游执行，不意味着 TenonEdge 需要运行 JavaScript。[LR06] 只有 Base64 或二进制 `data`、没有对应型号解析结果时，不猜测字节含义，不把解码后的字节直接当温湿度。

**字段。** 用第 6.4 节 JSON Pointer 指向实际字段。`object` 或其他数据字段不保证一定存在；名称、类型、单位由实物和上游解析器决定。电池值可能代表电压、百分比或状态，未核实不互相换算。RSSI、SNR 等可用信息按上游文档解释，不作为连接是否成功的唯一标准。[LR05]

**身份。** 本地 deviceKey 稳定不随显示名称变化，仍按第 9.3 节与 TenonIoT 关联。网关自己的 NodeId/GatewayId、无线接收网关 ID、传感器 DevEUI 是不同标识。平台不因接到多个无线接收记录而重复建立传感器。同步输出属性而非无线密码和完整载荷解码器。

**时间。** 保留网关 receivedAt。只有设备报文明确定义并提供采样时间时，才将它标为真实采集时间；上游事件时间、网络接收时间和本地接收时间要在接入文档中注明。沿用 collectedAt 时明确其时间来源，不默认将 `/time` 解读为传感器采样时刻。不要在补传时覆盖旧事件时间，也不要用旧事件刷新“当前在线”。[LR05] 以 ChirpStack 为例：它的 `time` 依次取接收记录中的 GPS 时间、偏差不超过 30 秒的网关时间、网络服务器组装事件时的当前时间，属于上游事件时间（timeSource=upstream），不是采样时间。

**QoS。** ChirpStack 的 MQTT 集成默认以 QoS 0 发布。接入时须把它配置为 QoS 1，否则 TenonEdge 断线或应用配置期间的上行会丢失（第 6.2 节）。

**状态。** Class A 终端可在两次上行之间休眠，下行接收也受上行后的窗口约束。[LR07] 因此保持三类信息分开：TenonEdge 到平台的心跳、TenonEdge 到上游的连接、传感器最后数据时间。未配置上报周期时，只显示最后接收时间或未知；不得用平台网关的 90 秒超时推断传感器离线。按周期自动标记过期属于 GW-21 的可选小扩展，不是复杂告警引擎。

**重复和质量。** 第 8—9 节保证的是本地投递编号及相应重试处理，不能因此宣称所有 LoRa 应用重复报文都已去重。上游重发、retained 消息和重复应用事件另行记录测试结果；帧计数不能单独当全局唯一键。未知/错误字段不补 0，不将旧测量伪造为新采集。ChirpStack 已在短窗口内合并多网关接收，并抑制帧计数重传；它的 deduplicationId 在同一事件重投时保持不变，可用于识别 MQTT 层的重投。以上游事件 ID 派生投递编号属于后续候选。

不为此修改首版平台 API 增加无线网络管理；确需上报额外诊断字段时，先约定字段语义并同步契约测试，不由单端私自扩展。

### 21.5 样例与界面

下面是用于本产品字段映射测试的人工样本，不是某个传感器的实测报文，也不是所有 ChirpStack 版本或设备的固定输出。实际样例以所选版本的上行结构和已配置的解码器为准。[LR05][LR06]

```json

  "deviceInfo": {
    "devEui": "0011223344556677",
    "deviceName": "soil-sensor-demo"
  },
  "object": {
    "temperature": 23.7,
    "moisture": 41.5,
    "batteryPercent": 92
  }
```

| 配置 | 示例或要求 |
|---|---|
| 输入 | 既有 MQTT 输入，精确订阅此设备的应用上行主题 |
