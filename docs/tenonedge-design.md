## 0. Agent 先读：不可偏离的约束

1. 开发的是可以独立安装、独立使用、方便二次开发的开源网关产品，不是演示页面。
2. 核心任务是：接入数据、必要的格式处理、输出数据。优先把真实输入到真实输出做通。
3. 首版为一个 .NET 服务，自带 Web 界面。本地配置和发送缓存使用 SQLite，不强制部署第二个服务。
4. 首版仅参考 Node-RED 的拖拽、连线、参数配置和调试体验，继续使用 TenonEdge 自有画布和执行逻辑。本期不嵌入、调用或安装 Node-RED，不建设其节点包或流程文件兼容层。官方嵌入方式仅按第 20 节记录为待评估选项，不授权实施，也不是永久排除。
5. 不引入 SQL 流计算、eKuiper、脚本引擎、复杂规则引擎、窗口聚合、插件市场、微服务集群或分布式调度。
6. SQLite 是内部存储，不是面向用户的 SQL 功能。不提供 SQL 编辑器、数据库查询节点或 SQL 数据分析。
7. 使用 TenonAdmin 作为管理基础；不得把 IoT 业务写回 TenonAdmin 内核，不复制一套新的用户、角色、菜单系统。
8. TenonIoT 是可选输出目标。未安装平台时，网关也必须能够完成初始化、设备配置、采集、编排和通用输出。
9. 首版平台联动只做：连接认证、设备关联、数据上报、状态上报。不做平台远程编辑网关配置，不做设备写入和远程控制。
10. 参考项目不是依赖清单。成熟协议库和画布组件可以复用；不得因为参考项目具有某功能，就自动扩大本方案范围。
11. 先阅读实际工作区的 AGENTS.md、项目结构、依赖版本和框架接入文档；没有核实的 TenonAdmin 接口不得自行假设存在。
12. 未经明确授权，不修改其他仓库、不覆盖用户未提交改动、不推送远程仓库。缺少平台源码时交付连接器、契约和测试接收端，不伪称已经完成真实平台联调。
13. 第 4 节 G0/L0 属于开源版完整能力，不因企业版规划被删减或增加商业激活要求。企业版复用同一核心，不维护第二套采集、转发、画布或权限实现。
14. 商业化首期只落实版本边界、发布记录、许可清单和整机交付规范。不自动开发授权服务器、在线激活、计费、设备商城、批量远程运维或企业插件市场。
15. 只在有明确需求、可验证的交付价值和合法分发权时增加企业扩展。不得擅自更改已有 LICENSE、将第三方代码改署为自研，或向公开仓库提交商业 SDK、客户资料和企业密钥。
16. 第 20 节是候选技术记录，不属于 G0/L0、T0—T5 或首版验收项。不得因此新增 Node.js 运行服务、Node-RED 包依赖、认证桥接、双运行引擎、空适配工程或兼容格式；未来启动评估须另获明确授权。
17. LoRa／LoRaWAN 按第 21 节接入已由上游处理的业务数据，优先复用 MQTT、HTTP 拉取或已实现的 Modbus TCP。不得自动实现无线驱动、网络服务器、入网密钥管理、原始包转发协议或下行控制；ChirpStack 不是默认依赖。通用接入的样例与测试可随 T2/T5 交付，新增能力与实物适配按 G1 和条件验收管理。

本文中的“必须”为验收约束；“默认”为可修改的初始配置，不是实测性能指标；“后续候选”不授权在首版实现。

## 1. 产品定位和边界

TenonEdge 是基于 .NET 的边缘接入与转发网关。用户在产品自己的界面中配置设备、数据来源和输出目标，用简单画布连接数据路径。

典型使用方式：

```text
Modbus TCP 设备 ───────────────→ MQTT 输出
MQTT 订阅 ──→ 字段映射 ───────→ HTTP 输出
HTTP 拉取 ──→ 字段映射/换算 ──→ TenonIoT 输出
```

同一份数据可以分发到多个输出目标，字段处理节点可以省略。网关不是 PLC、硬实时控制系统、通用 ETL 平台或长期历史数据库。

### 1.1 两个产品的职责

| 产品 | 首版职责 | 不承担的职责 |
|---|---|---|
| TenonEdge | 本地配置、接入、格式处理、转发、有限缓存、运行诊断 | 集中历史分析、远程设备控制、完整物联网业务 |
| TenonIoT | 网关登记、设备关联、数据接收、设备状态及平台侧数据展示 | 直接操作网关数据库、代替网关轮询设备 |

TenonEdge 作为独立仓库维护。TenonIoT 可以是已有或后续的独立仓库。二者通过接口协作，不互相引用宿主工程，不共享数据库。

TenonEdge 规划 Community（开源版）与 Enterprise（企业发行版）两种软件版本；预装工控主机是交付形式，不是第三套软件。企业版不是使用 TenonIoT 的前置条件。具体边界见第 15—18 节。

### 1.2 首版明确不做

- Node-RED 运行时、官方嵌入集成、外接 Node-RED、Node-RED 节点兼容层；本期不做，候选说明见第 20 节。
- SQL 查询节点、流式 SQL、复杂脚本、任意 C#/JavaScript 执行。
- 条件规则引擎、时间窗口、跨设备关联计算、复杂告警编排。
- 流程回环、子流程、动态修改正在运行的节点图。
- 网关集群、跨机任务调度、全局消息总线、Kafka 等强制基础设施。
- 内置 MQTT Broker、内置 OPC UA Server、设备写入、RPC 控制。
- 平台远程改点位、改画布、远程 Shell、网关自动升级。
- LoRa 射频收发驱动、LoRaWAN 网络服务器、入网管理、无线原始报文处理、下行控制；不因支持应用层数据接入而把 ChirpStack 等系统打入默认安装包。
- 长期遥测数据库、历史报表、大屏设计器、AI 功能。
- 商业授权服务器、强制在线激活、收费平台、远程停机、插件商城和按版本人为限制基础设备数/点位数。

本地错误状态、发送失败提示和运行统计必须保留，但不扩展成告警产品。

## 3. 技术方案

### 3.1 首版架构

```text
浏览器：TenonAdmin Vue 模板 + TenonEdge 页面 + 自有画布节点
                              |
                    TenonEdge.Host 单进程
                 管理 API / 后台运行服务 / 静态文件
                              |
          接入适配器 -> 简单映射 -> 输出报文生成 -> 发送缓存 -> 输出适配器
                              |
                       SQLite + 本地密钥文件
```

- 后端使用与 TenonAdmin 对齐的 .NET 10；前端先只做 Vue 3 + Naive UI。
- 首版 Node.js 只用于前端构建，发布后浏览器资源由 .NET 宿主提供；产品运行时不要求 Node.js。第 20 节候选记录不改变这项部署约束。
- 网关无强制外部数据库、Redis、消息服务器或中心平台依赖。用户选择 MQTT 时自行提供 Broker。
- 默认只启动一个服务；运行模块和界面在代码上隔离，不要求拆进程。
- 默认本地保存配置、有效版本、凭证引用和待发数据。实时值只做有界内存缓存，不做完整历史库。

### 3.2 代码结构

```text
TenonEdge/
  TenonEdge.sln
  src/
    TenonEdge.Abstractions/    数据契约及少量可替换接口
    TenonEdge.Runtime/         接入调度、路由校验、转换、发送任务
    TenonEdge.Adapters/        Modbus、MQTT、HTTP、TenonIoT、SQLite 实现
    TenonEdge.Host/            ASP.NET Core 宿主、TenonAdmin 接线、管理 API
  web/                        Vue 管理页面与画布
  tests/
    UnitTests/
    IntegrationTests/
    TestPlatform/             仅用于平台契约测试的接收端
  deploy/                     Dockerfile、启动与数据目录说明
  docs/
  samples/                    模拟器配置、示例路由、测试报文
```

不继续为每个目录机械拆成 Domain/Application/Infrastructure 多层。若工作区已有同等职责结构，沿用现有结构，不为匹配目录名重构。

依赖方向：

```text
Host -> Runtime / Adapters / TenonAdmin
Runtime -> Abstractions
Adapters -> Abstractions / 必要协议库 / 存储实现
Abstractions -> .NET 基础类型
```

- Abstractions 不引用 TenonAdmin 控制器、ORM 实体、MQTTnet 或 NModbus 类型。
- Runtime 不读取 HttpContext，不伪装成超级管理员执行采集。
- 驱动返回数据或错误，不操作页面、平台数据库和发送重试表。
- 只有会替换、需要隔离或需要测试替身的边界才定义接口；不要给每个实体建立空接口。
- 驱动和节点采用编译期模块加依赖注入注册。新增扩展后重新发布/重启，不提供上传任意 DLL 或热加载。
- 企业扩展仅通过第 11 节现有扩展点和显式宿主装配接入。开源核心不反向引用企业包，默认构建不需要私有仓库；第 16 节的企业目录是将来有实际模块后的组织规则，不要求现在创建空工程。

### 3.3 TenonAdmin 复用范围

复用认证、用户、角色、菜单、按钮权限、配置、日志、文件及现有前端组件；导入导出按需使用 Excel 包。

不使用审批工作流执行遥测路径，不使用通用 Cron 任务为每个点位单独建任务。采集由本产品后台服务调度。

TenonAdmin 当前文档中，未显式设置的数据范围可代表可信不受限上下文。机器身份和运行服务必须明确资源范围；不能把这一默认行为当作所有接口的授权。参考：https://github.com/Tenon-Net/TenonAdmin/blob/main/site/zh/backend/data-scope.md 。多组织也不能直接声称等同于完整 SaaS 多租户隔离。

用户正在开发的第三方集成能力只作为可能复用点。Agent 必须先检查实际实现，再决定复用连接、凭证和 HTTP 处理；不得臆造框架已有机器鉴权 API。

## 4. 功能清单与优先级

`G0`：独立网关首版必须完成。`L0`：配套平台联动必须完成的契约/网关能力。`G1`：有实际需求才进入下一批，不是首版任务。

G0 与 L0 全部归开源版。G1 不预先等同于收费功能；只有额外的专用适配、授权条件或交付维护价值经过确认，才考虑企业扩展。第 15—18 节中的商业候选与硬件检查不改变本表的功能优先级。

| ID | 优先级 | 功能 | 验收要点 |

| GW-01 | G0 | 独立初始化、登录、设置 | 不需要平台账号；重启后网关本地身份不变 |

| GW-05 | G0 | MQTT 订阅输入 | 连接外部 Broker、主题订阅、自动重连、JSON 载荷 |
| GW-06 | G0 | HTTP 拉取输入 | 定时 GET、固定地址、参数/请求头、JSON 提取、请求不重叠 |

## 5. 页面和用户操作

| 页面 | 主要内容 |
|---|---|
| 总览 | 输入数、输出数、当前运行状态、待发数据、最近错误 |
| 连接管理 | MQTT/HTTP/Modbus/平台连接；凭证写入但默认不可读回 |
| 设备与点位 | 设备、采集组、地址与类型；批量导入、一次读取预览 |
| 数据路由 | 左侧节点、中间画布、右侧参数、底部预览与错误 |
| 平台连接 | 作为连接管理的专用视图；关联设备、同步结果和状态 |
| 运行诊断 | 连接错误、发送状态、缓存统计、重试或清理操作 |
| 系统设置 | 用户权限、运行参数、有效配置、导入导出、数据目录 |

平台连接只是已有 Connection 的一种类型，不再实现第二套凭证存储和 HTTP 客户端。

标准操作：创建连接 -> 创建设备/输入 -> 配置点位 -> 选择输出 -> 连线 -> 用样本预览 -> 保存草稿 -> 应用配置 -> 查看运行状态。

预览默认不访问输出目标。真实采集预览和“发送测试报文”必须分别由用户显式触发，并使用与运行相同的权限、地址校验和超时。

## 6. 输入、字段和输出设计

### 6.1 Modbus TCP

- 设备配置包含主机、端口、UnitId、连接/读取超时。
- 采集组配置周期；点位配置唯一 key、显示名称、功能码、零基地址、数据类型、字节序、单位。
- 首版支持只读功能码 01/02/03/04，以及 bool、int16、uint16、int32、uint32、float32。其他类型按需求增加。
- 界面明确零基地址与设备手册编号的差别，不把 `40001` 等显示编号直接当成协议偏移量。
- 同一物理连接上的请求串行执行，不对不支持并发的设备无条件并行读取。
- 可使用简单连续区间批量读取，不实现复杂优化器；遵守所选协议库和设备的读取长度约束。
- 超时后的旧值只作为“最后成功值”显示，并显示时间和过期状态；不得当成新采集成功值继续发送。
- 无映射节点时，只发送本次成功读取的字段，失败字段从 values 省略并在质量/诊断中标为 bad；整组读取失败不伪造一条正常数据，改为更新设备采集状态。必填映射失败则按第 6.4 节阻止该路线本条输出。
- 用具有已知数值的测试寄存器验证字节/字序，不以连通成功作为读取正确的证据。

### 6.2 MQTT 输入

- 连接外部 Broker，首版按 MQTT 3.1.1 交付，支持 QoS 0/1 和 TLS；其他版本只在明确测试后声明支持。
- Topic Filter 支持协议允许的订阅通配；每个输入配置绑定一个逻辑 deviceKey。
- 首版不根据任意 Topic 自动创建设备，不解析二进制或脚本载荷。多设备使用多个显式输入配置。
- LoRaWAN 应用上行沿用一输入一设备：优先使用含具体 DevEUI 的精确主题，而不是把所有传感器通配订阅后写进同一个 deviceKey。共用主题中混合多设备的情况，按第 21.3 节列为需单独适配的范围。
- 对消息体设置大小限制；非法 JSON、解析失败、超限必须计数和显示错误，不能导致宿主退出。
- 若提供上游时间字段，必须显式映射和校验；保留原时间，否则使用网关接收时间并注明来源。
- 防止订阅主题与本机输出主题形成反馈：应用时检测明显重叠；不允许已知自反馈路线上线。

### 6.3 HTTP 输入

- 首版定时 GET，地址和方法来自受控连接配置；不允许数据报文修改目标 URL。
- 查询参数、非秘密请求头与凭证分开保存。支持固定 Bearer/Basic/API Key 凭证引用，不实现 OAuth 授权平台。
- 每个输入只有一个执行循环，上一次请求未完成不叠加下一次请求。
- 首版处理单个 JSON 文档；可用字段定位选择固定数组下标。不自动分页、拆分任意数组、增量游标同步。
- HTTP 拉取与接收上游 HTTP 推送不是同一能力。只有推送接口的无线网关不能直接当成已兼容；本地 Webhook 接收仍属 GW-20 的 G1，不因第 21 节自动增加。

### 6.4 统一消息与字段处理

内部消息至少包含：

| 字段 | 说明 |
|---|---|
| sourceMessageId | 一次输入采样/接收的本地稳定 ID；发往多个目标时保留 |
| inputId / deviceKey | 输入配置及逻辑设备身份，不使用名称代替身份 |
| collectedAt | 采集或上游事件时间，UTC；没有上游时间时按接入约定生成 |
| receivedAt | 网关接收到数据的时间，UTC |
| payload | 原始或处理后的 JSON 数据；数值、布尔、字符串不混转 |
| quality | 点位级质量与错误；缺值不静默转成 0 |

字段选择使用 JSON Pointer，例如 `/data/temperature`、`/values/0`。采用 RFC 6901 的定位语法，不提供查询表达式和脚本。依据：https://www.rfc-editor.org/rfc/rfc6901 。

首版映射规则只包含：目标字段名、来源位置、目标类型、是否必填、比例、偏移、可选固定值。数值转换为 `y = x * scale + offset`，不是执行用户表达式。

处理约定：

- 来源合法 JSON 已经符合输出格式时，可以直接转发，不能强制增加映射节点。
- 必填字段缺失或转换失败：该路线本条消息失败，不发送半成品；其他分支不受影响。
- 可选字段缺失：默认省略，并在预览中提示；不擅自复用旧值。
- 字段重名、无效数字、溢出、非有限浮点数必须可见地失败。
- 必须有单位/类型测试。输出 schema 反映换算后的类型与单位，而不是照抄原始寄存器类型。
- 多分支对消息使用独立的处理结果，不共享可变 JSON 对象造成相互污染。

### 6.5 通用输出

MQTT：固定 Broker 连接、Topic、QoS 0/1；Topic 只允许白名单占位符，例如 `{deviceKey}`，不执行字符串表达式。实时遥测默认不使用 retained 消息。

HTTP：固定连接与路径、POST JSON、超时、必要的静态请求头。成功规则默认是 HTTP 2xx；明确提供业务码判断时，只做固定字段等值判断，不引入规则语言。

输出报文支持“直接 JSON”与“配置式字段组装”。字段组装通过 JSON 序列化生成，不能用字符串拼接把输入内容插入 JSON。

通用 HTTP 接收方若不支持幂等，重试可能造成重复；通用 MQTT 的确认仅按协议保证，不代表下游平台已持久化。界面与文档必须明确区分“发送确认”和“业务处理成功”。MQTT QoS 与确认语义依据：[OASIS MQTT 3.1.1](https://docs.oasis-open.org/mqtt/mqtt/v3.1.1/os/mqtt-v3.1.1-os.html)。

## 7. 内置可视化编排

### 7.1 节点类型

| 节点 key | 类型 | 配置或作用 |
|---|---|---|
| `input.modbus` | 输入 | 引用设备采集组 |
| `input.mqtt` | 输入 | 引用 MQTT 输入配置 |
| `input.http` | 输入 | 引用 HTTP 输入配置 |
| `input.simulator` | 输入 | 固定可复现样本及发送周期 |
| `transform.map` | 处理 | 字段选择、重命名、类型和数值换算 |
| `output.mqtt` | 输出 | MQTT 目标与报文 |
| `output.http` | 输出 | HTTP 目标与报文 |
| `output.tenon` | 输出 | TenonIoT 连接和设备映射 |

调试作为编辑器预览面板实现，不另造必须接在线上的调试节点。

### 7.2 首版连接规则

- 只支持有向无环图；支持一对多分发，不支持多输入合并。
- 输入节点无输入端口；处理、输出节点最多一个上游；输出节点没有下游。
- 至少包含一条输入到输出的完整路径，不接受悬空节点、环、未知类型或缺少引用的配置。
- 同一 inputId 只建立一个实际接入实例，然后在内部分发给引用它的路线，不因连了两个输出就采集两次。
- 每条启用路线设置节点上限，默认 50。该值是防误配置限制，不是性能承诺。
- 首版不做条件分支节点；多条连线代表复制分发，不表示条件判断。

### 7.3 自有流程格式

执行定义和布局分开。下面是格式示例，相关连接/采集组需先创建；不是可直接运行的完整设备配置。

```json
{
  "schemaVersion": 1,
  "id": "route-meter",
  "name": "电表转发",
  "enabled": true,
  "nodes": [
    {"id": "n1", "type": "input.modbus", "version": 1, "config": {"inputId": "group-meter-1"}},
    {"id": "n2", "type": "output.tenon", "version": 1, "config": {"connectionId": "platform-main"}}
  ],
  "edges": [{"source": "n1", "target": "n2"}],
  "layout": {
    "nodes": {"n1": {"x": 80, "y": 120}, "n2": {"x": 380, "y": 120}}
  }
}
```

后端不认识 Vue Flow 的私有状态；前端负责转换。未知 schemaVersion 或节点版本应拒绝导入/应用，不能猜测后执行。

### 7.4 配置应用

首版使用“全局草稿 + 当前有效快照 + 上一有效快照”。连接、点位和路线一起形成一致快照，界面按钮为“应用全部变更”，不假装支持细粒度无中断发布。

1. 保存只更新草稿，不影响运行。
2. 校验全部引用、节点图、字段、权限和目标地址；不以外部设备暂时断线作为静态配置无效的唯一依据。
3. 同一时刻只允许一个应用操作。准备新运行计划，暂停并停止旧输入；输出缓存继续按原目标处理。
4. 成功停止后切换有效快照并启动。结构性启动失败则恢复上一快照；设备暂时离线则显示运行降级并重连。
5. 停止超时应中止应用，不能再启动第二套重复采集任务。允许提示需要维护重启。
6. 重启只加载有效快照，不加载未应用草稿。有效快照损坏时报告错误，禁止静默清空配置。

首版允许短暂采集暂停，不承诺零中断。待发记录保留已经生成的报文，不按新流程重新处理。

## 8. 运行与有限缓存

### 8.1 运行组织

用后台服务维护接入循环和输出发送循环。输入到处理的缓冲有明确容量，输出 I/O 不阻塞整个采集循环。

同一设备连接串行读取；不同设备可在明确上限内并发。所有 I/O 有超时、取消和资源释放。库不支持真正取消时设置传输超时，不依靠不断 Task.Run 避免阻塞。

输出按目标独立处理。简单计数器和最后错误即可，不建设追踪平台或自定义分布式调度器。

### 8.2 发送缓存的最小实现

SQLite 中使用一个发送表，按 outputId 分区查询即可。不要同时实现文件队列、Redis 队列和多个持久化引擎。

发送记录包含：

- deliveryId：入库时生成，作为该目标下这次投递的稳定编号。
- sourceMessageId、deviceKey、routeId、outputId。
- 已转换的报文、目标地址/主题快照、非秘密请求头、凭证引用。
- 目标身份指纹、创建时间、下次重试时间、尝试次数、状态、最后错误。

流程：生成目标报文 -> 持久化 -> 发送 -> 获得约定确认 -> 删除待发记录并更新计数。

- 承诺范围从发送记录成功提交本地存储开始。输入内存阶段、设备未被采集的变化及磁盘硬件损坏不在此保证内。
- 进程在发送后、清理前退出，恢复时可能重发。TenonIoT 依靠稳定编号识别重复；不得宣称全链路 exactly-once。
- 网络错误、超时、HTTP 408/429/5xx：有限退避重试；429 尊重合理的 Retry-After。
- 认证失败、无效配置、其他确定性 4xx：停止自动重试，显示失败，修正后允许人工重试。
- MQTT QoS 1 按 Broker 的对应确认清理；QoS 0 只能按本地发送完成判断，可靠性较弱。二者都不等于最终业务存储确认。
- 单目标缓存满时，只拒绝该目标的新记录并增加丢弃计数；不能拖垮整个进程或悄悄挤掉其他目标的数据。
- 过期记录可清理，但必须累计过期数量并提示。人工清理要权限、确认和审计。
- 同一数据库失败时不绕过持久化假装成功；显示“存储异常”，统计无法入库的数据，不无限占用内存。

### 8.3 配置变更与缓存

首版采用简单规则：存在待发送数据时，不允许把对应连接切换成其他服务器、Topic、平台网关身份或接收方。用户先发送完毕或显式清理后再改。

相同目标下轮换凭证可以允许，旧数据仍发送到原目标。删除连接、设备绑定和输出配置前检查引用及待发数据。不得把旧数据自动转发到新客户或新平台。

### 8.4 初始默认值

以下是待实测调整的默认值，不是容量承诺。

| 参数 | 初始值 |
|---|---|
| 采集/HTTP 拉取周期 | 默认 5 秒，首版最小 1 秒 |
| 单次外部请求超时 | 默认 5 秒，可按连接调整 |
| 输入报文大小 | 最大 1 MiB；JSON 深度设置上限 |
| 单条输出报文 | 最大 256 KiB；超限明确失败 |
| 单输出待发缓存 | 最多 10,000 条或 64 MiB，先达到者生效 |
| 全局发送缓存 | 最多 256 MiB，失败待处理数据也计入 |
| 待发记录保留 | 默认 24 小时；过期显式计数 |
| 重试间隔 | 退避并加少量抖动，最高 60 秒，不紧密循环 |
| 调试预览 | 有界环形缓存，默认最近 100 条，默认不落盘原始载荷 |

SQLite 文件/WAL 也需要监控空间和保留磁盘余量，不能只限制表中 payload 长度就声称限制了磁盘占用。运行文档说明备份与恢复，使用受支持的在线备份方式或受控停止写入后的完整备份，不用复制正在写入的数据库文件冒充一致备份。参考：[SQLite Backup API](https://www.sqlite.org/backup.html)。

## 9. 与 TenonIoT 的联动

### 9.1 已确定的交付边界

首版网关本地配置是唯一配置来源。平台仅接收关联信息、数据和状态，不反向改网关配置。

平台的存在不影响通用输出。TenonIoT 连接器复用 HTTP 输出的凭证、请求和缓存基础，但额外处理平台身份、设备映射和业务确认。

### 9.2 使用流程

1. 平台管理员创建网关及专用凭证。
2. 用户在 TenonEdge 新建 TenonIoT 连接，输入地址和凭证，测试连接。
3. 用户选择需要同步的设备及最终输出字段。平台按授权创建新设备，或由平台管理员关联已有设备。
4. 画布中使用 `output.tenon`，引用该平台连接。
5. 网关发送数据与心跳。平台分别显示网关在线状态、设备采集状态和数据时间。

没有平台源码时，使用 `tests/TestPlatform` 验证以下接口，不搭建完整云平台。测试端只用于研发，发布包默认不包含它。

### 9.3 身份与设备映射

- NodeId：网关首次初始化生成的本地身份，重启保持不变。复制部署不能复制身份，须有明确的重置操作。
- GatewayId：平台登记的网关身份，由凭证确定，不由任意请求体中的字段决定。
- deviceKey：网关内稳定逻辑设备标识。设备改名不改 key。
- PlatformDeviceId：平台设备 ID。
- 绑定关系：平台连接 + GatewayId + deviceKey -> PlatformDeviceId。

平台凭证首次连接可绑定一个 NodeId；另一个实例用同一身份连接应拒绝或要求管理员明确重新绑定，不静默顶替。

平台只接收被授权设备的数据。网关不能通过提交其他组织 ID、其他网关 ID 或任意 PlatformDeviceId 越权。

同步的是设备和输出属性描述，不是 Modbus 地址、密码或整个画布。比例换算或重命名后的字段，以最终输出类型、key 和单位为准。

### 9.4 最小接口契约

以下接口为 TenonEdge/TenonIoT 拟定协议，不是参考项目已有接口，也不意味着你的框架当前已经实现。

统一路径前缀：`/api/edge/v1`。所有请求使用 HTTPS，凭证放 `Authorization: Bearer <gateway-token>`，不得放 URL、Topic、导出文件或普通日志。

| 方法与路径 | 用途 | 核心请求内容 | 成功结果 |
|---|---|---|---|
| `POST /connect` | 验证并绑定网关 | nodeId、agentVersion、protocolVersion | gatewayId、serverTime |
| `POST /devices/sync` | 幂等更新所选设备清单 | catalogVersion、deviceKey、名称、字段定义 | 每项 created/bound/pending/rejected 状态及映射 |
| `POST /telemetry` | 单设备数据上报 | messageId、deviceKey、collectedAt、values、quality | accepted 或 duplicate |
| `POST /heartbeat` | 当前运行状态 | sentAt、agentVersion、设备采集状态摘要、失败/待发计数 | 平台当前接收时间 |

成功响应统一为：`{"code":"ok","data":{...}}`；失败响应包含稳定的字符串 code、message 和可选 fieldErrors，并配合正确 HTTP 状态码。若实际平台已采用统一响应封装，以生成的 OpenAPI 统一调整双方，不允许一边手改后不同步。

#### 设备同步

- `/devices/sync` 是 upsert，不是删除接口；本次未出现的设备不得自动删除。
- 不以名称相等自动合并客户设备。关联已有设备在平台受权限控制的界面完成。
- 平台可设置该网关是否允许自动创建新设备；关闭时返回 pending，不能开放任意创建权限。
- 重复同步同一 deviceKey 不重复创建。字段类型冲突返回 rejected 并说明，不能静默改变历史属性含义。
- 未绑定设备不得当作其他设备上传。返回明确错误，待关联完成后人工恢复对应发送。

#### 数据报文

`messageId` 采用本次目标投递的 deliveryId。重试不重新生成；不同目标各有自己的投递编号。

```json
{
  "schemaVersion": 1,
  "messageId": "a4b5e193-090d-4a88-8d19-5b6b7d21f053",
  "sourceMessageId": "071529ee-c6ad-4c56-b9b6-34b0e72e5120",
  "deviceKey": "meter-001",
  "collectedAt": "2026-09-28T08:30:00Z",
  "values": {"voltage": 220.5, "current": 4.2},
  "quality": {"voltage": "good", "current": "good"}
}
```

```json
{
  "code": "ok",
  "data": {
    "messageId": "a4b5e193-090d-4a88-8d19-5b6b7d21f053",
    "status": "accepted"
  }
}
```

平台处理约束：

- 以凭证获得 GatewayId，以 `(GatewayId, messageId)` 作为幂等键；保存记录与幂等结果在同一可靠提交边界内完成。
- 相同编号、相同内容重复请求返回 `duplicate`；相同编号而内容不同返回 HTTP 409，不覆盖原数据。
- `accepted` 必须意味着已持久保存或进入平台可靠存储，不是仅放入临时内存。
- 首版单设备消息整体校验、整体确认，不做批量部分成功。后续需要批量再扩展协议。
- 断网补传保留 collectedAt。旧数据可记入历史，但不能把最新值倒退到旧采样时间。
- 检查时间格式与明显未来时间；首版可拒绝超过平台时间 5 分钟的消息并明确提示校时。
- 去重记录保留时间必须大于网关允许重试/保留时间及时间容差。初始可取 7 天；超期人工重放不声明仍有去重保证。

典型错误：401 凭证无效，403 无权，409 身份/内容冲突，422 设备未绑定或字段不合法，429 超限，5xx 临时服务异常。401/403/409/422 不无限自动重试。

#### 心跳与状态

- 默认每 30 秒发送一次心跳，平台超过 90 秒未收到则显示网关离线；这是可配置初始策略。
- 在线判断使用平台接收时间，不使用补传遥测中的旧时间。
- 网关在线但部分设备读取失败时，分别显示设备错误。网关离线时，下挂设备状态显示未知或过期，不宣称设备物理损坏。
- 心跳不进入历史补传队列：只发送最新状态，丢失后等下次；不能重放旧心跳伪装在线。
- 上述 30/90 秒策略只用于 TenonEdge 与平台的连接，不用于 LoRa 传感器。MQTT/HTTP 上游连通也不代表传感器正在上报；传感器按最后报文时间与已确认的上报周期展示。未配置周期时显示最后接收时间或未知，不套用网关心跳判定掉线，见第 21.4 节。

### 9.5 平台侧最小实现清单

| ID | 平台侧工作 |
|---|---|
| PL-01 | 网关登记、启停、凭证生成/撤销、NodeId 绑定 |
| PL-02 | 设备同步、待关联处理、创建/关联权限与稳定映射 |
| PL-03 | 遥测接收、校验、持久化、幂等确认与最新值更新 |
| PL-04 | 心跳接收、最后通信时间、网关和设备状态展示 |

完整 TenonIoT 的报表、规则、历史存储选型和管理页面不在本网关任务中扩张。真实平台接口路径、响应、版本变更须同步更新 `docs/platform-api.yaml` 和契约测试。

## 10. 管理 API、数据和安全

### 10.1 本地管理 API 分组

沿用 TenonAdmin 的认证、分页、错误和 OpenAPI 约定。建议业务前缀 `/api/edge-admin/v1`，与平台接入协议区分。

| API 分组 | 能力 |
|---|---|
| connections | 新增/编辑/禁用、连接测试、凭证更新；不返回秘密明文 |
| devices / groups / points | 基础配置、导入导出、一次读取预览 |
| routes | 草稿 CRUD、静态校验、用样本预览 |
| configuration | 应用全部草稿、查看有效版本、恢复上一版 |
| runtime | 状态、当前值、错误、计数 |
| deliveries | 待发/失败统计、人工重试、明确确认后的清理 |
| platform-links | 复用连接模型，提供连接测试和设备同步操作 |

所有“测试”“预览”“导入”“重试”都必须做与正常操作一致的授权和目标校验。不能只保护 CRUD。

### 10.2 存储对象

可按下表建立实体；最终命名沿用实际仓库约定，不另造复杂主数据平台。

| 对象 | 最少内容 |
|---|---|
| Connection | 类型、名称、非秘密参数、credentialRef、状态 |
| Device | 稳定 deviceKey、名称、连接引用、启停 |
| InputDefinition | 采集组/MQTT/HTTP/模拟输入参数、deviceKey、字段描述 |
| Point | InputDefinition 引用、字段 key、协议地址、类型、单位 |
| Route | 草稿节点定义与布局、启用状态 |
| RuntimeSnapshot | revision、完整非秘密配置快照、有效/上一版引用 |
| Credential | 受保护的秘密内容、用途、更新时间 |
| Delivery | 目标投递数据、稳定编号、状态、重试信息 |
| PlatformDeviceMap | 平台连接、deviceKey、平台设备 ID、同步状态 |

实时值、连接状态、最后错误采用有界内存状态和必要日志即可。不为每条读取写操作审计，也不保存无限历史遥测。

### 10.3 必须保留的基础安全

- 权限至少分管理员、配置人员、只读人员；编辑与应用配置、测试外发、清理缓存分别受控。
- 秘密与普通配置分离，使用框架已有可用保护能力或 ASP.NET Core Data Protection；密钥环必须持久化，并保护访问权限。
- 数据库、密钥和备份放在受限目录；日志和预览脱敏。只做可逆编码、只靠 UI 星号遮盖不算秘密保护。
- Data Protection 密钥丢失会影响解密；迁移时必须处理密钥，不能只复制数据库。参考：https://learn.microsoft.com/en-us/aspnet/core/security/data-protection/configuration/overview?view=aspnetcore-10.0 。
- HTTPS/TLS 证书校验默认启用。连接工业内网所需的明文协议须明确标注风险，不通过全局关闭证书校验解决问题。
- 固定可访问目标；目标的 scheme、主机、端口、DNS 解析结果均校验。允许管理员显式授权现场私网设备，不一刀切禁用所有私网。
- 默认不跟随 HTTP 重定向，不将数据字段作为 URL；防止访问云元数据、宿主管理接口等非授权地址。参考：https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html 。
- 管理页不匿名暴露到公网；首次管理员凭证沿用框架安全初始化，不硬编码公共密码。
- 不允许运行任意脚本或上传执行程序集。扩展模块是受信任的代码依赖，不声称插件机制具有安全沙箱。参考：https://learn.microsoft.com/en-us/dotnet/core/tutorials/creating-app-with-plugin-support 。

## 11. 二次开发要求

只设置三个主要扩展点：输入适配器、纯转换处理器、输出适配器。持久化对 Runtime 提供小接口以便测试，但不开展多存储引擎项目。

- 输入适配器：校验配置、启动接收/采集、输出统一消息、停止释放。
- 转换处理器：输入消息与配置，返回处理结果；默认不访问网络和数据库。
- 输出适配器：校验并生成目标报文，发送已持久化报文，返回明确确认或错误类别。

参数面板先用少量类型化表单和复用组件实现，不先造通用表单设计器或动态 UI 平台。添加一种驱动/输出只改注册和新增实现，不修改路由核心的大量类型判断。

必须给出至少一个模拟输入、一个已有输出的扩展说明和测试。不要把“可以 fork 源码随便改”当成二次开发文档。

完成条件：用户不编辑 JSON 文件也能完成一条路线；浏览器关闭和服务重启后仍按有效配置运行。

### T4：实现 TenonIoT 连接

- 固化 `docs/platform-api.yaml`，实现连接、设备同步、遥测、心跳。

- 测试重复消息、未绑定设备、身份冲突、凭证撤销、旧数据补传。

完成条件：真实平台联调与测试接收端验证分开标注；不以“平台返回 200”代替数据落库和设备关联验证。

- 写出安装、首次采集、画布、平台连接、故障处理、升级备份和扩展开发文档。

## 13. 验收场景

| ID | 场景 | 通过标准 |
|---|---|---|
| AT-01 | 无平台独立启动 | 不安装 TenonIoT/Node-RED，也能登录、配置并使用通用输出 |
| AT-02 | Modbus 已知数据 | 所选功能码、地址、整型/浮点和字节序与模拟设备/实物值一致 |
| AT-03 | MQTT 接收转发 | 外部发布、接收、映射、另一订阅者收到正确内容 |
| AT-04 | HTTP 拉取与推送 | 查询/请求头正确；外部接收端记录完整请求；超时不叠加请求 |
| AT-05 | 可视化真实运行 | 新建路线、保存应用后真实发送；关闭浏览器不停止 |
| AT-06 | 多输出 | 同一输入只建立一个采集实例；一个目标离线不拖停另一个 |
| AT-07 | 格式异常 | 必填缺失、非法 JSON、溢出、超限均可见失败，不发送伪造 0 或旧值 |
| AT-08 | 输入掉线 | 自动重连；显示最后成功时间和过期状态，不上报旧值为新值 |
| AT-09 | 输出断网与恢复 | 已持久化记录按策略补传；旧时间不变；缓存有上限 |
| AT-10 | 进程重启 | 有效配置与 NodeId 保留，待发记录恢复；已读入内存但未入库的风险被如实说明 |

## 16. 企业扩展的代码、发布和授权规则

### 16.1 一套核心，不维护两个长期分支

当前只需要公共 `TenonEdge` 仓库。以后确有商业模块时，可建立私有的企业扩展仓库：

```text
公开 TenonEdge
  Abstractions / Runtime / Adapters / Host / Web
  普通用户仅使用这些内容即可构建和运行

以后按需求增加的私有企业扩展
  专用 Input/Output Adapter
  必要的模块参数组件
  企业发行版装配清单、已授权 SDK 和交付工具
      -> 引用固定版本的公开核心与扩展契约
```

约束：

- 开源核心不引用企业命名空间、私有包源或商业授权服务。公开 CI 不依赖企业仓库凭据。
- 企业扩展复用现有输入、转换、输出三类扩展点，不增加第二套用户、设备、画布、缓存和平台接口。
- 企业发行包仍是一个 .NET 服务和自带 Web 界面；装配发生在构建与依赖注入阶段，不建设在线 DLL 安装。
- 企业发行版可增加一个很薄的装配入口，但不复制 Host 实现；出现通用能力缺口时，经确认回到开源核心修复。
- 前端默认沿用原有参数面板。确实需要自定义组件时明确注册，不把私有代码打入公开包后只用菜单隐藏。
- 不在采集循环、发送路径和每个页面遍布 `if enterprise`。商业模块的可用性在装配/模块边界处理。
- 公开构建中缺少企业模块时应能正常运行。导入引用缺失节点的配置时报告缺失模块并拒绝应用，不静默删节点。
- 企业模块卸载或切换回开源包，遵守第 7.4、8.3 节停止、引用与待发数据检查；保留可导出的配置，不自动删除客户数据。
- 此依赖隔离是工程边界，不是第三方许可合规结论。

### 16.2 发布记录与兼容性

两种发行版使用同一核心版本号，企业模块另记录自身版本及兼容的核心版本。每个实际发布包至少记录：核心版本、扩展模块及版本、构建来源、目标 OS/架构、配置 schema 版本、依赖锁文件和包校验值。

首期用构建生成的 JSON 或文本清单即可，不新增版本管理平台。公开发行清单不泄露私有仓库地址、客户名、激活密钥或下载凭据。

企业模块集成测试必须复用开源核心的相关验收，不接受“企业版自己能启动”作为兼容证据。尚未存在企业模块时，仅验证公开构建不依赖它，不创建无用占位接口。

### 16.3 商业授权：先确定规则，暂不实现服务

以下是未来企业模块的产品约束，不是已签合同，也不授权 Agent 开发授权平台：

- 开源功能不需要商业授权。社区用户二次开发仍按开源许可证行使权利。

## 21. LoRa／LoRaWAN 应用层数据接入

- 记录编号：INT-LORA-01；关联需求：GW-05/06/08/17—19、GW-21。
- 状态：接入方向已确认，具体网关、传感器、报文与兼容性尚未验证。
- 本期工作：复用 G0 输入、字段映射与输出，提供接入说明、单设备样例和软件测试；不增加无线运行环境。
- 扩展工作：需要新增接口、专用适配、多设备分流或按周期自动判断新鲜度时，先明确设备与验收，再按 G1 实施，不自动扩大 T0—T5。
- 版本归属：通用接入与公开配置样例归开源版。专有 SDK 或实际商业适配按第 15—17 节判断，不将 LoRa 整体划为企业专享。

### 21.1 范围与名词

LoRa 是无线调制技术，LoRaWAN 是建立在其之上的通信协议。仅有“LoRa”标识，不能证明设备采用 LoRaWAN 或与某个网关互通。[LR01]

无线网关负责接收和转发无线消息；LoRaWAN 网络及应用服务负责后续网络与应用处理。TenonEdge 的角色是接入已处理的数据，而不是替代这些无线组件。普通工控主机安装本软件不会获得无线收发能力。[LR02]

本方案只接入上游提供的结构化业务数据：不实现射频驱动、不接收原始 Packet Forwarder 消息、不管理 LoRaWAN 入网和根密钥，不增加阀门控制、无线下行或固件升级。

### 21.2 三类现场接入方式

| 上游情况 | 数据链路 | 本方案的处理 |
|---|---|---|
| 网关内置网络服务，且已输出结构化业务数据 | 传感器 -> 无线网关 -> MQTT/HTTP/Modbus 等 -> TenonEdge | 按实际接口复用已实现适配器；先检查通信方向、鉴权与字段，不按产品名称判断兼容 |
| 网关只转发 LoRaWAN 无线报文 | 传感器 -> 无线网关 -> 已部署的 ChirpStack 等网络/应用服务 -> 应用 MQTT -> TenonEdge | 消费应用上行事件，不直接订阅无线网关原始报文作为业务数据 |
| 厂商私有 LoRa、透传或专有报文 | 传感器 -> 厂商接收设备 -> 厂商接口 -> TenonEdge | 按接口协议处理；只有串口或私有二进制时需单独适配，不能称为 LoRaWAN 通用接入 |

ChirpStack Gateway Bridge 转换的是网关包转发协议，并不等于已完成传感器业务字段解码。[LR03] ChirpStack 在本产品中只是可选上游，不是默认依赖；客户另行部署它时也不改变 TenonEdge 单 .NET 服务的交付方式。

Milesight UG65 官方资料列有内置网络服务器、载荷编解码和 MQTT/HTTP/Modbus TCP 等集成能力，可作为第一类设备的接口案例。[LR08] 这不是本产品的采购选型、兼容承诺或整机认证；具体型号、固件、区域配置与实测结果仍需记录。

### 21.3 最小配置：一台传感器对应一个显式输入

优先链路：

```text
已解析的传感器上行数据
       -> input.mqtt
       -> transform.map（需要字段重命名或换算时）
       -> output.tenon / output.mqtt / output.http
```

不新增通用 `input.lora` 节点，也不建设第二套设备管理、凭证或输出服务。初期模板使用普通输入配置和映射规则即可，不实现模板商城。

以 ChirpStack 的默认应用 MQTT 主题为参考，可为已登记设备订阅：[LR04]

```text
application/{applicationId}/device/{devEui}/event/up
```

这里替换为实际 Application ID 与设备 DevEUI，不将 `applicationId` 当成 JoinEUI；MQTT 主题区分大小写，按服务端实际主题配置，不因本地规范化标识而修改主题。[LR04]

实施规则：

1. 保持第 6.2 节的固定 `inputId -> deviceKey`：每台传感器建立一个显式输入，使用精确设备主题；多个输入可引用同一个 Broker 连接配置。
2. 不把 `application/+/device/+/event/up` 收到的全部数据都记到一台逻辑设备。未知设备不能因为出现于报文中而自动建档。
3. 若上游只向一个共用主题发送多设备消息，或一次报文包含多设备数组，记录为需要 G1 的设备筛选/分流适配。未完成前，不用错误的固定绑定冒充兼容。
4. 设备预先由用户建立，外部来源身份与本地 deviceKey 明确关联。LoRaWAN 优先使用来源系统/应用范围与 DevEUI；私有 LoRa 使用厂商定义的稳定节点编号。
5. DevEUI 不是无线接收网关的标识。不要把接收网关 ID 当作传感器 ID；同一传感器被不同无线网关接收时不应变成多个设备。[LR02][LR05]
6. 厂商仅提供 HTTP 推送时，先确认 GW-20 的受鉴权接收接口是否实际存在；HTTP 拉取和 HTTP 输出不能替代它。未实现则记录缺口，不向用户宣称已支持。

### 21.4 载荷、时间、状态和平台关联

**载荷。** 首版优先要求上游把业务载荷解码为 JSON。ChirpStack 可在设备配置中设置载荷编解码规则；这项处理在上游执行，不意味着 TenonEdge 需要运行 JavaScript。[LR06] 只有 Base64 或二进制 `data`、没有对应型号解析结果时，不猜测字节含义，不把解码后的字节直接当温湿度。

**字段。** 用第 6.4 节 JSON Pointer 指向实际字段。`object` 或其他数据字段不保证一定存在；名称、类型、单位由实物和上游解析器决定。电池值可能代表电压、百分比或状态，未核实不互相换算。RSSI、SNR 等可用信息按上游文档解释，不作为连接是否成功的唯一标准。[LR05]

**身份。** 本地 deviceKey 稳定不随显示名称变化，仍按第 9.3 节与 TenonIoT 关联。网关自己的 NodeId/GatewayId、无线接收网关 ID、传感器 DevEUI 是不同标识。平台不因接到多个无线接收记录而重复建立传感器。同步输出属性而非无线密码和完整载荷解码器。

**时间。** 保留网关 receivedAt。只有设备报文明确定义并提供采样时间时，才将它标为真实采集时间；上游事件时间、网络接收时间和本地接收时间要在接入文档中注明。沿用 collectedAt 时明确其时间来源，不默认将 `/time` 解读为传感器采样时刻。不要在补传时覆盖旧事件时间，也不要用旧事件刷新“当前在线”。[LR05]

**状态。** Class A 终端可在两次上行之间休眠，下行接收也受上行后的窗口约束。[LR07] 因此保持三类信息分开：TenonEdge 到平台的心跳、TenonEdge 到上游的连接、传感器最后数据时间。未配置上报周期时，只显示最后接收时间或未知；不得用平台网关的 90 秒超时推断传感器离线。按周期自动标记过期属于 GW-21 的可选小扩展，不是复杂告警引擎。

**重复和质量。** 第 8—9 节保证的是本地投递编号及相应重试处理，不能因此宣称所有 LoRa 应用重复报文都已去重。上游重发、retained 消息和重复应用事件另行记录测试结果；帧计数不能单独当全局唯一键。未知/错误字段不补 0，不将旧测量伪造为新采集。

不为此修改首版平台 API 增加无线网络管理；确需上报额外诊断字段时，先约定字段语义并同步契约测试，不由单端私自扩展。

### 21.5 样例与界面

下面是用于本产品字段映射测试的人工样本，不是某个传感器的实测报文，也不是所有 ChirpStack 版本或设备的固定输出。实际样例以所选版本的上行结构和已配置的解码器为准。[LR05][LR06]

```json
{
  "deviceInfo": {
    "devEui": "0011223344556677",
    "deviceName": "soil-sensor-demo"
  },
  "object": {
    "temperature": 23.7,
    "moisture": 41.5,
    "batteryPercent": 92
  }
}
```

| 配置 | 示例或要求 |
|---|---|
| 输入 | 既有 MQTT 输入，精确订阅此设备的应用上行主题 |
| 逻辑设备 | 用户预先创建，例如 `soil-sensor-001`，不靠名称自动合并 |
| 温度 | `/object/temperature` -> `temperature`；单位需核实，示例按摄氏度解释 |
| 湿度 | `/object/moisture` -> `soilMoisture`；含水率口径及单位需按传感器确认 |
| 电池 | `/object/batteryPercent` -> `batteryPercent`；仅此人工样本明确表示百分比 |
| 时间 | 此样本不含采样时间，使用接入约定的接收时间并注明来源，不伪称实测采样时间 |
| 输出 | 复用已配置 TenonIoT 或通用 MQTT/HTTP 输出 |

界面先沿用“连接管理—设备—MQTT 输入—字段映射—输出”操作。不新增 LoRaWAN 租户、入网、频段规划、无线网关运维或网络服务器控制台。需要展示上报周期时放在设备状态配置中，不改变设备发射周期或下发配置。

配置与导出只保存应用接入凭证引用，不能夹带终端 AppKey、NwkKey 等无线根密钥。实际无线入网和区域设置由用户在相应网络服务/设备侧管理。[LR02]

整机没有 LoRa 无线硬件时，对外描述为“可接入兼容无线网关/网络服务器提供的数据”，不能标成自带 LoRa 射频网关；销售和部署范围仍按第 18 节实际配置核实。
