## 1. Executive Summary

**整体路线是自洽的。** 这条路线由以下几部分组成：

- 单个 .NET 进程；
- SQLite 存储转发；
- 自有的最小运行时和画布；
- TenonAdmin 作为管理底座；
- 可选接入 TenonIoT。

它与"可独立部署的边缘接入转发网关"这个定位一致。Kafka、Redis、微服务、Node-RED、流式 SQL 都不需要，本评审也不建议引入其中任何一项。§0 的约束和 §1.2 的排除项在全文中基本得到遵守；§20（Node-RED）和 §21（LoRa）两节也没有侵入核心架构。

**问题集中在可靠转发的核心。** 文档对投递队列只写到原则层面：发送前入库、确认后清理、容量限制、有限重试。几个承重的定义要么缺失，要么有歧义。它们决定了 T1 的表结构和发送状态机，以及 T3 的应用配置流程——编码之后再改，就是返工。

**最大的风险：**

1. **投递目标没有身份定义**（P0-1）。
   - 投递表按 outputId 分区，单输出配额也以 outputId 为单位；
   - §8.3 的变更约束却是按「对应连接」来写的，退避的单位也没有规定；
   - outputId 本身从未定义，存储对象里也没有输出实体。
2. **失败分类缺少"暂停目标"**（P0-2）。
   - 文档把两类故障混为一谈："凭证失效"是整个目标的故障，"这一条报文不合法"只是单条报文的问题；
   - 失败数据又计入全局缓存上限。一台未绑定的设备，或者一次 token 吊销，就能慢慢吃掉全局上限，最终让所有目标都无法入队。
3. **§2.3 会把投递队列引进 TenonAdmin 的数据库栈**（P0-3）。核实源码后发现：
   - TenonAdmin 的 SQLite 默认没有任何调优，空闲时也在持续写库；
   - 它的 SqlSugarScope 带有依赖用户上下文的审计和过滤钩子；
   - 它自己的部署文档写着「多实例、或有并发写，就换 MySQL / SqlServer / PostgreSQL」。
4. **TenonAdmin 的默认值不适合整机交付**（P0-4）。
   - 它默认创建 5 个密码为 `123456`、处于启用状态的演示账号；
   - 生产环境首次启动还依赖若干必须预置的密钥，否则要么启动失败，要么凭证在重启后无法解密。
5. **"接管"没有可执行的定义**（P1-1）：单写者、分组提交、`synchronous` 级别、掉电语义都没有规定。
6. **应用配置不具备崩溃原子性**（P1-2）："数据库已切换、运行时却没有成功启动"的半成功状态仍然可能出现，还可能演变成崩溃循环。
7. **MQTT 输入按库的默认值实现，就是 at-most-once**（P1-4）。
   - 按 MQTTnet 的默认值实现（clean session、收到即确认），每次应用配置或重启都会丢数，而且没有计数；
   - LoRa 常见的上游 ChirpStack 默认以 QoS 0 发布，问题更严重。
8. **画布规则让配置量与"输入数 × 输出数"成正比**（P1-3）。每台设备都要复制一份映射节点和全部输出节点；10 台设备的场景放在一条路线里，就恰好达到默认的 50 节点上限。
9. **容量数学没有写出来**（P1-6，本文第 7 章 S1）。按默认值，Scenario 1 的每个输出只能缓冲约 1.4 小时的断网；若逐条串行发送，每个目标的吞吐上限约为 1/RTT。

**实际能提供的投递语义**（§8.2 没有宣称 exactly-once，这一点是对的）：

| 区段 | 语义 |
|---|---|
| 采集/接收 → 入库提交之前 | at-most-once。MQTT 输入若"收到即确认"，同样是 at-most-once |
| 入库提交 → 目标确认 | 有界 at-least-once。受配额拒绝、24 小时过期、人工清理和掉电窗口的限制；重发会产生重复，重试时可能乱序 |
| 到 TenonIoT | 在平台的去重窗口（7 天）内 effectively-once，前提是平台按 §9.4 在同一个提交中保存数据和幂等记录 |
| 到通用 MQTT / HTTP | at-least-once。§6.5 已提示可能重复，但通用报文不带可供去重的编号（P2-11） |

**编码前需要修改的基础设计（①）**：P0-1 至 P0-4。P1-11 调整的是 T 阶段的顺序，只改计划、不改架构，但同样应在 T1 之前完成。其余各项都属于"补全定义 + 简单实现"（②），不需要引入新组件。

**成熟网关踩过、本设计还没有意识到的问题**（详见本文 8.10）：

- 把"放进内存队列"或"等待超时"当成"已持久化"或"已确认"（ThingsBoard 网关）；
- 离线缓存"先删除、再发送"（Neuron）；
- 目标参数变了却检测不到，旧数据被发往新目标（EdgeX，推断）；
- 持久存储实际上不限容量（EdgeX、Azure IoT Edge）；
- 共享消息体让各输出的保留策略互相牵制（Fledge）；
- 读指针和时间单位出错，导致积压数据大面积丢失——ThingsBoard 网关在调研探针中，25,000 条积压只送出了 5,020 条。

TenonEdge 的原则性设计已经避开了其中大部分，但原则必须落到 P0-2、P1-1、P1-5、P2-1 这些具体机制上才算数。

**建议保持不动的设计：**

- 单进程，SQLite 作为唯一的存储引擎；
- 应用配置时先停旧、后启新。**不要**改成"先启新、再切换、再停旧"的蓝绿方式，理由见本文第 2 章；
- 每个目标一行投递记录，保存已渲染的报文；
- deliveryId 作为 TenonIoT 的幂等键；
- 一输入一设备；
- 待发数据存在时阻断目标变更；
- 每个目标独立配额；
- 停止超时就中止应用；
- LoRa 走上游网络服务器；
- 首版不引入 Node-RED。

## 2. What Is Well Designed

| 设计 | 章节 | 为什么保留 |
|---|---|---|
| 单进程、SQLite、自带 Web，没有强制的外部依赖 | §0 第 3 条、§3.1 | 边缘现场的运维成本最低；备份和迁移只涉及一个数据目录。 |
| 投递行保存**已渲染的报文**；已入库的数据不按新流程重新处理 | §7.4 末段、§8.2 | 重发的字节是稳定的，所以 TenonIoT「相同编号而内容不同返回 HTTP 409」的判定才可靠；配置变更也不会影响已入库的数据。EdgeX 保存的是流水线位置和版本哈希，哈希一变就删除积压（本文 8.10），TenonEdge 的做法避开了这个问题。 |
| 区分「发送确认」和「业务处理成功」，不宣称 exactly-once | §6.5、§8.2 | 语义诚实，不把 MQTT QoS 1 或 HTTP 200 当成端到端的保证。 |
| deliveryId 作为 messageId；平台以 `(GatewayId, messageId)` 做幂等，并与数据在同一个提交里保存 | §9.4 | 这是网关到平台这一跳实现 effectively-once 的正确做法，AT-11 可以直接测试。 |
| 先停旧输入，再切换、再启动 | §7.4 | 很多 PLC 只接受 1–4 个 Modbus TCP 连接，MQTT Broker 遇到相同的 ClientId 会踢掉旧会话。蓝绿切换要求新旧两套连接并存，在这两类场景里会造成重复采集或互相踢线。它的代价是短暂停采；只要上游以 QoS 1 发布，再配合 P1-4 的持久会话，MQTT 输入在停顿期间就不会丢数。 |
| 同一 inputId 只建立一个采集实例，在内部分发 | §7.2 | 对应 §7.2「不因连了两个输出就采集两次」。 |
| 一输入一设备 | §6.2、§21.3 | 身份绑定显式而且静态，杜绝"通配订阅把多台设备的数据写进同一台设备"。动态分流放到 G1 是合理的（比较见本文 8.1）。 |
| 待发数据存在时阻断目标变更 | §8.3 | 防止旧数据被发给新客户或新平台，这是数据泄露级的风险。参考项目在这里都出过问题：EdgeX 在目标参数变化后检测不到，Neuron 在重配置时会直接删除缓存（本文 8.10）。保留这条规则，补一个显式的迁移操作即可（P2-1）。 |
| 每个目标独立配额，满了就计数拒绝 | §8.2、§8.4 | EdgeX 和 Azure IoT Edge 的持久存储实际上不限容量，一个离线的目标就能占满磁盘（本文 8.10）。TenonEdge 的每目标上限更稳妥。 |
| 停止超时就中止应用，不启动第二套采集 | §7.4 第 5 步 | Node-RED 在节点关闭超时后只记录一条错误，然后照常启动新节点（本文 8.10），新旧实例可能同时持有连接。TenonEdge 的规则更严格。 |
| 缺值不补 0，旧值不当新值，失败可见 | §6.1、§6.4、AT-07/08 | 数据质量的立场正确，很多网关在这里出错。 |
| 说明零基地址；同一物理连接串行访问 | §6.1 | 避开现场最常见的地址错位问题，也避免并发请求把设备打挂。 |
| JSON Pointer 加 `y = x * scale + offset`，不引入表达式语言 | §6.4 | 足以覆盖首版的需求。作为对比，iotgateway 用 DynamicExpresso 表达式做换算，等于引入了脚本能力。 |
| 心跳不进补传队列；传感器的新鲜度与网关心跳分开处理 | §9.4、§21.4 | 避免重放旧心跳来伪装在线，也避免用网关超时去判定传感器掉线。 |
| 编译期模块加 DI 注册，不做 DLL 上传和热加载 | §3.2、§10.3 | 扩展被明确当作受信任的代码，不假装有沙箱。 |
| LoRa 只接入上游已经解码的应用数据 | §21 | 不碰射频和网络服务器，边界正确。 |
| Node-RED 只作为候选记录 | §20 | 自有运行时对本产品更便宜，见本文 8.8。 |
| 证据纪律：implementation-status，未验证的内容明确标注 | §12–§14、§19 | 防止用静态页面或模拟数据冒充能力。 |

## 3. Critical Findings

### P0（全部为 ①）

#### P0-1 投递目标（outputId）没有身份定义　①

- **Finding**：
  - 以 outputId 为单位的有三处：投递表的分区（§8.2）、单输出配额（§8.4）、「输出按目标独立处理」（§8.1）。
  - §8.3 的变更约束却是按「对应连接」来写的；退避的单位也没有规定。
  - outputId 本身在文档里从未定义。
- **Evidence**：
  - §8.2：「按 outputId 分区查询」；投递记录包含 routeId 和 outputId。
  - §10.2 的存储对象里有 InputDefinition，却没有任何输出实体。
  - §7.1、§7.3 中，输出节点的配置内联在路线节点里：`{"id": "n2", "type": "output.tenon", "version": 1, "config": {"connectionId": "platform-main"}}`。
  - 示例中的节点 id 是 `n1`、`n2`。文档没有规定它们如何生成、是否稳定（推断：由前端生成）。
- **Why it matters**：outputId 决定了以下各项：
  - 队列的分区键和索引；
  - 配额的计量单位；
  - 退避和暂停状态挂在哪里；
  - 每条记录由谁发送；
  - §8.3 比较的是什么；
  - 诊断页显示什么。

  它有三种可能的含义：Connection、独立的 OutputDefinition、路线节点。三种含义会导出不同的表结构和状态机。
- **Failure scenario**：
  - 如果按"路线节点"实现：用户在画布上删除一个输出节点，再拖入一个新的——这是很常见的编辑动作。新节点的 id 不同，旧待发记录的 outputId 在新快照里就不存在了。接下来会发生两种情况之一：
    - 这些记录没有人发送，24 小时后按过期计数清理。数据丢了，过期计数也不会说明原因是"目标已不存在"；
    - §8.3 阻止应用，逼用户清空缓存。
  - 两条路线发往同一个 Broker 时，会出现两套独立的退避状态，各自去探测同一个故障目标。
- **Recommendation**：
  - 把投递目标定义为 **Connection**，即物理接收方。§8.3 本来就是按「对应连接」描述目标变更的，这个定义与它一致。
  - 队列分区、发送 worker、退避和暂停状态、配额、§8.3 的身份指纹，全部以 connectionId 为单位。
  - 每条记录冻结自己的 topic/path、QoS 和非秘密请求头。
  - 路线节点只作为统计标签（routeId + nodeId）。
  - 另一个选择是新增一个与 InputDefinition 对称的 OutputDefinition 实体，代价是多一类实体、多一层引用。
  - 无论选哪种，都必须在 T1 建表之前定下来（本文 11，Q1）。
- **V1 impact**：影响 T1 的队列表结构、T3 的画布校验，以及 §8.3 的检查逻辑。做出定义大约需要半天；定义错了，代价是迁移队列数据。

#### P0-2 失败分类缺少"暂停目标"，失败数据挤占全局缓存　①

- **Finding**：
  - §8.2 流程之后的第 4 条，把「认证失败、无效配置、其他确定性 4xx」一律处理为「停止自动重试，显示失败，修正后允许人工重试」。
  - 它没有区分两类故障：
    - 属于**整个目标**的：401/403、TLS/证书错误、平台身份冲突；
    - 只属于**这一条报文**的：400/413/422、内容冲突 409。
  - §8.4 又规定失败数据计入全局上限。
- **Evidence**：
  - §8.2 流程后的第 3、4 条。
  - §8.4 表格"全局发送缓存"一行：「最多 256 MiB，失败待处理数据也计入」；"单输出待发缓存"一行没有说明失败数据是否计入。
  - §9.4：「401/403/409/422 不无限自动重试」；「未绑定设备……待关联完成后人工恢复对应发送」。
- **Why it matters**：两类故障的处理方式完全不同。
  - 目标级故障：应当暂停整个目标，记录保持待发状态，修好之后自动恢复。
  - 报文级故障：只把这一条移到失败区，其余照常发送。

  混为一谈，只会得到两种坏结果之一：
  - 逐条标记失败——凭证修好之后，要人工重试成千上万条；
  - 持续重试——被平台限流，甚至封禁。
- **Failure scenario**：
  - **token 被轮换**：平台侧轮换了 token，网关开始收到 401。如果逐条标记失败，此后每 5 秒一条的新数据都会立即失败，直到有人发现；修复之后还要人工批量重试。
  - **设备未关联**：一台设备在平台上还没有关联，它的每条数据都返回 422，变成失败记录。
    - 按 §8.4，这些失败数据计入**全局** 256 MiB 上限；而失败记录的保留和上限都没有规定。
    - 全局上限会被这一台坏设备慢慢吃掉，最终**所有目标**的新数据都无法入库。
    - 如果实现时把失败记录也计入单输出上限，同一目标下的健康设备会更早被挤掉。
  - 两种结果都违背了 GW-13「慢目标不能无限阻塞其他目标」的精神，只是阻塞的来源从"慢"变成了"坏"。
- **Recommendation**：输出适配器返回四类结果：`Ack`、`Retry(transient, retryAfter?)`、`RejectMessage(code)`、`SuspendTarget(code)`。
  - **Transient**（网络错误、超时、408/429/5xx）：
    - 在目标级退避：指数加抖动，封顶 60 秒；遵守 Retry-After，但设上限；
    - 只用队头的一条记录做探测，不给每条记录单独计时。
  - **SuspendTarget**（401/403、TLS/证书错误、平台身份冲突）：
    - 暂停整个目标，记录保持待发状态，不计入失败；
    - 修复凭证或人工恢复后，继续发送。
  - **RejectMessage**（400/413/422 字段错误、409 内容冲突）：只把这一条移到失败区。
  - **未知异常**：按 transient 处理。但如果同一条记录连续失败 N 次（例如 10 次），而同一目标的其他请求能成功，就把它移到失败区，防止毒消息卡住 FIFO 的队头。
  - **失败区**：单独计数，设单独的上限和更短的保留期，不挤占待发数据的配额。
  - **TenonIoT 的"设备未绑定"**：在路由阶段就不为未绑定的设备生成投递，改为计入 skipped-unbound 并提示，而不是先生成注定会失败的记录（本文 11，Q2）。
  - **平台错误码的映射**：错误码与四类结果的对应关系写进 `docs/platform-api.yaml`。§9.4 已经要求平台返回稳定的字符串 code。
- **V1 impact**：影响 T1 的状态机和表字段（status 的取值、失败区的独立计数），以及 T4 的设备绑定检查。

#### P0-3 投递队列不能放进 TenonAdmin 的数据库栈　①

- **Finding**：
  - §2.3 规定本地存储「优先沿用 TenonAdmin 已有 SqlSugar 接入」，§0 第 3 条又说配置和发送缓存都使用 SQLite。
  - 照此实现，投递队列会和 TenonAdmin 的内核表落在同一个 SQLite 文件里，经由同一个 SqlSugarScope 读写。
  - 核实 TenonAdmin 的源码后发现，这个环境不适合承载写入频繁的队列。
- **Evidence**（TenonAdmin `8109dea`，静态阅读，没有运行）：
  - **库文件**：默认是 `./data/admin.db`（`AdminDatabaseOptions.cs:7-9`）。
  - **没有调优**：产品代码没有设置任何 SQLite PRAGMA，也就是没有开启 WAL（`SqlSugarSetup.cs:307-319`；已亲自核对，`src` 下没有与 SQLite 相关的 PRAGMA）。
  - **ORM 作用域**：全局只有一个共享的 SqlSugarScope（`SqlSugarSetup.cs:99,313`）：
    - 它带软删除和组织过滤；
    - 插入和更新时，按当前用户自动填写审计字段（`SqlSugarSetup.cs:148-203`）；
    - 后台服务中用户和组织为空，以空 CreateOrgId 保存的行，对受限用户不可见（`data-scope.md:90-92`）。
  - **空闲写库**：机器 ID 租约每 5 秒写一次，调度器每 10 秒写两次心跳（`WorkerIdLeaseGuard.cs:34-36`；`JobSchedulerService.cs:179-200`）。
  - **操作日志**：每个已认证的非 GET 请求都同步写入 `sys_op_log`，而且不会自动清理（`OperationLogFilter.cs:59-67`；`LogService.cs:221-230`）。
  - **官方建议**：部署文档原文是「多实例、或有并发写，就换 MySQL / SqlServer / PostgreSQL」（`site/zh/guide/deployment/index.md:37`，已亲自核对）。
  - **额外开销**：SqlSugarScope 每次访问成员，都会构造一次 `new StackTrace(true)`（SqlSugar@01c1c70:`SqlSugarScope.cs:37,51`）。
  - **锁与同步设置**：Microsoft.Data.Sqlite 遇到锁会自动重试，直到命令超时（默认 30 秒）；`synchronous` 没有连接串参数，只能逐个连接设置（Microsoft 文档，已验证）。
- **Why it matters**：
  - 投递队列是全系统写入最频繁、对延迟最敏感的部分，它的事务边界就是可靠性承诺本身（P1-1）。
  - 和管理面共用一个文件、一个 ORM 作用域，意味着写锁争用、审计钩子、组织过滤、文件损坏和磁盘写满的影响范围全都连在一起。
- **Failure scenario**：
  1. 管理员在界面上批量导入点表（一个大事务），与此同时，租约和调度器在写心跳。
  2. 队列写者拿不到写锁（没有开启 WAL 时，读者也会阻塞写者），自动重试最长 30 秒。
  3. 输入通道随之写满，新数据被丢弃，计为"无法入库"。
  4. 另外，admin.db 一旦损坏或磁盘写满，配置、身份和待发数据会同时受影响。
- **Recommendation**：
  - **独立文件**：队列使用独立的 `queue.db`，归 Runtime 所有，直接用 Microsoft.Data.Sqlite 打开：一个写连接（`journal_mode=WAL`，`synchronous` 见 P1-1），加若干只读连接。表结构和版本号由 Runtime 自己管理。
  - **不违反 §2.3**：§2.3 说「不再引入第二套 ORM」。Microsoft.Data.Sqlite 是 SqlSugarCore 本身依赖的 ADO.NET 驱动（SqlSugarCore 依赖 Microsoft.Data.Sqlite ≥ 10.0.11，已验证），不是 ORM。
  - **配置实体留在原处**：Connection、Device、Route、快照、凭证密文这些配置类实体，继续按 TenonAdmin 的约定放在 admin.db 中；启动时为 admin.db 开启 WAL。TenonEdge 的实体不实现 IOrgScoped。
  - **依赖边界**：Runtime 不引用任何 TenonAdmin 程序集。
  - **为什么不用 AdditionalDatabases**：TenonAdmin 的 `AdditionalDatabases[]` 也能挂第二个库，而且没有过滤和审计钩子（`SqlSugarSetup.cs:112-125`）；但它仍然是 SqlSugarScope，也不会自动建表，对队列没有额外的好处（本文 11，Q3）。
- **V1 impact**：必须在 T1 写下第一行队列代码之前定下来。改动只是修改 §2.3 的一句话。

#### P0-4 TenonAdmin 的默认值不适合整机交付：演示账号与首次启动的密钥　①

- **Finding**：设计文档在三处提出了要求：
  - §10.3 第 8 条：「首次管理员凭证沿用框架安全初始化，不硬编码公共密码」；
  - §18.3：「不使用所有设备相同的公共密码」；
  - HW-09：「镜像不含公共生产秘密」。

  TenonAdmin 的默认行为与这些要求冲突，而且生产环境的首次启动依赖若干必须预置的密钥。
- **Evidence**（TenonAdmin `8109dea`）：
  - **演示账号**：`DefaultUserSeed` 始终注册（`ServicesSetup.cs:207`），会创建 **5 个启用状态、密码为 `123456` 的账号**（`DefaultUserSeed.cs:14-21`，已亲自核对；这个类是 `internal sealed`）。
    - 它们属于没有菜单权限的演示角色。
    - 从代码看，它们可以登录，并调用只要求登录的 `[ActiveSession]` 端点（静态阅读，未运行验证）。
    - 要关掉它，只有两个办法：设置 `EnableSeed=false`（这会同时关掉全部种子），或者移除这个注册。
  - **JWT 密钥**：非开发环境下，缺少 `Jwt:SecretKey` 时启动失败（`JwtKeyResolver.cs:44-45`）。
  - **保护密钥**：自带的 `ISecretProtector`，在生产环境下如果同时满足两个条件——没有配置 `Security:DataProtection:Key`，也没有启用 TOTP 或 Cookie 模式——就会**为每个进程生成一个临时密钥**。源码注释原文是「重启后旧信封不可解密」（`LocalDataProtectionKeyProvider.cs:55-89`，已亲自核对）。
  - **建表**：生产环境默认不建表（`EnableCodeFirstInProduction=false`），缺表时启动失败（`AdminDatabaseOptions.cs:19`；`DatabaseInitializer.cs:31-34`）。
  - **初始密码**：superAdmin 的随机密码只在日志里打印一次（`SuperAdminSeed.cs:25-41`）。
- **Why it matters**：
  - TenonEdge 的交付形式包括开源版自行部署和整机交付（§15.1）。整机以镜像形式出厂，部署在工厂的局域网里。
  - §10.3 所依赖的"框架安全初始化"，对这种交付形态并不安全。
- **Failure scenario**：
  - **演示账号**：每台出厂的网关都带着 5 个 `123456` 账号，局域网内任何人都能登录。如果某个 TenonEdge 接口误用了 `[ActiveSession]`，就等于向他们开放了这个接口。
  - **统一的 JWT 密钥**：如果镜像里预置了统一的 `Jwt:SecretKey`，令牌可以在所有设备之间伪造。
  - **保护密钥没有持久化**：每次重启后，所有连接的凭证都会解密失败，全部输出进入认证失败状态。
  - **初始密码**：整机首次开机时，没有人去看日志，就拿不到 superAdmin 的初始密码。
- **Recommendation**：
  - **移除演示账号**：
    - `DefaultUserSeed` 是 `internal` 类，使用方只能按类型名字符串把它从 `IServiceCollection` 中移除，每次升级都可能失效。
    - 更稳妥的做法是请 TenonAdmin 上游把演示种子改为显式开启。这属于另一个仓库，未经授权不改。
    - 在上游修改之前，Host 用字符串匹配移除这个注册，再加一道启动自检：数据库里存在演示账号，就拒绝启动。
  - **首次启动预置密钥**：生成每台设备独有的 `Jwt:SecretKey`、保护密钥和 NodeId，写入数据目录下访问受限的 `secrets` 文件，并作为配置源加载。检测到自己正在使用临时密钥时，拒绝启动运行时。
  - **建表**：首次启动时，受控地建表。
  - **初始密码**：整机交付提供不依赖日志的首次设置流程，例如一次性设置口令。
  - **验收**：HW-01 和 AT-01 各增加两项检查——"不存在演示账号"，以及"两台设备的密钥互不相同"（本文 11，Q4）。
- **V1 impact**：属于 T0 的宿主接线，是一次性的工作，但不做就不能对外交付。

#### P1-1 "接管"缺少可执行的定义：单写者、分组提交、同步级别、掉电　②

- **Finding**：
  - §8.2「承诺范围从发送记录成功提交本地存储开始」，边界的位置是对的。
  - 但"成功提交"在 SQLite 中的含义，取决于 `journal_mode` 和 `synchronous` 的设置。
  - 文档也没有规定写入的组织方式：每条一个事务还是批量提交，由谁来写。
- **Evidence**：
  - 全文没有出现"事务""synchronous""fsync"；WAL 只在 §8.4 最后一段谈磁盘空间时出现过一次。
  - AT-10、HW-05 却要求验证崩溃和异常终止之后的恢复。
- **Why it matters**：
  - **NORMAL 的边界**：SQLite 官方原文是「A transaction committed in WAL mode with synchronous=NORMAL might roll back following a power loss or system crash」（sqlite.org/pragma.html#pragma_synchronous，已验证）。进程崩溃不受影响；而 `FULL` 在 WAL 模式下是持久的。工控现场断电是常态，选 NORMAL，就等于"接管"的承诺在掉电时不成立。
  - **FULL 的代价**：选 FULL 又每条记录一个事务，eMMC/SD 这类存储上每秒会有几十次 fsync，吞吐和寿命都会受损。
  - **多写者**：多个写者（管理 API、运行时、清理任务）同时写同一个文件，会出现锁等待；Microsoft.Data.Sqlite 会自动重试，直到命令超时（默认 30 秒）。
- **Failure scenario**：
  - 选 NORMAL：断电之后，最近几秒内已经"入库"的数据消失。
  - 选 FULL 却逐条提交：在低端存储上，吞吐和寿命都受损。
  - 清理任务与写入争锁：写入超时失败，被计为"无法入库"，数据丢失。
- **Recommendation**：
  - 队列采用**单写者任务加分组提交**：入库、删除、失败标记都交给同一个写者，每 50–100 毫秒或每 N 条提交一次。
  - 使用 `journal_mode=WAL`。建议队列库使用 `synchronous=FULL`，fsync 的成本由分组提交摊薄。
  - 读连接只开短事务。
  - 在文档和 AT-10/HW-05 的测试口径里写明：接管时刻 = 包含该记录的分组提交返回的时刻。
  - 如果最终选择 NORMAL，文档必须写明："进程崩溃安全，掉电可能丢失最近的提交"（本文 11，Q5）。
- **V1 impact**：只影响 T1 的实现方式，不引入新组件。

#### P1-2 应用配置缺少崩溃原子性，结构性失败没有界定　②

- **Finding**：
  - §7.4 第 4 步：「成功停止后切换有效快照并启动。结构性启动失败则恢复上一快照；设备暂时离线则显示运行降级并重连。」——也就是先写指针，后启动。
  - 文档没有定义：进程如果在"已切换、未启动完"之间崩溃，重启后加载哪个快照。
  - 也没有界定"结构性失败"与"设备暂时离线"的分界线。
- **Evidence**：§7.4 第 3–6 步；GW-10；AT-13。
- **Why it matters**：
  - 如果新快照在启动阶段让进程崩溃（适配器缺陷、未捕获的异常），§7.4 第 6 步「重启只加载有效快照」会再次加载它，形成崩溃循环。
  - "数据库配置已经切换，运行时却从未成功启动"，正是本次评审要消除的半成功状态。
- **Failure scenario**：
  1. 用户应用了一份配置，它会让某个适配器在初始化时抛出异常；
  2. 进程退出，systemd 或 Docker 把它重启；
  3. 进程加载同一份快照，再次退出；
  4. 如此循环，现场网关失联，只能手工改库。
- **Recommendation**：
  1. **快照不可变**，revision 单调递增。数据库保存三个指针：`effectiveRevision`、`previousRevision`、`pendingRevision`。
  2. **应用流程**：
     - 校验；
     - 写入 `pendingRevision`；
     - 停止旧输入（超时就中止，并清空 pending）；
     - 启动新计划；
     - 启动成功后（或者稳定运行 N 秒后），在**一个事务**里执行 `previous = effective; effective = pending; pending = null`。
  3. **启动恢复**：启动时如果发现 `pendingRevision` 不为空，说明上次应用中途崩溃了。丢弃 pending 并记录原因，然后按 `effectiveRevision` 启动。
  4. **适配器契约**：`Start` 不做阻塞式的网络 I/O，只建立循环。连接失败一律异步上报为"降级"，不构成应用失败。
  5. **结构性失败**：指构建或启动阶段抛出的异常，例如配置无法解析、凭证无法解密、类型未注册、资源冲突。分两条规则处理：
     - **应用时，全有或全无**：任何结构性失败都整体回滚到上一版，保证有效配置始终是一个一致的整体。
     - **启动时，按单元降级**：加载已生效的快照时，已经没有"上一版"可以原子地切回。所以某个单元的结构性失败（密钥丢失导致凭证无法解密、模块缺失）只停掉这个单元并告警，其余照常运行。
  6. **回滚**：以上一版快照为目标，再走一遍同一条流程，不另写一套逻辑。回滚也失败时，进入明确的 `RuntimeFailed` 状态：输入全部停止，输出继续清空队列，界面告警。
- **V1 impact**：三个指针字段、一个启动检查，加上适配器契约里的两句话。

#### P1-3 画布规则让配置量与"输入数 × 输出数"成正比　②

- **Finding**：§7.2 的三条规定：
  - 「处理、输出节点最多一个上游」；
  - 「不支持多输入合并」；
  - 「每条启用路线设置节点上限，默认 50。该值是防误配置限制，不是性能承诺」。
- **Evidence**：§7.2 第 1、2、5 条。
- **Why it matters**：
  - 网关最典型的用法是"N 台同型号设备 → 同一组输出"。
  - 每个非输入节点只能有一个上游，所以每台设备都要各自复制一份映射节点，以及每一个输出节点。
  - 真正的问题是这种复制带来的维护负担；50 个节点的上限本身是可以调的。
- **Failure scenario**：
  - Scenario 1：10 台电表 × 3 个输出 = 10 个输入 + 10 个映射 + 30 个输出，共 50 个节点。放在一条路线里，恰好达到默认上限；改一个换算系数，要改 10 个映射节点。
  - Scenario 9：500 个 LoRa 传感器需要 1,500 个节点。即使调高上限，这样的画布也没法维护。
- **Recommendation**：
  - 允许**扇入（fan-in）但不做合并（no join）**：一个映射或输出节点可以有多个上游，每条消息独立处理，设备身份取自消息自带的 deviceKey。
  - 图仍然是 DAG，仍然禁止环、脚本、条件和窗口。
  - 运行时编译器从每个输入出发，展开它能到达的路径集合（DFS），不假设图是树形。
  - 现有的 JSON 格式（edges 列表）不需要改版，只要放宽校验。所以这项改动技术上可以推迟，但编译器从第一天起就不能假设树形。
  - 500 台设备的规模问题，留到 G1 用"输入集合节点"解决：一个节点引用一组 InputDefinition，每个 InputDefinition 仍然只绑定一个 deviceKey（本文 8.1；本文 11，Q7）。
- **V1 impact**：影响 T3 的校验规则和编译器。这属于"为了简单而过度简化，导致首版不好用"的一类问题。

#### P1-4 MQTT 输入的会话、ClientId 和确认时机没有定义　②

- **Finding**：文档没有规定三件事：MQTT 输入是否使用 clean session；ClientId 如何生成；QoS 1 的消息在什么时候向 Broker 确认。
- **Evidence**：
  - 全文没有出现 Clean、会话、ClientId。
  - §6.2 只写了 QoS 0/1 和 TLS；GW-05 写了自动重连。
  - §8.2 声明，入库之前的阶段不在保证范围之内。
- **Why it matters**：如果按库的默认值实现（clean session、收到即确认）：
  - 每次应用配置（全局停启所有输入）、每次重启、每次断线期间，Broker 上发布的消息会全部丢失，而不只是延迟；
  - 对 10–15 分钟上报一次的 LoRa 数据源，丢一条就是一个周期的空洞；
  - 这类丢失没有任何计数，因为网关根本没有收到这些消息。

  ClientId 的生成方式同样有问题：按 NodeId 派生，复制部署出来的两个实例会互相踢线；随机生成，又无法使用持久会话。
- **Failure scenario**：用户改了一个换算系数，点击"应用全部变更"。所有 MQTT 输入断开重连 2–5 秒，这段时间里的上游消息永久丢失，诊断页上看不到任何迹象。
- **Recommendation**（MQTTnet 的相关事实都在 MQTTnet@14463d1，即 v5.2.0 的源码中核实过）：
  1. **会话**：
     - 显式指定 `WithProtocolVersion(V311)`。MQTTnet v5 默认使用 MQTT 5.0（`Options/MqttClientOptions.cs:82`），而在 5.0 下会话过期时间默认为 0，只设 CleanSession=false 也保不住会话。
     - 设置 `WithCleanSession(false)`，它的默认值是 true。
     - ClientId 必须稳定——它的默认值是随机的 GUID（`MqttClientOptions.cs:45,51`）。建议在连接上可以配置，默认取 `te-{nodeId 短码}-{connectionId}`。
     - 连接成功后，检查 `IsSessionPresent`。
  2. **确认**：
     - 设置 `AutoAcknowledge=false`，它的默认值是 true。
     - 回调只做大小校验和解析，写入通道后立即返回。
     - 写者完成分组提交后，**按到达顺序**调用 `AcknowledgeAsync`（`Receiving/MqttApplicationMessageReceivedEventArgs.cs:32,76-89`）。MQTT 3.1.1 要求按到达顺序确认 [MQTT-4.6.0-2]。
  3. **畸形或超限的报文**：计数后立即确认。否则它们会一直占着 Broker 的在途窗口，重连后又被重投。只有存储失败时才不确认。
  4. **吞吐**：受"Broker 在途窗口 ÷ 提交延迟"的限制，对首版的量级足够。
  5. **上游也要用 QoS 1**：订阅端的 QoS 1 加持久会话，对以 QoS 0 发布的消息无效。ChirpStack 的 MQTT 集成默认就是 QoS 0（chirpstack@3237e30:`chirpstack/src/integration/mqtt.rs:77-82`、`config.rs:331`），LoRa 的接入说明必须要求上游改为 QoS 1。
  6. **QoS 0 输入**：保持 at-most-once，并在界面上标明。

  这样，只要上游以 QoS 1 发布，Broker 就会在断线和应用配置期间替网关保留消息，输入侧升级为 at-least-once（本文 11，Q8）。
- **V1 impact**：属于 T2 MQTT 输入的实现细节。它也减少了"全局停启"式应用配置造成的丢数；是否只重启有变化的输入，见本文 11，Q14。

#### P1-5 时钟跳变与时间来源　②

- **Finding**：
  - 保留期、重试时间和 collectedAt 全部依赖系统墙钟。文档没有处理三种情况：没有 RTC、RTC 电池失效、NTP 跳变。
  - §6.2 和 §21.4 都要求注明时间来源，但消息模型和报文里都没有承载它的字段。
- **Evidence**：
  - 全文没有出现"时钟""NTP""RTC"。
  - §8.4 规定保留 24 小时；§8.2 的记录字段里有"下次重试时间"。
  - §9.4 只在平台侧检查「明显未来时间」。
  - §6.2 要求「否则使用网关接收时间并注明来源」；§21.4 要求「上游事件时间、网络接收时间和本地接收时间要在接入文档中注明」。但 §6.4 的消息表和 §9.4 的报文里都没有时间来源字段。
- **Why it matters**：墙钟一旦跳变，过期判断、重试调度和数据的时间戳都会同时出错。
- **Failure scenario**：
  - **向前跳变**：
    1. 设备开机时，系统时间是 2020-01-01（没有 RTC）；
    2. 采集并入库几个小时后，NTP 同步到 2026 年；
    3. 清理任务按 createdAt 判断，这些记录全部"超过 24 小时"，整个待发队列被当作过期清理——有过期计数，但数据已经没了；
    4. 同时，这些数据的 collectedAt 是 2020 年，会被平台当作历史数据接受，因为平台只拒绝未来的时间。
  - **向后跳变**：情况相反，记录永远不会过期，重试时间落在几年之后。
- **Recommendation**：
  - 进程内的调度（退避、采集周期、超时）一律使用单调时钟，通过注入 `TimeProvider` 实现；测试时换成 FakeTimeProvider。
  - 持久化的 nextRetryAt，在重启后按"当前时间 + 剩余间隔"重新计算。
  - 过期判断加上跳变保护：createdAt 落在未来，或者与启动时刻的差距异常时，标记为"时钟异常"，而不是清理。
  - 暴露"时钟未同步"的状态。
  - 消息模型和 TenonIoT 报文增加 `timeSource` 字段，取值为 device / upstream / gateway；时钟未同步时，把 collectedAt 标记为不可信（本文 11，Q10）。
- **V1 impact**：改动量小，但必须在 T1 的调度和清理代码中落地。

#### P1-6 发送吞吐的上限、顺序，以及"确认"的定义　②

- **Finding**：
  - §9.4 规定「首版单设备消息整体校验、整体确认，不做批量部分成功」，通用 HTTP 输出也是逐条 POST。
  - 文档没有规定每个目标的在途并发数，也没有规定投递顺序。"顺序"一词在文中只出现在"实施顺序"和"建议顺序"里。
- **Evidence**：§9.4；§6.5；§8.1。
- **Why it matters**：
  - 严格串行时，每个目标的吞吐约为 1/RTT：云端平台的 RTT 为 100 毫秒时，大约每秒 10 条。
  - 确认的定义如果不严格，就会误删数据，或者永久挂起（见下）。
- **Failure scenario**：
  - 100 台 Modbus 设备按 5 秒周期采集，每秒产生 20 条消息，超过了每秒 10 条的发送能力。即使网络一直正常，TenonIoT 目标的队列也会持续增长，直到配额写满、开始拒绝新记录。
  - 断网恢复之后，只有当发送速率大于输入速率时，积压才能追平。
- **Recommendation**：
  - **在途上限**：每个目标可以配置。建议的默认值（本文 11，Q15）：
    - 通用 HTTP：1，保证顺序；
    - TenonIoT：4，因为平台按 collectedAt 处理，不依赖到达顺序（§9.4 已经要求最新值不能倒退）；
    - MQTT QoS 1：可以流水线发送。
  - **顺序**：文档写明，通用目标在重试和并发下可能乱序，接收方应以 collectedAt 判断新旧；积压补传按 FIFO 进行。批量接口留到 G1。
  - **"确认"的定义要严格**：确认 = 真实的协议确认，超时一律视为 transient 失败。
    - MQTTnet 的 `PublishAsync` 没有默认超时，只看调用方传入的 CancellationToken（MQTTnet@14463d1:`Source/MQTTnet/MqttClient.cs:244-282`）。不传带超时的令牌，一个丢失的 PUBACK 就会让发送者永久挂起。
    - ThingsBoard 网关的做法正好相反：最多等 1 秒，超时就当作成功（本文 8.10），数据可能在 Broker 根本没收到的情况下就被删除。
    - MQTTnet 失败时，原因码通过返回结果表示，不抛异常，所以要检查 `IsSuccess`。
    - 使用 5.2.0 或更新的版本：从这个版本起，迟到的 PUBACK 不再断开连接。
- **V1 impact**：发送 worker 多一个参数，文档多一段说明。

#### P1-7 背压、异常隔离和停机顺序没有落到机制上　②

- **Finding**：§8.1 要求「输入到处理的缓冲有明确容量」，但文档没有规定三件事：
  - 缓冲写满时，每类输入怎么处理；
  - 运行单元的异常如何隔离；
  - 进程停机时如何排空。
- **Evidence**：§8.1；全文没有出现 BackgroundService 或 HostedService。
- **Why it matters**：
  - **宿主会被整个停掉**：从 .NET 6 起，BackgroundService 出现未处理的异常时，默认会停止整个宿主（`BackgroundServiceExceptionBehavior.StopHost`）。
  - **MQTTnet 的无界队列**：MQTTnet v5 把收到的 PUBLISH 先放进一个**无上限**的内部队列，再由单独的任务逐条等待回调处理（MQTTnet@14463d1:`Source/MQTTnet/Internal/AsyncQueue.cs:16,45-52`；`MqttClient.cs:954-956,677-708`）。
    - 回调变慢，不会阻塞保活；但积压全部堆在库的内部，而不在我们的有界通道里。
    - QoS 1 时，这部分积压受 Broker 在途窗口的约束；QoS 0 完全没有约束。
  - **静默丢弃**：System.Threading.Channels 的 Drop 模式在丢弃时，`TryWrite` 仍然返回 true（dotnet/runtime@9596acb:`BoundedChannel.cs:418-441`）。如果不用 `itemDropped` 回调（.NET 6 起提供），丢弃就是静默的。
  - **超时不一致**：Docker 默认的停机宽限期是 10 秒，而 .NET 宿主默认的 ShutdownTimeout 是 30 秒。
- **Failure scenario**：
  - 某个适配器在后台循环中抛出未捕获的异常 → 宿主退出 → 自动重启 → 同一份配置再次抛出异常 → 崩溃循环（与 P1-2 叠加）。
  - MQTT QoS 0 的高速输入遇上慢速写入 → 积压转移到 MQTTnet 的无界队列 → 内存持续增长 → OOM。
  - `docker stop` 在 10 秒后发出 SIGKILL，写者手中还没提交的那一批记录全部丢失。
- **Recommendation**：
  - **一个 RuntimeHost**：只注册一个 BackgroundService。它的内部由 supervisor 管理所有运行单元：每个连接或输入的循环、分发器、存储写者、每个目标的发送者、清理任务。
  - **异常隔离**：
    - 每个单元有自己的 CancellationTokenSource；
    - 异常在单元的边界捕获，记录最后一次错误，按退避重启，绝不冒泡到宿主；
    - 禁止 `async void` 和未等待的回调。
  - **背压按输入类型定义**：
    - 轮询类（Modbus、HTTP）：等待。周期超时就跳过本周期，并计一次 overrun。
    - 推送类（MQTT）：回调永远不等待，只用 `TryWrite` 写入有界通道。通道满时，QoS 1 不确认，交给 Broker 的在途窗口形成背压；QoS 0 立即丢弃并计数。
    - 所有的丢弃都通过 `itemDropped` 回调或显式的计数器可见。
  - **停机顺序**：
    1. 停止输入；
    2. 排空通道；
    3. 写者做最后一次提交；
    4. 停止发送——在途的发送被取消，记录保持待发状态。

    HostOptions.ShutdownTimeout 与 Docker 的 `stop_grace_period` 对齐。
- **V1 impact**：属于 T1 的骨架。不做的话，它会在现场以"偶发的全站停摆"的形式出现。

#### P1-8 连接共享模型没有定义，预览和测试会干扰运行中的连接　②

- **Finding**：
  - §21.3 第 1 条写着「多个输入可引用同一个 Broker 连接配置」，§6.1 规定同一物理连接串行访问。
  - 但文档没有定义一个 Connection 在运行时对应几个客户端实例。
  - 也没有定义预览和"测试连接"走什么通道。
- **Evidence**：
  - §6.1；§21.3 第 1 条；§5「一次读取预览」；§10.1「连接测试」。
  - §6.1 写的是「设备配置包含主机、端口、UnitId」，而 §10.2 的 Device 是「稳定 deviceKey、名称、连接引用、启停」，两处不一致。
- **Why it matters**：连接是现场最稀缺的资源。很多设备只接受一两个 TCP 连接，Broker 又按 ClientId 管理会话。
- **Failure scenario**：
  - 每个输入各开一个 MQTT 客户端：Scenario 9 就是 500 个 TCP 连接、500 个 ClientId；Broker 重启时，500 个客户端同时重连。
  - Modbus 预览另开一个 TCP 连接：遇到只允许 1 个连接的 PLC 或串口服务器，要么把运行中的采集连接挤掉，要么自己被拒。这违反了 §6.1 的串行约束。
  - MQTT"测试连接"复用运行中的 ClientId：会把运行中的连接踢下线。
  - TCP 转 RTU 的串口服务器：多个 UnitId 共用同一个 host:port，必须共享一个连接和一个串行执行器。
- **Recommendation**：
  - 运行时提供 ConnectionManager：每个 Connection 对应一个客户端或会话，按引用计数管理（类似 Node-RED 的配置节点，见本文 8.10）。输入、输出和预览都向它借用连接。
  - Modbus 预览作为一次性请求，排进这个连接的串行执行器。
  - MQTT 测试连接，使用带独立后缀的 ClientId。
  - Modbus 的 host:port 只放在 Connection 上，设备和采集组只持有 UnitId。
- **V1 impact**：影响 T2 的适配器实现，同时为 Modbus RTU 铺路：串口本身就是一个 Connection。

#### P1-9 出站校验必须在建立连接的那一刻执行　②

- **Finding**：设计已经定好了策略，缺的是执行方式。
  - **策略**：
    - §10.3 第 6 条：「目标的 scheme、主机、端口、DNS 解析结果均校验。允许管理员显式授权现场私网设备」；
    - §10.3 第 7 条：「默认不跟随 HTTP 重定向……防止访问云元数据、宿主管理接口等非授权地址」；
    - §5 与 §10.1 要求预览、测试和重试，使用与运行时相同的权限和目标校验。
  - **执行方式**：文档没有规定校验发生在保存时还是连接时，也没有说明如何处理代理，以及库的默认值与策略相反时怎么办。
- **Evidence**：§10.3 第 6、7 条；§5 最后一段；§10.1 最后一段。
- **Why it matters**：HTTP 拉取加上预览，构成了一条**带回显的 SSRF** 通道。只在保存时校验，是可以绕过的。
- **Failure scenario**：
  - **DNS rebinding**：配置人员填写一个域名，保存时它解析为公网地址，通过了校验；到实际拉取时，它被解析为 `127.0.0.1`（本机的管理端口）或 `169.254.169.254`。响应的 JSON 会出现在预览面板里。
  - **代理**：容器里设置了 `HTTP_PROXY` 时，HttpClient 默认走代理，`ConnectCallback` 看到的是代理的地址，校验失效（dotnet/runtime@9596acb:`HttpConnectionPool.cs:582-583,804`）。
  - **重定向**：HttpClient 默认 `AllowAutoRedirect=true`。重定向时只清除 `Authorization` 头，`X-API-Key` 等自定义头会被原样带到新主机（Microsoft 文档，已验证）。实现者如果忘了显式关闭，就违背了 §10.3 第 7 条。
- **Recommendation**：
  - **HTTP**：
    - 在 `SocketsHttpHandler.ConnectCallback` 里，对实际连接的 IP 做校验；
    - 显式设置 `AllowAutoRedirect=false`；
    - 默认 `UseProxy=false`，确实需要代理时，作为连接的显式参数。
  - **MQTT 和 Modbus**：在建立 socket 之前，做同样的校验。
  - **默认拒绝的地址**：
    - 回环地址，包括本机的管理端口；
    - 链路本地地址（169.254.0.0/16、fe80::/10）；
    - 未指定地址；
    - 组播地址；
    - 以及上述各类地址的 IPv4 映射 IPv6 形式。
  - **预览响应**：限制长度。
- **V1 impact**：T2 就要做（HTTP 拉取在 T2 实现），不能等到 T5。

#### P1-10 凭证保护机制：两个候选都有默认陷阱　②

- **Finding**：
  - §10.3 第 2 条要求「使用框架已有可用保护能力或 ASP.NET Core Data Protection；密钥环必须持久化」，第 4 条要求「迁移时必须处理密钥」。
  - 方向是正确的，但文档没有指出这两个候选各自的默认陷阱。
- **Evidence**：
  - **TenonAdmin 自带的 `ISecretProtector`**（AES-GCM，密钥为 `Security:DataProtection:Key`）：
    - 生产环境下，如果没有配置密钥，也没有启用 TOTP 或 Cookie 模式，**每个进程都会生成一个临时密钥**（`LocalDataProtectionKeyProvider.cs:55-89`）；
    - 只有一个密钥版本，不支持轮换（`:99-103`）；
    - 目前只用于保存 TOTP 种子（`ServicesSetup.cs:33-46`）；
    - TenonAdmin 本身没有配置 ASP.NET Data Protection。
  - **ASP.NET Core Data Protection**（aspnetcore@ad6ce5f 与 Microsoft 文档，已验证）：
    - 在 Linux 上，默认的密钥位置是 `$HOME/.aspnet/DataProtection-Keys`；没有用户目录时，使用临时密钥；
    - 密钥不加密落盘，警告文本是 "No XML encryptor configured"；
    - 应用鉴别符默认取内容根的物理路径（`Internal/HostingApplicationDiscriminator.cs:30-42`）。官方要求 `SetApplicationName` 的值 "should match across deployments"；
    - 在容器中不挂卷时，官方警告 "Protected data will be unavailable when container is destroyed"；
    - 官方还说明，它并非主要用于机密载荷的无限期持久化。
- **Why it matters**：凭证丢失意味着所有输出同时失效，而且只有重新录入全部凭证才能恢复。
- **Failure scenario**：
  - **选了 TenonAdmin 的保护器，却没有配置密钥**：每次重启后，所有连接的凭证都解密失败，全部输出进入认证失败状态。
  - **选了 ASP.NET Data Protection，却没有设置应用名，也没有挂卷**：升级时换了安装目录（推断），或者重建了容器，结果相同。
  - **备份**：两种情况下，备份包里都同时存着密文和明文的密钥，备份本身就等同于明文。
- **Recommendation**：
  - **只选一种机制**（本文 11，Q6）。在 Abstractions 中定义 `ICredentialResolver`，由 Host 实现，这样 Runtime 就不依赖 TenonAdmin。
  - **无论选哪一种**：
    - 密钥或密钥环在首次启动时生成，持久化到数据目录（P0-4）；
    - 检测到临时密钥时，拒绝启动运行时。
  - **如果选 ASP.NET DP**：固定调用 `SetApplicationName("TenonEdge")`，并且永远不清理旧密钥。
  - **威胁模型**：文档写明，这套机制只防"只拿到数据库文件"的泄露，不防整个磁盘被获取。备份要包含密钥，并按秘密的级别保管。
  - **验收**：AT-19 增加用例——重启、更换安装路径、重建容器之后，凭证仍然能解密。
- **V1 impact**：几行配置，加若干测试用例。选哪种机制，由你决定。

#### P1-11 T0–T5 的顺序：凭证存储、权限码和运行计划契约需要前移　②

- **Finding**：
  - T1 实现运行时加「一个最小配置」，T3 才实现快照和应用。
  - T5 才「完善权限、日志脱敏、有限缓存和配置安全操作」。
  - 凭证存储没有出现在任何一个 T 步骤里，但 T1、T2 的 MQTT/HTTP 输出已经需要凭证了。
- **Evidence**：§12 T1–T5。
- **Why it matters**：顺序不对，前面做的东西就要返工。
- **Failure scenario**：
  - T1 用了一个临时的配置格式；T3 引入快照之后，运行时的加载路径要重写。
  - T2 的 HTTP 输出如果先把 Bearer token 放在配置 JSON 里、打算"以后再改"，秘密就会进入快照、导出文件和日志。
  - T5 才补权限，意味着之前所有的 API 都要回头加授权，再重新测试一遍。
- **Recommendation**：
  - T1 就定义 `RuntimePlan`：它是快照编译之后的不可变 DTO，放在 Abstractions 里，作为 Host 与 Runtime 之间唯一的契约。T1 从种子文件加载它，T3 只增加"草稿 → 编译 → 应用"这一层。
  - 凭证存储和 P0-4 的首次启动预置，放进 T0/T1。
  - 每个管理 API 在创建时就带上权限码（本文 8.5），T5 只做审计和补漏。
  - SSRF 白名单随 T2 一起落地（本文 11，Q11）。
- **V1 impact**：只调整计划，不扩大范围。

#### P1-12 磁盘将满时的行为，包括管理界面是否还能用　②

- **Finding**：
  - §8.4 已经提出要保留磁盘余量，但没有规定何时停止接收。
  - 也没有考虑队列之外的写入在磁盘写满时会怎样，包括 TenonAdmin 的会话、操作日志、令牌，以及文件日志。
- **Evidence**：
  - §8.2 流程后的最后一条；§8.4 最后一段；AT-12；HW-07。
  - TenonAdmin 把会话存在数据库里：每个请求都要校验会话，刷新令牌轮换时要写库（`ISessionService.cs:17`；`RolePermissionAttribute.cs:37-43`）。
  - 每个已认证的写请求，都同步写入 `sys_op_log`（`OperationLogFilter.cs:59-67`）。
  - SQLite 官方说明：SQLITE_FULL 可能回滚整个事务，建议显式执行 ROLLBACK（sqlite.org/lang_transaction.html）。
- **Why it matters**：AT-12 要求磁盘不足时「显示故障」，前提是运维人员还能登录进来看到它。
- **Failure scenario**：
  - 磁盘写满后，队列插入失败，按设计丢弃并计数——这一步没有问题。
  - 但删除已确认的记录同样要写 WAL，也会失败：已确认的记录删不掉，重启之后会被重发。
  - 登录续期和所有的管理操作都要写库，也会失败。运维人员无法进入界面查看"存储异常"，只能 SSH 上去处理。
- **Recommendation**：
  - 以可用空间的阈值为界（例如低于 5% 或 500 MB，可以配置），提前进入"存储保护"状态：拒绝新的入队并计数，同时为删除、检查点、管理界面和日志留出余量。
  - 可用空间恢复到阈值以上后，自动退出这个状态。
  - 对"已确认、但删除尚未提交"的记录，发送者在内存中保留标记，避免在同一个进程里重复发送。
- **V1 impact**：一个定时检查，加一个状态。AT-12 的验收依赖它。

#### P1-13 平台 API 如果沿用 TenonAdmin 的默认封装，网关就无法判定成败　②

- **Finding**：
  - §9.4 定义了成功报文：「成功响应统一为：`{"code":"ok","data":{...}}`」；失败时返回稳定的字符串 code，并且「配合正确 HTTP 状态码」。
  - §9.1 要求连接器处理「业务确认」。
  - §9.4 也预见到了分歧：「若实际平台已采用统一响应封装，以生成的 OpenAPI 统一调整双方」。
  - 但文档没有规定：平台一旦沿用了 TenonAdmin 的封装，网关该如何判定成败。
- **Evidence**：TenonAdmin 的默认封装是 `{code,msgKey,args,message,data}`，code 为 0 表示成功；**业务错误返回 HTTP 200**（`Result.cs:12-44`；`AdminExceptionFilter.cs:23` 返回的 `ObjectResult` 没有设置状态码，已亲自核对）。
- **Why it matters**：TenonIoT 如果基于 TenonAdmin 构建（**待验证**），"设备未绑定""字段不合法"这类错误，都会以 HTTP 200 加一个非 0 的 code 返回。
- **Failure scenario**：输出适配器按"HTTP 2xx 即成功"来判定，未绑定设备的数据被当作已送达并删除，静默丢失。这恰好绕过了 P0-2 的全部保护。
- **Recommendation**：
  - T4 之前，在 `docs/platform-api.yaml` 中定下一种约定（本文 11，Q12）。
  - TenonIoT 输出适配器同时校验 HTTP 状态和封装里的 code；任何无法识别的响应，都按 transient 处理，而不是当作成功。
  - 契约测试覆盖"HTTP 200 + 业务错误"的情况。
  - §6.5 通用 HTTP 输出的「业务码判断」同样适用这条规则。
- **V1 impact**：T4 之前定稿。

### P2（全部为 ②）

**P2-1 目标变更阻断：补充发送时校验和显式迁移操作　②**
- **Finding**：§8.3 的阻断规则是对的，但有两个缺口：检查的时机，以及"旧服务器已经下线"这个死角。
- **Evidence**：
  - §8.3：「用户先发送完毕或显式清理后再改」。
  - §7.4 第 2 步是校验，第 3 步是停止输入。文档没有规定 §8.3 的检查放在哪一步（推断：最自然的实现是放在第 2 步）。
- **Why it matters**：这条规则防的是"旧数据被发往新的接收方"，它只有在检查不留空隙时才真正有效。
- **Failure scenario**：
  - 检查放在第 2 步时：从校验到停止输入之间，旧输入仍在产生新记录。切换之后，这些记录带着旧目标留在队列里。
  - 旧服务器已经永久下线，用户只是想换一个地址：此时"发送完毕"不可能实现，只剩"清空"一条路，被迫丢掉最多 24 小时的数据。
- **Recommendation**：
  - 停止输入之后，再检查一次。
  - 真正的不变量放在发送时：发送者比较记录上的目标指纹与当前连接的指纹，不一致就不发送，并标记为 target-changed。
  - 增加一个需要管理员权限的操作——"将 N 条待发记录迁移到新目标"，需要二次确认并记入审计，实现上只是一条 UPDATE（本文 11，Q16）。
- **V1 impact**：发送时多一次比较，外加一个管理操作。

**P2-2 投递记录不应保存凭证引用　②**
- **Finding**：§8.2 的投递记录字段里包含「凭证引用」。
- **Evidence**：§8.2 的记录字段；§8.3「相同目标下轮换凭证可以允许，旧数据仍发送到原目标」。
- **Why it matters**：凭证属于连接，不属于某一条记录。把引用存进记录，就把队列和凭证的生命周期绑在了一起。
- **Failure scenario**：
  - 如果凭证轮换是通过"新建凭证、再修改连接的引用"来完成的，旧记录仍然引用已吊销的旧凭证，发送时会批量 401。如果是原地更新，就不会出现这个问题——§10.1 的「凭证更新」和 §10.2 的「更新时间」暗示的是原地更新（推断）。
  - 无论哪种方式，删除凭证前的引用检查都要扫描整个队列。
- **Recommendation**：凭证在发送时从当前的 Connection 解析。记录上只保存目标指纹，以及冻结的 topic/path、QoS 和非秘密请求头。
- **V1 impact**：投递表少一个字段。

**P2-3 消息模型需要补充的字段和约定　②**
- **Finding**：统一消息模型缺少四样东西：时间来源、实际来源的元数据、完整的 quality 取值、数值精度的约定。
- **Evidence**：
  - §6.4 的字段表。
  - quality 只在正文和示例里出现过 good（§9.4 的示例）和 bad（§6.1），没有完整的取值定义。
  - §6.2 允许通配订阅。
- **Why it matters**：
  - 通配订阅时，实际收到的 topic 会丢失。
  - quality 的取值和数值的表示方式一旦进入 TenonIoT 的契约，以后再改就是破坏性变更。
- **Failure scenario**：
  - 用 double 计算时，int16 × 0.1 得到 23.700000000000003；float32 的 23.7 转成 double 是 23.700000762939453。AT-02 会因此出现"看起来不一致"的值。
  - OPC UA（G1）需要 uncertain 这个取值，也需要每个值自己的时间戳。
- **Recommendation**：
  - 增加 `timeSource` 字段（见 P1-5）。
  - 增加只读的 `source` 元数据：实际的 topic、HTTP 状态码、Modbus 的 UnitId 和功能码。
  - quality 的取值定为 good / uncertain / bad，并附原因码。建议采用稀疏表示：出现在 values 里的字段默认为 good，只把异常字段单独列出——参考 Neuron 把 values 和 errors 分开的做法（本文 8.10）。
  - 为"每个字段可选的时间戳"留出位置。
  - 数值：整数寄存器的换算用 decimal 计算；float32 按 float 的最短往返格式序列化；映射规则增加一个可选的"保留小数位"。
- **V1 impact**：在 T1 定义消息模型时一并确定。

**P2-4 草稿的并发编辑，以及凭证的生命周期　②**
- **Finding**：全局草稿没有并发控制；凭证又不进入快照，所以凭证的修改和回滚都不受"应用"流程约束。
- **Evidence**：§7.4 的「全局草稿」；§10.2 的 RuntimeSnapshot 是「完整非秘密配置快照」；§10.1 的 connections 分组包含「凭证更新」。
- **Why it matters**：回滚的前提是，上一版快照引用的东西都还在。
- **Failure scenario**：
  - 两名配置人员同时编辑全局草稿，后保存的会覆盖先保存的。
  - 凭证的修改不经过"应用"，立即生效（推断）；回滚配置时，凭证不会跟着回滚。
  - 如果删除了一个被上一版快照引用的凭证，回滚就会失败。
- **Recommendation**：
  - 草稿加版本号，做乐观并发控制。
  - 被 effective 或 previous 快照引用的凭证，不可删除。
  - 在界面上说明：凭证的修改立即生效，不需要应用。
- **V1 impact**：一个版本字段，加一条删除检查。

**P2-5 平台设备同步应当基于有效快照　②**
- **Finding**：设备同步的内容来自草稿还是有效快照，文档没有规定。
- **Evidence**：§9.2 第 3 步：「用户选择需要同步的设备及最终输出字段」，而最终的输出字段由映射决定；§9.4 的 catalogVersion 没有定义。
- **Why it matters**：平台上的字段定义，应当与网关实际发送的数据一致。
- **Failure scenario**：如果从草稿计算同步内容，平台会收到尚未生效的字段定义，与实际上报的数据对不上。
- **Recommendation**：同步内容只从 effective 快照计算；catalogVersion 取 effective revision。
- **V1 impact**：T4 的一条规则。

**P2-6 保留期与平台去重窗口：不变量已经写了，还要能强制执行　②**
- **Finding**：
  - §9.4「平台处理约束」的最后一条已经规定：「去重记录保留时间必须大于网关允许重试/保留时间及时间容差」。
  - 但网关的保留期是可以配置的（§8.4、§15.2），缺少强制手段。
- **Evidence**：§9.4（「初始可取 7 天」）；§8.4（默认 24 小时）；§15.2（「必须可解释和可配置」）。
- **Why it matters**：一旦越过去重窗口，平台的幂等就失效了。
- **Failure scenario**：用户把保留期调到 10 天。重发 7 天以前的数据时，平台会把它们当作新数据保存。
- **Recommendation**：`/connect` 的响应返回平台的去重窗口，网关把保留期的上限钳制在这个窗口之下。
- **V1 impact**：协议加一个字段，网关加一次校验。

**P2-7 检测复制部署，需要实例级的随机标识　②**
- **Finding**：§9.3 要求「另一个实例用同一身份连接应拒绝或要求管理员明确重新绑定」，但协议里没有可以区分实例的字段。
- **Evidence**：§9.3；§9.4 中 `/connect` 的请求内容只有 nodeId、agentVersion 和 protocolVersion。
- **Why it matters**：两个实例发送的是同一个 NodeId，平台无法区分"同一个实例在重连"和"一个克隆出来的实例"。
- **Failure scenario**：整机被复制部署后，两个实例轮流上报，数据交错写入同一个平台身份。MQTT 的 ClientId 也会冲突，两个实例互相踢线。
- **Recommendation**：
  - `/connect` 和心跳增加一个 `bootId`：每次进程启动时随机生成，不持久化。
  - 平台在一个心跳窗口内，看到两个不同的 bootId 交替出现，就判定为身份冲突。
  - ClientId 可以配置。
- **V1 impact**：协议加一个字段，平台加一条判定规则。

**P2-8 快照 schema 升级、缺失模块和降级　②**
- **Finding**：文档规定了导入和应用时如何处理未知版本和缺失模块，但没有规定启动时怎么处理。
- **Evidence**：
  - §7.3：「未知 schemaVersion 或节点版本应拒绝导入/应用」。
  - §16.1：「导入引用缺失节点的配置时报告缺失模块并拒绝应用」；「企业模块卸载或切换回开源包，遵守第 7.4、8.3 节停止、引用与待发数据检查」。
  - §14 要求提供「数据库初始化/升级方式」。
- **Why it matters**：软件升级和切换发行包，都发生在正在运行的程序之外，程序没有机会先执行 §16.1 要求的那些检查。
- **Failure scenario**：
  - 升级之后，已保存的 effective 快照还是旧的 schemaVersion。
  - 企业包换回开源包之后，effective 快照里含有未知的节点类型，启动时的行为没有定义。
  - 降级之后，新版本写入的快照读不出来。
- **Recommendation**：
  - 提供逐版本的快照升级器（vN → vN+1），用纯函数实现，带测试。
  - 启动时遇到缺失的模块，按 P1-2 的"启动时按单元降级"规则处理：受影响的路线不启动，并报告"缺少模块"；其余路线照常运行。
  - 保存快照时附带内容哈希，启动时校验，对应 §7.4 第 6 步的「有效快照损坏时报告错误」。
  - 不支持降级；升级之前自动备份。
- **V1 impact**：一个升级器框架，加一条启动规则。

**P2-9 凭证类型需要包含证书　②**
- **Finding**：Credential 实体没有类型字段，无法表达证书类的凭证。
- **Evidence**：GW-02 要求统一保存「TLS、凭证引用」；§10.2 的 Credential 只有「受保护的秘密内容、用途、更新时间」。
- **Why it matters**：常见的输出目标和未来的协议，都需要证书。
- **Failure scenario**：
  - MQTT 输出到 AWS IoT Core，或者某些工业 Broker 时，需要客户端证书（mTLS）。
  - 使用自签 CA 的内网 Broker，需要自定义受信任的 CA。
  - OPC UA（G1）完全依赖证书。
- **Recommendation**：首版的 Credential 增加类型字段，取值包括：
  - password；
  - token；
  - apiKey，并注明位置：header 或 query；
  - clientCertificate：PKCS#12，或 PEM 加私钥；
  - trustedCa：不是秘密，但同样纳入管理。
- **V1 impact**：一个类型字段，加两种 TLS 装配方式。

**P2-10 敏感信息的旁路　②**
- **Finding**：用户会把秘密放进非秘密的字段里，文档对此没有防护措施。
- **Evidence**：§6.3：「查询参数、非秘密请求头与凭证分开保存」。
- **Why it matters**：秘密一旦进了普通配置，就会随快照、导出和日志扩散出去。
- **Failure scenario**：
  - 用户会把 `X-API-Key` 写进"静态请求头"，把 `?token=` 写进 HTTP 拉取的 URL，把 `user:pass@host` 写进地址。
  - 如果重定向没有关闭，自定义头还会被带到新的主机上（P1-9）。
  - .NET 10 的 HttpClient 日志是否默认对查询串脱敏：**待验证**。
- **Recommendation**：
  - 校验时识别常见的敏感请求头名、查询参数名和 URL 中的 userinfo，要么直接拒绝，要么强制转为凭证引用。
  - 显式配置 HttpClient 日志的脱敏。
- **V1 impact**：校验器增加一组规则。

**P2-11 通用输出应当携带稳定的消息编号　②**
- **Finding**：接收方要去重，必须有一个稳定的编号，但目前只有 TenonIoT 的报文带这个编号。
- **Evidence**：
  - §6.5：「通用 HTTP 接收方若不支持幂等，重试可能造成重复」——文档只做了提示。
  - §9.4 的 messageId 只用于 TenonIoT。
- **Why it matters**：at-least-once 的前提是接收方能够去重。
- **Failure scenario**：网关崩溃后重发，通用 HTTP 接收方收到两份相同的数据，却没有办法识别出来。
- **Recommendation**：
  - 通用 HTTP 输出默认加上 `Idempotency-Key: <deliveryId>` 请求头。
  - 报文组装提供三个白名单占位符：`{messageId}`、`{sourceMessageId}`、`{collectedAt}`。
  - MQTT 3.1.1 没有用户属性，编号只能放在报文里。
- **V1 impact**：一个请求头，三个占位符。

**P2-12 Modbus 采集调度的细节　②**
- **Finding**：采集调度的几个细节没有定义：周期超时怎么办，失败后多快放弃，批量读取怎么合并，支持哪几种字节序。
- **Evidence**：§6.1。
- **Why it matters**：这些细节决定了一台坏设备，会不会拖慢同一条总线上的其他设备。
- **Failure scenario**：
  - 周期超时时怎么处理没有定义：按固定速率还是固定延迟，要不要跳过。
  - 设备离线时，每个读取块都要各等一次 5 秒超时。设备挂在串口服务器上时，同一连接上的其他设备也会被一起拖慢。
  - 合并读取的区间如果跨过了未配置的地址，很多设备会对整块返回异常码 02。
- **Recommendation**：
  - 周期超时就跳过本周期，并计一次 overrun。
  - 一个块超时后，本周期剩下的块直接判为失败，然后按退避重连。
  - 合并区间不得跨越未配置的地址。
  - 32 位类型明确支持四种字节/字序：ABCD、CDAB、BADC、DCBA。
- **V1 impact**：T2 的调度实现。

**P2-13 项目结构：存储实现不应放在 Adapters　②**
- **Finding**：§3.2 把 SQLite 实现放在 `TenonEdge.Adapters` 里；§11 又说「持久化对 Runtime 提供小接口以便测试」。
- **Evidence**：§3.2 的代码结构；§11。
- **Why it matters**：投递存储不是可以替换的协议适配器。它承载的是核心的可靠性语义：事务边界、配额和状态机。
- **Failure scenario**：存储放在 Adapters，再为了"可测试"包一层接口，可靠性的逻辑就被拆散到了两个地方。
- **Recommendation**：
  - 存储实现放进 Runtime（或者一个独立的 TenonEdge.Storage 项目），直接基于 SQLite 实现。
  - 测试时用真实的 SQLite 临时文件，不需要 IDeliveryStore 这类替身接口。
- **V1 impact**：只调整代码结构。

**P2-14 管理界面的传输安全　②**
- **Finding**：§10.3 第 8 条只规定「管理页不匿名暴露到公网」，没有规定传输加密。
- **Evidence**：§10.3 第 8 条。
- **Why it matters**：管理界面上要录入管理员密码和各种凭证。
- **Failure scenario**：在现场局域网里用 HTTP 访问管理页，管理员密码和正在录入的秘密都以明文传输。
- **Recommendation**：
  - 首次启动时生成自签证书，默认使用 HTTPS，并允许替换证书；或者在文档中明确要求由反向代理提供 TLS。
  - TenonAdmin 部署文档的安全基线表里，有两条同样适用（`site/zh/guide/deployment/index.md`，已亲自核对）：
    - 在反向代理之后运行时，必须配置 `TenonAdmin:Api:ForwardedHeaders`，否则限流和防暴力破解都会按代理的 IP 计算；
    - 后端顺带托管前端时（即"路线 A"，正是 TenonEdge 的单服务形态），上传目录必须移出 `wwwroot`，否则上传的文件可以被匿名访问。
- **V1 impact**：属于 T5 的部署项。

**P2-15 术语不一致　②**
- **Finding**：同一个词，在不同的章节里指不同的东西。
- **Evidence**：
  - "路线"在 §7.3 中指整个图文档；而在 §6.4「该路线本条消息失败，不发送半成品；其他分支不受影响」中，指的是一条路径。
  - §8.3 说「把对应连接切换成其他服务器、Topic」，但 Topic 属于输出节点，不属于连接。
- **Why it matters**：实现者会按字面理解，写出不一致的代码。
- **Failure scenario**："路线失败"被实现成整张图失败，结果一条分支上的映射错误，阻断了所有分支。
- **Recommendation**：在术语表中固定以下用法：
  - Flow：图文档；
  - Path：从一个输入到一个输出的路径；
  - Target：即 Connection；
  - Delivery：一条投递记录。
- **V1 impact**：只改文档。

**P2-16 Modbus 库的默认值不适合现场　②**
- **Finding**：§2.3 默认选用的 NModbus，它的默认值会导致读取挂起和线程池被占用。
- **Evidence**（NModbus@d96e770，即 v3.0.83，已验证）：
  - `*Async` 方法不接受 CancellationToken，内部是用 `Task.Run` 包起来的同步 I/O（`NModbus/Device/ModbusMaster.cs:517-552`）；
  - ReadTimeout 和 WriteTimeout 直接传给 NetworkStream（`IO/TcpClientAdapter.cs:25-34`），默认值是无限；
  - 默认重试 3 次，每次间隔 250 毫秒（`Modbus.cs:15,18`）。
- **Why it matters**：§7.4 第 5 步的停止超时，依赖读取能够被及时打断。
- **Failure scenario**：
  - 不显式设置超时，遇到半开连接时读取会永久挂起，停止和应用配置只能靠重启进程来解决。
  - 默认的重试，让一次失败的读取耗时约"4 × 超时 + 0.75 秒"。
  - 每个挂起的读取占用一个线程池线程。大量设备同时离线时，会造成线程池饥饿，拖慢整个进程，包括管理界面。
- **Recommendation**：
  - T0 显式设置读写超时；库内的重试设为 0 或 1，重试交给调度器负责。
  - 每个 Modbus 连接的循环，跑在专用的长任务线程上（`TaskCreationOptions.LongRunning`）。
  - 停止时，通过释放 TcpClient 来打断阻塞中的读取。
  - FluentModbus（MIT 许可，真正的异步 I/O，支持 CancellationToken，最后一次代码提交在 2024-11）可以作为备选，在 T0 用同一组测试比较之后再定。
- **V1 impact**：T0 的一次比较，加一组配置。

**P2-17 控制与 TenonAdmin 的耦合面　②**
- **Finding**：TenonAdmin 迭代很快，前端又没有升级通道，耦合面越大，维护成本就越高。
- **Evidence**（TenonAdmin `8109dea`）：
  - 前端不发布 npm 包，使用方只能克隆后合并，或者一次性复制——文档原话是「没有升级通道」（`site/zh/guide/getting-started.md:150-157`）。
  - 2026-07-15 至 2026-09-27 之间发布了 18 次；1.0 之前，API 可能变化（`CHANGELOG.md:378`）。
  - 权限码由"HTTP 方法 + 小写的路由模板"生成（`PermissionCode.cs:14-15`）。
  - 数据范围未设置时不受限；后台服务没有身份（`IDataScopeContext.cs:6-7`；`SystemCurrentUser.cs:5-20`）。
- **Why it matters**：TenonEdge 对 TenonAdmin 的每一处依赖，都会在它升级时变成一个需要合并的地方。
- **Failure scenario**：
  - TenonAdmin 每发一个小版本，都要手工合并前端，并处理后端的破坏性变更。
  - 管理 API 的路由一改名，已经分配给角色的权限就失效了。
  - TenonEdge 的实体如果实现了 IOrgScoped，后台写入的行（CreateOrgId 为空）对受限用户不可见。
  - admin.db 随操作日志无限增长。
- **Recommendation**：
  - 锁定 TenonAdmin 的稳定版（当前是 0.6.0；0.7 还是预览版）。
  - web 中 TenonEdge 的代码集中放在独立目录，并记录模板基线的提交号。
  - 管理 API 的路由一次定好。每个需要单独授权的操作——测试、预览、重试、清空、迁移、应用、回滚——都使用独立的方法和路由。
  - 除了只读的状态查询，一律使用 `[RolePermission]`，不使用 `[ActiveSession]`。
  - TenonEdge 的实体不实现 IOrgScoped。
  - 为操作日志增加保留期清理。
- **V1 impact**：T0 的接线约定，加一个清理任务。

**MQTT 输入的不同之处：**
- 第 2 步变成"共享客户端的接收回调"。
- 第 6 步的分组提交返回之后，才按到达顺序发送 PUBACK（P1-4）。
- 这样，上游的所有权与本地的所有权在同一时刻交接：提交之前归上游，提交之后归 TenonEdge。

**HTTP 拉取的不同之处：**
- 第 2 步变成"每个输入一个拉取循环，请求不叠加"。
- 1 MiB 的大小上限在解析之前检查；JSON 的深度在解析过程中限制（`JsonReaderOptions.MaxDepth`）。

## 6. Crash & Recovery Analysis

| 崩溃点 | 崩溃时的状态 | 重启之后 | 丢失 / 重复 | 设计要求 |
|---|---|---|---|---|
| receive：Modbus 读取到一半 | 内存里还没有消息 | 下一个周期重新读取 | 丢一个采样点，对采样语义可以接受 | 无 |
| receive：MQTT 已确认，还没写入通道 | 消息只在内存里 | 已确认的消息，Broker 不会重投 | **丢失**（at-most-once） | 采用 P1-4 的"入库后确认" |

| transform / render | 在内存里 | — | 同上面两行 | 无 |
| persist：COMMIT 返回之前 | SQLite 在恢复时回滚 | 队列里没有这批记录 | 同 receive | 无（SQLite 保证写者崩溃不会破坏数据库） |

| ack：已收到 ACK，删除还没提交 | 同上 | 同上 | 重复，窗口不超过一个提交间隔 | 写进文档 |
| delete：已提交 | 完成 | — | — | — |
| apply：指针已切换，启动还没完成 | 按设计文档：指向新快照 | 按设计文档：加载新快照；如果新快照会导致崩溃，就陷入循环 | 崩溃循环 | P1-2：pendingRevision，启动时回退 |
| cleanup：清理过期记录 | 在事务中进行 | 原子完成 | 无 | 时钟跳变保护（P1-5） |
| 队列库损坏 | — | 无法打开 | 待发数据丢失 | 把损坏的文件移到一旁，新建队列库，记录丢失计数并告警。前提是按 P0-3 分成两个文件，这样配置库不受影响 |
| 配置库损坏 | — | 运行时无法加载 | — | 不启动运行时，保留管理界面用于恢复；不得静默清空（§7.4 第 6 步） |
| 密钥丢失 | — | 凭证无法解密 | — | 按 P1-2 的"启动时按单元降级"：只停用受影响的连接，提示重新录入凭证（P1-10） |
| 磁盘写满 | 写入失败 | — | 新数据计为"无法入库" | P1-12 的余量阈值 |
| SIGTERM 后 10 秒被 SIGKILL | 写者手里还没提交的那一批 | — | 丢失这一批 | P1-7：停机顺序与宽限期对齐 |

## 7. Scenario Walkthroughs

### S1　10 台 Modbus 设备，每台 100 个点，5 秒采集一次

- **负载**：
  - 每台设备一个采集组，合计每秒 2 条消息。每条约 100 个值，JSON 大小约 3–6 KB；quality 采用稀疏表示时可以减半。
  - 3 个目标时，每秒 6 次插入、6 次删除，SQLite 的写入压力可以忽略。
- **采集**：
  - 100 个点通常需要 2–10 次读请求，取决于地址是否连续，以及单次最多读取 125 个寄存器的限制。
  - 设备各有独立的 IP 时，并行采集，没有压力。
  - 10 台设备都挂在同一个 RTU 串口服务器（同一个 host:port）上时，情况不同：
    - 假设多数点是 32 位类型，每台约 200 个寄存器，10 台合计约 2,000 个寄存器，分 30 次读取；
    - 按 9600 波特率、RTU 每字符 11 位计算，请求加响应的线路传输时间约为 5 秒；
    - 再加上 3.5 字符的帧间隔和从站的响应时间，**会超过 5 秒的周期**；
    - 因此必须有 overrun 策略（P2-12），或者降低采集频率、提高波特率。
- **一台设备离线**：这台设备所在的连接每个周期都会超时。按 P2-12 快速失败，才不会拖慢共用这个连接的其他设备。
- **缓存**：
  - 单输出的上限是「最多 10,000 条或 64 MiB，先达到者生效」。按每条约 5.5 KB 计算，64 MiB 可以容纳约 1.2 万条，所以先触发的是 10,000 条的限制：10,000 ÷ 2 ≈ 5,000 秒，**约 1.4 小时**。
  - 只调高条数上限，也只能撑到 64 MiB，约 1.7 小时。
  - 要缓冲 12 小时，每个输出需要约 86,400 条、约 475 MB。这要求同时调高单输出的条数上限、单输出的 64 MiB 上限，以及 256 MiB 的全局上限。三个目标同时离线 12 小时，大约需要 1.3 GiB。
- **画布**：见 P1-3。10 台设备放在一条路线里，恰好是 50 个节点。
- **结论**：功能上成立，但默认值只能覆盖一个多小时的断网。界面应当按当前的速率，显示"缓存可以覆盖的时长"。

### S2　一个 MQTT 输入 → 两个 MQTT 目标 + 一个 HTTP 目标；HTTP 离线 12 小时

- **扇出**：设输入速率为 r。每条消息在一个事务中生成 3 条投递。
- **隔离**：两个 MQTT 目标由各自独立的发送者处理，不受影响，满足 GW-13 和 AT-06。
- **HTTP 目标的退避**：
  - 在目标级退避（P0-2），大约每 60 秒用一条记录探测一次。
  - 如果改成按记录各自计时，发送者每一轮都要对多条记录各等一次 5 秒超时，等于持续冲击一个已经故障的目标。
- **配额**：
  - 按条数计算，10,000 ÷ r 秒后写满：r = 10 时约 17 分钟。如果单条报文较大，64 MiB 的上限可能先到。
  - 此后，这个目标的新记录被拒绝并计数；两个 MQTT 目标有各自的配额，不受影响。
- **恢复**：
  - 按 FIFO 先发送约 12 小时前的积压。净追平速率 = 发送速率 − r，只有发送速率大于 r 时才能追平。
  - 按 RTT 100 毫秒、在途数 1、r = 10 计算，发送速率恰好是每秒 10 条，积压**永远追不平**，这时需要调高在途上限（P1-6）。
  - 接收方会先看到旧数据，接着是约 11.7 小时的空洞，最后才是当前的数据。接收方如果把"最后到达的"当成"当前值"，在追平期间就会显示旧值。文档必须写明：应以 collectedAt 判断新旧（P1-6）。
- **重复**：边界上会出现重复——请求已经被处理，但响应丢失了。需要 Idempotency-Key（P2-11）。

### S3　目标已确认，SQLite 删除之前崩溃

- 记录仍处于待发状态，重启后被重发：
  - TenonIoT：平台返回 duplicate，网关视为 Ack 后删除，平台上只有一份数据（AT-11）。
  - 通用 MQTT 目标：订阅者会收到两次，需要报文里带有 messageId 才能去重。
- **结论**：at-least-once。分组删除会把重复窗口放大到一个提交间隔，这一点需要写进文档。

### S4　SQLite 所在的磁盘写满

- 插入失败 → 整批回滚 → 计为"无法入库"。内存有界，满足 §8.2 流程后的最后一条。
- 删除同样需要写入，也可能失败 → 已确认的记录删不掉 → 重启后被重发。
- TenonAdmin 的会话存在数据库里，刷新令牌的轮换和每个已认证的写请求（写 `sys_op_log`）都要写库。所以，即使队列已按 P0-3 分成独立的文件，只要 admin.db 在同一块磁盘上，登录续期和所有管理操作都会失败，管理员无法进入界面查看故障。
- **结论**：没有 P1-12 的余量阈值，AT-12 无法可靠地通过。

### S5　应用了一份错误的配置，新运行时部分启动失败

- **静态错误**（环、缺少引用、未知节点、字段错误）：在校验阶段就被拒绝，有效配置保持不变，满足 AT-13。
- **连接不上**：属于降级。保留新快照，持续重连。
- **结构性失败**（凭证解密失败、适配器构建异常）：
  - 按 P1-2 的"应用时全有或全无"，整体回滚到上一版快照。
  - 即使 9 个输入已经启动、只有 1 个失败，也要整体回滚，保证有效配置始终是一个一致的整体。
  - 上一版也失败时，进入 `RuntimeFailed` 状态。
- **启动过程中进程崩溃**：按设计文档当前的写法，会陷入崩溃循环，需要 P1-2 的 pendingRevision。

### S6　运行期间修改输出服务器，旧投递还没有发送完

- 按 §8.3 阻止应用。但如果检查放在第 2 步的校验中，在校验和停止输入之间仍会产生新记录。所以真正的保证，只能来自发送时的指纹校验（P2-1）。
- 旧服务器已经永久下线时，用户只能清空、丢掉数据，所以需要"迁移到新目标"这个操作（P2-1）。
- 如果凭证轮换是通过"新建凭证并修改引用"来完成的，而记录里保存的是凭证引用，旧记录就会带着已吊销的凭证去发送（P2-2）。

### S7　MQTT 输入持续高速发送，输出明显更慢

- **慢目标**：队列以"输入速率 − 发送速率"的速度增长，写满配额之后开始拒绝并计数；快目标照常发送。持久化队列把输入和输出解耦了，所以真正可能成为瓶颈的只有单写者。
- **写者也跟不上时**：通道写满后，QoS 1 延迟确认，让 Broker 承担背压；QoS 0 丢弃并计数。
- **关键在于回调绝不能等待**：MQTTnet 在回调之前有一个无界的队列。回调一旦变慢，积压就转移到库的内部，而不在我们的有界通道里。QoS 1 时，这部分积压还受 Broker 在途窗口的约束；QoS 0 完全没有约束，最终导致 OOM（P1-7）。
- **结论**：只要落实 P1-4 和 P1-7，内存就是有界的，丢失也都是可见的。

### S8　某个适配器出现永久性异常

- **输入适配器**：
  - supervisor 捕获异常，按退避重启（例如从 1 秒到 5 分钟），状态置为 error，并保存最后一次错误。其他单元不受影响。
  - 没有 supervisor 时，默认的 StopHost 行为会让整个网关退出，再与 P1-2 叠加，形成崩溃循环。
- **输出适配器**：
  - 对所有记录都抛异常：按 transient 处理，在目标级退避。
  - 只是某条报文触发的缺陷：达到毒消息阈值后，这一条被移入失败区，队列继续前进（P0-2）。
- **转换缺陷**：只让这一条消息的这一条路径失败，并计数。

### S9　LoRaWAN 上游，一个 Application 下有 500 台设备

- **V1 模型**：500 个 Device，加上 500 个 MQTT InputDefinition，每个订阅一个精确的主题。
- **连接**：必须共享一个客户端，订阅 500 个精确主题（P1-8）。否则就是 500 个 TCP 连接和 500 个 ClientId。
- **上游 QoS**：ChirpStack 默认以 QoS 0 发布，必须改成 QoS 1。否则，TenonEdge 断线或应用配置期间的上行会直接丢失（P1-4）。
- **录入**：GW-03 的批量编辑覆盖设备、采集组（即 Modbus 输入）和点位，**不覆盖 MQTT/HTTP 输入**。500 个输入需要 CSV 批量导入，字段包括 deviceKey、名称、DevEUI 和主题。
- **画布**：
  - 允许扇入的话，是 500 个输入节点，远超默认的 50 节点上限，需要 G1 的"输入集合节点"。
  - 不允许扇入的话，是 1,500 个节点。
- **负载**：假设每台设备 10 分钟上报一次，合计每秒约 0.83 条，可以忽略。
- **状态**：按每台设备最后一次收到数据的时间来展示，不套用网关心跳（§21.4 的做法是对的）。
- **结论**：V1 在工程上能跑，但实际可维护的规模在几十台左右，文档应当写明这个上限。同时，V1 的数据模型不能挡住 G1：状态必须按 deviceKey 统计，连接必须共享。

### S10　未来增加 OPC UA

- **能自然扩展的部分**：以输入适配器的形式接入。订阅推送的形态与 MQTT 类似；节点 ID 可以放进 Point 的"协议地址"字符串里。
- **会给现有模型带来压力的部分**：
  1. 每个值都有自己的 SourceTimestamp，而一条消息只有一个 collectedAt；
  2. StatusCode 分为 Good、Uncertain、Bad 三类，quality 需要 uncertain 这个取值；
  3. 需要应用实例证书和受信任列表，Credential 需要证书类型（P2-9）；
  4. 节点浏览需要自定义的界面面板；
  5. 节点 ID 应当以 `nsu=` 的形式存储，因为命名空间的索引在服务器重启后可能变化。
- **许可**：OPC UA 协议栈的许可需要按 §17 审查（**待验证**）。
- **结论**：只要 V1 按 P2-3 和 P2-9 预留好位置，就不需要改动运行时。

## 8. 专题评审

### 8.1 Message Model 与"一输入一设备"

统一消息模型能表达三类数据：
- Modbus 点位：values 加上每个点的 quality；
- MQTT/HTTP 的 JSON：payload 树；
- LoRaWAN 的应用 JSON：payload 树加上 DevEUI 绑定。

需要补充的，只有 P1-5 和 P2-3 列出的几项。

输出字段的 schema 有三个可能的来源：Modbus 点位、映射节点、InputDefinition 的「字段描述」（§10.2）。
- §6.4 规定「来源合法 JSON 已经符合输出格式时，可以直接转发，不能强制增加映射节点」，所以映射节点不是必需的。
- 但 output.tenon 同步设备时需要显式的字段 schema。三个来源一个都没有时，就无法同步到平台。

| | 保持"一输入一设备"（V1） | 支持动态设备分流 |
|---|---|---|
| 身份 | 静态绑定，配置时就能校验 | 运行时从 topic 或 payload 中提取，需要一张绑定表 |
| 未知设备 | 不存在：精确主题只会收到已登记设备的数据 | 需要策略：丢弃并计数，或者放进待审批列表。ThingsBoard 网关在正则不匹配时，把表达式文本本身当成了设备名（本文 8.10） |
| 状态与诊断 | 输入的状态就是设备的状态 | 每个输入内部，要维护每台设备各自的状态 |
| 数组报文 | 不支持 | 一条消息拆成 N 条，每条需要自己的 ID，还要处理部分失败 |
| 平台同步 | 显式选择 | 发现新设备后，还要走同步和审批 |
| 串数据风险 | 最低 | 提取规则一旦写错，数据就会进错设备 |
| 工作量 | 已包含在 V1 中 | 绑定表 + 提取器 + 未知设备策略，大约 1–2 周；数组拆分另算 |

**结论**：V1 保持这条约束，同时为 G1 预留两点：
- 所有下游状态，按消息自带的 deviceKey 统计，不按 inputId；
- 连接可以共享。

G1 应优先实现"输入集合节点 + 输入批量导入"。它不破坏这条约束，就能解决 500 台设备的规模问题。只有当上游只提供共用主题或数组报文时，才需要做真正的动态分流。

### 8.2 Route / Revision 模型

```text
Draft（可变，带版本号，可多人编辑）
  └─ Validate（纯函数：图规则、引用、字段、权限、出站白名单）
      └─ Compile → Revision N（不可变；包含非秘密快照、内容哈希、schemaVersion）
          └─ pending = N ─ 停旧输入 ─ 启动新计划 ─ 确认 ─▶ effective = N，previous = 旧的 effective
                                        └─ 失败 ─▶ 回到 effective（最后一次确认可用的配置）
Rollback = 以 previous 为目标，重新走一遍"停旧 → 启动 → 确认"
```

- **概念对应**：
  - Route Definition：草稿中的 Flow 文档；
  - Route Revision：编译进快照中的内容；
  - Active Revision：effective；
  - Apply 和 Rollback 走同一条流水线。
- **应用粒度**：全局一次性应用、先停后启，保持文档的选择。是否细化为"只重启有变化的输入"，见本文 11，Q14；IoTEdge 和 Node-RED 都只重启变化的部分（本文 8.10）。
- **在途的内存消息**：停止输入之后，先排空通道，再切换计划，旧计划下产生的消息不会交给新计划处理。已入库的投递记录不受影响，这与 §7.4 末段一致。

### 8.3 Delivery Queue

**扇出：每个目标一行，保存已渲染的报文（反规范化），不采用"一条消息 + N 个引用"。** 理由：
1. 每个目标的报文在渲染之后本来就不同：topic、格式、映射结果都不一样；
2. 每个目标的配额和隔离可以精确计算，一个离线的目标只消耗自己的配额；
3. 删除就是按行删除，不需要引用计数，也不需要垃圾回收；
4. 崩溃后的一致性很简单：N 行在同一个事务里插入。

共享存储方案的代价，在参考项目里都有实例（本文 8.10）：
- Fledge：共享 readings 表 + 每个北向一个位置 + 清理策略；
- Azure IoT Edge：单一消息存储 + 每个端点的检查点 + TTL。

两者都出现了保留策略互相牵制的问题；Azure IoT Edge 的代码注释还写明没有使用事务。反规范化的代价是：报文相同时，存储量乘以 N。但总量受配额约束，在边缘规模下可以接受。

**接管边界**：包含该记录的分组提交返回的那一刻（且 `synchronous=FULL`）。对采用"入库后确认"的 MQTT QoS 1 输入来说，这同时也是向上游确认的时刻。

**重试是否完整：**

| 项 | 文档 | 缺口 |
|---|---|---|
| 指数退避 | 有（§8.4：最长 60 秒，「不紧密循环」） | 按目标还是按记录，不明确（P0-2） |
| 抖动 | 有 | — |
| Retry-After | 429 时遵守「合理的 Retry-After」 | 需要设上限；503 的 Retry-After 也应遵守 |
| 永久失败 | 确定性 4xx 停止重试 | 目标级和报文级不分（P0-2） |
| 人工重试 | 有 | 重置尝试次数；权限；批量操作 |
| 失败区 / 死信 | 只写了「显示失败」 | 独立配额、保留期（P0-2） |
| 毒消息 / 最大尝试次数 | 无 | P0-2 |
| 过期 | 24 小时，并计数 | 时钟跳变（P1-5）；计数需要持久化 |
| 暂停 / 熔断 | 无 | P0-2 |

**目标变更（§8.3）：**
- 这条约束是合理的，确实能显著简化首版：不需要为旧目标保留客户端，也不需要按记录路由连接。
- 它不算过严，只有一个死角——旧服务器已经下线。用 P2-1 的显式迁移操作就能解决，实现只需要一条 UPDATE 和一条审计记录。
- 不建议放开成"允许修改、旧记录继续发往旧地址"：那需要为每个历史目标保留连接和凭证，复杂度明显更高。

### 8.4 SQLite

**适用性：**
- **配置存储、加密后的凭证、revision 快照**：完全合适。写入频率低，事务一致，单文件备份方便。
- **投递队列**：满足下列条件时合适：
  - 单写者加分组提交；
  - WAL + `synchronous=FULL`；
  - 总量有界；
  - 使用独立的文件。

| 主题 | 建议 |
|---|---|
| WAL | 两个库都开启。读写可以并发，但只能有一个写者 |
| 事务 | 写者按批提交；读连接只开短事务。官方说明：只要始终有活动的读者，WAL "will grow without bound"，`journal_size_limit` 只能在事后截断（sqlite.org/wal.html §6） |
| 读者 / 写者 | 管理 API 对队列只读；所有修改都通过写者 |
| 队列扫描与索引 | 用 `seq INTEGER PRIMARY KEY` 表示 FIFO 顺序；建立索引 `(target_id, status, seq)` 和 `(created_at)`；deliveryId 单独存一列 |
| 清理 | 过期和删除都由写者分批执行。删除后的空闲页会被复用，但不会还给操作系统（sqlite.org/faq.html Q12）；文件大小停在历史最高水位，而这个水位受配额约束 |
| VACUUM | 不在热路径上做。VACUUM 最多需要原库两倍的空闲空间（sqlite.org/lang_vacuum.html），磁盘将满时尤其危险。需要回收空间的话，在建库时就设置 `auto_vacuum=INCREMENTAL`（事后再切换，需要新建库或做一次 VACUUM），并在空闲时执行 `incremental_vacuum` |
| 磁盘写满 | 见 P1-12 的余量阈值；遇到 SQLITE_FULL 之后，显式执行 ROLLBACK |
| 损坏 | 配置库在启动时执行 `quick_check`；队列库损坏时，把文件移到一旁并新建，计数告警；配置库损坏时，不启动运行时 |
| 分文件 | TenonAdmin 的 `admin.db`（内核表、TenonEdge 配置、快照、NodeId、凭证密文）与 `queue.db`（投递、计数）分开。好处：写入争用隔离，损坏的影响范围隔离，备份策略也可以不同——配置必须备份，队列通常不需要。TenonAdmin 的库没有任何 PRAGMA，空闲时约每 10 秒写 4 次（本文 8.5），这更说明两者不应共用一个文件（P0-3） |
| 备份 | 用 Online Backup API 或 `VACUUM INTO` 生成一致的副本，再连同密钥打成一个归档。注意，Microsoft.Data.Sqlite 的 `BackupDatabase` 在备份期间会阻止其他连接写入（Microsoft 文档）：对 admin.db 可以接受，对 queue.db 应当避免在线备份。恢复流程由 AT-19 验证 |
| 升级与迁移 | 配置库做版本化迁移，快照使用升级器（P2-8）；队列库的 schema 带版本号；**永远不对已入库的报文重新渲染** |

**SQLite 什么时候会成为限制**：这里不给虚构的数字，只列出触发条件，具体数值由 HW-06 实测。
1. 持续的"输入速率 × 扇出"，超过了单写者在目标存储上能承受的提交速率。在 eMMC/SD 上，fsync 的延迟是决定因素。
2. 积压达到 GB 级，清理、备份和磁盘预留的时间与空间成本都会上升。
3. 需要多个进程同时写入（HA、多实例）。这在本产品的范围之外。
4. 管理界面对大队列使用 OFFSET 分页。应改用键集分页。

即便真的到了那一步，下一步也应当先实测，而不是换成外部的消息系统。

### 8.7 LoRa / LoRaWAN

- **接入路线**："传感器 → 无线网关或网络服务器 → MQTT/HTTP/Modbus → TenonEdge"是正确的。在网关里自己实现 LoRaWAN，意味着要处理射频、入网、密钥和区域参数，完全超出了产品范围。
- **身份**：DevEUI 加上应用范围，映射为 deviceKey；接收网关的 ID 不等于设备（§21.3 第 5 条）。这部分是正确的。
- **时间**：需要区分四种时间：
  - 传感器采样时间：只有报文里明确给出时才有；
  - 上游事件时间：即 ChirpStack 的 `time`，实际上是无线接收时间（见下）；
  - 网络服务器接收时间；
  - 网关接收时间：即 TenonEdge 的 receivedAt。

  ChirpStack 的 `time` 按下面的顺序取值：任一接收记录的 GPS 时间；偏差在 30 秒以内的网关时间；否则，取网络服务器组装事件时的当前时间（chirpstack@3237e30:`chirpstack/src/uplink/helpers.rs:56-91`）。所以它只能标为 `timeSource=upstream`，不能当作采样时间。§21.4 的认识是对的，但缺少承载时间来源的字段，平台无法区分这几种时间（P1-5）。
- **去重**：
  - ChirpStack 在 200 毫秒的窗口内合并多个网关的接收，并为每个合并后的上行生成一个随机的 `deduplicationId`（`uplink/mod.rs:180-222`）。
  - 帧计数重传或重置的上行，不会产生 up 事件（`uplink/data.rs:487-543`）。
  - 因此，`deduplicationId` 适合识别 MQTT 层面的重投：同一事件被重投时，ID 不变。`(devEui, fCnt)` 只能在一次入网会话之内判断语义上的重复，因为重新入网后 fCnt 会归零。
  - 可以提供一个可选配置——"上游事件 ID 的 JSON Pointer"——用它为每个目标派生 deliveryId，让平台的幂等覆盖上游的重投。这一项属于 ③，不列入 V1 的必做范围。
- **QoS**：ChirpStack 的 MQTT 集成默认以 QoS 0 发布，retain 恒为 false（`integration/mqtt.rs:77-82,281`）。接入说明必须要求改为 QoS 1。否则，P1-4 的持久会话对 LoRa 数据无效：TenonEdge 断线或应用配置期间的上行会直接丢失。
- **折中评价**："一台设备一个精确的 MQTT 输入"是合理的 V1 折中，但有两个前提：连接共享（P1-8），以及文档写明规模上限（S9）。
- **结论**：没有为 LoRa 单独设计一套运行时，这一点是对的；§21 也没有破坏 §0 的约束。

### 8.8 Node-RED 决策

| 成本 / 能力 | 自有运行时（当前方案） | 嵌入 Node-RED 运行时 |
|---|---|---|
| 进程与技术栈 | 一个 .NET 进程 | .NET 和 Node.js 两个运行时，两套生命周期和升级流程 |
| 可靠转发 | 自有的 SQLite 队列，语义由自己掌握 | Node-RED 的消息只在内存中；要持久化，只能自己写 JS 节点，或者桥接回 .NET。核心价值要么重写，要么跨进程 |
| 认证与权限 | 直接使用 TenonAdmin | 需要在 adminAuth 与 TenonAdmin 之间做桥接；编辑器、Admin API 和 httpNode 要分别保护（§20.3 已经列出） |
| 约束符合度 | 天然满足"不运行脚本"（§0 第 5 条） | function 节点可以执行任意 JS，与 §0 第 5 条冲突，需要禁用和裁剪 |
| 画布与调试 | 需要自建（基于 Vue Flow），但节点类型只有 8 种 | 成熟 |
| 协议节点 | 自研 Modbus / MQTT 适配器 | 社区节点，质量参差不齐 |
| 配置格式 | 自有，由 schemaVersion 控制 | flows.json 加一份加密的凭证文件，格式由 Node-RED 决定 |

**结论：**
- Node-RED 能省下来的，只有画布和调试界面这一小块；而本产品的核心——可靠队列、身份、采集调度——它省不下来，甚至会削弱。首版不引入 Node-RED 的决定是正确的。
- 可以借鉴的具体机制有三个（本文 8.10）：配置节点共享连接并按引用计数（P1-8）；按修改的范围部署（Q14）；节点关闭超时。
- 对一个非目标来说，§20 的篇幅偏长，但对架构没有影响。

### 8.9 扩展性

| 未来能力 | 类型 | 说明 |
|---|---|---|
| Modbus RTU | 自然扩展 | 前提是 Connection 代表物理通道（串口），多个 UnitId 共用一个串行执行器（P1-8）；Docker 需要映射设备节点 |
| OPC UA | 自然扩展，但带来压力 | 见 S10：每个值的时间戳、uncertain、证书、浏览界面 |
| BACnet/IP | 自然扩展 | COV 属于推送；设备发现需要额外的界面；UDP 广播在容器中通常需要 host 网络 |
| TCP Client / 串口私有协议 | 针对具体设备写适配器，属于自然扩展；**"可配置的通用二进制协议"会突破模型** | 通用解码需要 DSL 或脚本，与 §0 第 5 条冲突 |
| HTTP 推送（Webhook）接收 | **轻微突破** | 输入适配器需要宿主提供入站端点，涉及调用方鉴权、端口暴露和背压。建议到时由 Host 提供统一的 `/ingest/{inputId}`，再转发给适配器，适配器本身不依赖 ASP.NET。收到数据后先入库、再返回 2xx，天然就是 at-least-once |
| Kafka 输出 | 自然扩展 | 生产者使用 acks=all 并开启幂等；用 deviceKey 作为分区键来保证顺序 |
| 数据库输出 | 自然扩展 | 用 messageId 做唯一键，`ON CONFLICT DO NOTHING` 即可做到 effectively-once；注意不要演变成 §0 第 6 条禁止的 SQL 功能 |
| 变化上报 / 死区（RBE） | **突破"纯转换"的契约** | 需要按 (input, field) 保存上一个值。到时放在输入侧（采集时判断），或者做一个专门的有状态过滤节点（③） |
| 写入 / 控制 / 下行 | **突破模型** | 模型是单向的，§0 第 9 条明确排除了这类功能 |

**结论**：对"接入 → 处理 → 输出"来说，三类扩展点（输入、转换、输出）已经足够。V1 真正需要补的只有三处：
- 适配器契约中的连接借用和一次读取；
- 凭证类型；
- quality 与时间戳的可演进性。

不需要万能的插件系统。

1. **把"确认"和"持久化"定义到代码层面**：真实的 PUBACK，真实的提交，超时就是失败。ThingsBoard 网关在这两点上都出过错。
2. **目标参数变了要能检测到，而且不删除积压**。EdgeX 和 Neuron 分别在这里出过错。
3. **每个目标都有硬上限**。EdgeX 和 Azure IoT Edge 实际上不限容量。
4. **队列要有"大积压 + 时钟/单位"一类的测试**。ThingsBoard 的指针缺陷和 TTL 缺陷，都只有在积压跨文件、时间单位不一致时才会暴露出来。

其余方面，TenonEdge 的原则性设计比这些参考项目更稳健：先持久化；每个目标一行；保存已渲染的报文；阻断目标变更；停止超时就中止。

### 8.11 .NET 结构

- **项目拆分**：
  - 五个项目已经足够，不需要为每个目录再拆出 Domain / Application / Infrastructure（§3.2 已经这样要求）。
  - 需要调整两点：存储放进 Runtime（P2-13）；`RuntimePlan` 作为 Abstractions 中唯一的配置契约（P1-11）。
  - Adapters 暂时保持一个程序集。是否按协议拆分，等出现第一个企业模块时再定（③）。
- **依赖方向**：方向本身是正确的，但要补一条硬约束：Runtime 不引用 TenonAdmin 的程序集，不使用它的 SqlSugar 作用域和用户上下文（P0-3、本文 8.5）。运行时的状态通过 Runtime 暴露的只读查询接口提供给 Host，由 Host 转成 API。
- **抽象**：
  - 需要的接口：`IInputAdapterFactory` / `IInputAdapter`、转换函数、`IOutputAdapterFactory`（Render）/ `ITargetSender`（Send，返回四类结果）、`IConnectionManager`、`ICredentialResolver`。
  - 不需要的：IDeliveryStore 替身接口（直接测试真实的 SQLite）、每个实体一个仓储接口、通用的表单引擎。
- **Runtime 的职责**：包括 supervisor、连接管理、调度、分发、转换、存储、发送、诊断状态和应用编排。它们构成一个内聚的核心，放在同一个程序集里并不过重。需要守住的，是那些**不能**进入 Runtime 的东西：HttpContext、用户身份、ORM 实体、权限判断。
- **生命周期**：由 supervisor 统一管理状态转换：`Created → Starting → Running(Connected | Degraded) → Stopping → Stopped | Faulted → Disposed`。Stop 必须等循环退出之后再释放资源——iotgateway 就在这里出过错。
- **DI**：
  - 每个节点类型用 keyed singleton 注册一个工厂，例如 `input.modbus`。
  - 模块通过 `services.AddTenonEdgeModbus()` 这类扩展方法装配。
  - 适配器实例由工厂按计划创建，不注册成 DI 单例。
- **HostedService**：只有一个 RuntimeHost。不要为每个输入注册一个 HostedService：运行时无法动态增删它们，异常也会直接冒泡到宿主。
- **取消与资源释放**：
  - 每个单元一个 CancellationTokenSource；StopAsync 带超时。
  - 对于不支持取消的同步 I/O，靠 socket 超时，再释放 TcpClient 来打断（P2-16）。
  - HTTP 为每个 Connection 创建一个 SocketsHttpHandler，以便设置 ConnectCallback、TLS 和 PooledConnectionLifetime；它的生命周期跟随 Connection。
- **可测试性**：
  - 转换是纯函数；
  - 存储用真实的 SQLite 临时文件；
  - 时间用 FakeTimeProvider；
  - Broker 用本地的 Mosquitto；
  - Modbus 用进程内的从站模拟器；
  - 平台用 TestPlatform。

### 合入 v1.6 时的更正

合入后做了两轮独立核对，发现本文有三处建议照字面实现会出错。v1.6 已更正；本文正文保持原样，以设计文档为准。

- **P1-4、P1-7：QoS 1 消息遇到通道满。** 本文建议回调永不等待、通道满时 QoS 1 不确认。但这条消息既没有入库，也没有确认：MQTT 3.1.1 只保证在重连时重投，而按到达顺序确认又会让后续消息的确认全部卡在它后面。v1.6 改为：
  - 通道使用等待模式；QoS 0 写不进就丢弃并计数。
  - QoS 1 在回调中等待空位，最长 5 秒。超时按存储写入失败处理：不确认，断开连接，由 Broker 重投。等待必须有上限，因为 MQTTnet 依次执行回调，等待期间同一客户端的后续消息（包括不受在途窗口限制的 QoS 0）都会积压在库内的无界队列里。
  - 凡是不产生任何投递记录的消息，计数后即可确认，不等待提交，但仍按到达顺序确认。P1-4 的“计数后立即确认”随之改写。
- **P0-2：毒消息判定。** 本文的条件是“同一目标的其他请求能成功”，但退避期间只用队头探测，通用 HTTP 的在途上限又是 1，这个条件观察不到。v1.6 改为：
  - 只有目标已给出响应的非临时失败（502、503、504 以外的 5xx，以及无法识别的响应）和本地未知异常，计入失败次数；连接失败、超时、408、429 与 502、503、504 只触发退避。
  - 队头达到阈值后，探测其后第一条未达阈值的记录。它成功，就立即重试队头；队头仍出现计入的失败，才移入失败区。其后没有未达阈值的记录时，继续用队头探测，只计数、不移入失败区。
  - 核对时用一个规则模拟脚本检查过这条规则（只检查规则逻辑，不是实现测试）：连续多条毒消息能逐条识别；断网、429/503 退避和全面 5xx 故障恢复后都没有误判。代价是每次都超时的记录识别不了，会阻塞目标直到过期，所以诊断页显示队头阻塞时长。
- **P0-2：未列出的状态码。** 本文的四类结果只列出具体状态码，v1.5 的“其他确定性 4xx”在其中没有归属。v1.6 规定：重定向 3xx 和未列出的 4xx 默认按 SuspendTarget 处理，避免把 404 这类目标级错误当作报文级错误，把整个队列移进失败区。

核对时还补入或调整了以下几项：

- C9、C10 两处文档澄清。
- P1-5：退避状态改为按目标保存在内存中，重启后先用一条记录探测，不再持久化下次重试时间。这一项调整了本文的原建议（持久化，并在重启后重新计算）。
- P1-6：发布结果的判定。未连接、连接中断和超时以异常出现；MQTT 5 的原因码放在返回结果中。
- P1-9：预览限制长度。
- P1-12：已确认、未删除的记录在内存中标记。
- 失败区满时怎么办，P0-2 没有规定：新的失败记录不再保留，只计数；失败区按目标和全局分别设上限。
- 本文 8.6 的权限矩阵。“应用、回滚”一格原为“可配置”；为符合固定三种角色，定为配置人员可执行，并记审计（2026-09-29 经用户确认）。另补入“查看审计记录”、用户与角色管理（均仅限管理员）和“修改自己的密码”。

### 补充决定（2026-09-29）

- 配置人员可以执行应用与回滚，每次记审计。这确认了合入时的暂定写法。
- 同一目标连续 20 条报文被拒（RejectMessage）、其间没有成功时，按 SuspendTarget 暂停该目标。这是为了避免接收方整体拒收时，整批数据进入失败区，失败区满后被丢弃。
