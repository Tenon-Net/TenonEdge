# 损坏有效快照的受限恢复（T3-06）

维护者于2026-10-14确认的边界：有效快照损坏时，仅管理员可预检并二次确认恢复到完整历史版本。此功能不是备份恢复，不修复损坏数据库文件，也不把损坏快照解释为空配置。普通回滚与人工重试的保护保持不变。

## 使用步骤

1. `/configuration` 显示运行失败、有效快照无效，普通应用清单与重试不能绕过故障。管理界面仍可使用，`/readyz` 返回503。
2. 管理员在配置历史中选择一个**曾生效、校验通过且包含完整草稿**的版本，展开检查历史草稿和运行计划；只有符合条件的历史详情显示“损坏有效快照恢复”。种子格式等不含完整草稿的旧版本、未生效版本或损坏历史均不能作为恢复目标。
3. 点击“预检恢复到此历史版本”。服务端捕获当前真实草稿版本；普通草稿比较因有效快照损坏而失败，不妨碍该专用预检。预检不保存草稿、不分配运行版本、不启动输入、不联网或向外发送。
4. 核对目标版本、当前接收方身份、待发/失败记录核对结果及单元构建问题。任一阻断都禁止确认；不自动清空、迁移或改写记录。
5. 分别勾选恢复确认与**保留全部草稿**确认。执行会生成新的有效版本，并保留原草稿的版本、全部对象和编辑标记，包括冻结后另存的修改。不会将草稿顺便应用，也不把草稿替换成历史内容。恢复后要再次核对未应用变更。
6. 返回202只表示后台接管。按操作编号或最近操作列表查看完成结果；响应丢失后不得自动重放。正常完成后运行按新版本激活；单元健康情况仍以诊断为准。

只读角色和配置人员不能调用恢复预检或确认，即使直接构造请求也会被拒绝。管理员会话或API Token还会在冻结与持久COMMIT事务内复核；失效、降权或吊销不能借已获得的预检越权提交。

## 安全与数据边界

- 恢复只在“运行失败”且没有已激活运行计划时准入，与普通应用、回滚、重试、队列管理写入及停机共享原协调者，不创建第二套运行时。一个仍在运行、仅持久文件被外部修改的进程不能从此入口直接覆盖其活跃计划。
- 预检确认绑定当前有效版本、**实际损坏内容**的校验标记、完整目标快照哈希、当前草稿版本及当前凭证版本/输出身份。有效快照被修复或改变、目标被改动/清理、凭证变化或冻结前草稿另存均要求重新预检。损坏的存储哈希本身不是可信依据。
- 使用当前凭证，不恢复历史秘密；引用必须存在、接收方匹配、所需秘密可解密。HTTP历史原本匿名但现在有凭证的，也必须核对当前凭证，而不是默默忽略或向别处转发。
- 原有效快照不可解析，不能用它作目标变更比较。因此逐条流式检查待发和失败记录的**冻结指纹及原Topic/路径**，不读取报文正文。MQTT主题按该条设备key展开；HTTP按冻结相对路径核对。同一连接有格式化路线时，额外的队列接续单元不能绕过路径检查；只有纯队列接续目标才按原规则保留冻结路径。身份或地址不符、目标缺失均阻止恢复。
- 返回真实核对/阻断条数，最多列出100个阻断连接并标注是否还有其他连接；不把截断清单当全部。已隔离记录保持隔离，不因恢复自动放行或改变冻结内容。
- 恢复沿用准备、静默、持久提交、提交后激活流程。`runtime.snapshotRecovered` 审计、新有效指针及运行中标记同事务提交。新快照来源为 `recovery`，保留历史来源及损坏版本编号。审计失败时不切换有效版本；原损坏内容保留，不补造空快照。提交后的激活失败不自动恢复到损坏版本。
- 恢复过程中不会重写已冻结报文、投递编号、失败状态或人工暂停设置。正常激活后的发送、保留期清理和诊断仍按原规则运行；“不改写记录”不是承诺阻止正常到期删除。
- config.db整体无法读取、没有完整可用历史、所需连接/秘密已删除或队列身份无法安全核对时，本入口不承诺可恢复。修复存储或完整备份恢复仍按T5范围，不提供强制绕过按钮。

## 持久提交与进程中断

恢复与普通应用使用同一个持久 COMMIT 边界，不以上层方法返回为准：

- **COMMIT 前**：即使事务内已写入新指针，强杀后 SQLite 撤销未提交事务。重启仍报告原有效快照损坏、就绪503；不启动输入或输出、不自动恢复。已冻结的恢复版本标为“未生效：进程中断”。管理员重新预检并确认才生成下一个新版本，不复用中断版本号。
- **COMMIT 成功后**：即使上层恢复方法尚未返回，重启加载新的完整有效版本；恢复审计和运行中标记已同事务持久化，不再自动创建恢复操作。正常加载后按原规则处理冻结队列，并采集恢复版本的数据，而非未应用草稿。
- 两侧都保留未应用草稿、草稿版本和编辑标记。重启后内存中的操作编号可能返回404，应核对持久历史、审计与运行状态，不能因此自动重放确认。

本地 Linux 已以原 SQL/连接回调固定两个窗口，分别执行真实 SIGKILL 和正常放行对照，并由未经注入的产品 Host 重启核对 HTTP 冻结报文、编号、FIFO及新采样。证据见实施状态§2.239；这是软件故障注入，不是物理断电验证。

## API

- `POST /api/edge-admin/v1/configuration/versions/{revision}/recovery-review`
  - 必须显式包含 `expectedVersion`；可传 `null`，由服务端读取当前草稿版本并绑定至结果；也可提交已知版本作并发检查。
  - 返回目标内容哈希、确认哈希、当前有效/历史版本、草稿版本、非秘密输出身份、队列核对统计、准备问题和 `canConfirm`。
- `POST /api/edge-admin/v1/configuration/versions/{revision}/recover`
  - 提交预检的 `expectedVersion`、`confirmationHash`、`confirmed:true`、`preserveDraftConfirmed:true`；可附最多1000字符说明。
  - 服务端重新预检后才交原协调者，后台冻结/提交仍复核。202返回原配置操作结构；查询使用已有 `/configuration/operations/{id}`。

两接口均为管理员权限、no-store、共享预览预算和8KiB请求体限制；Cookie请求须CSRF，API Token仍须HTTPS。客户端不能传入任意计划、指纹、账户或运行指针。不以页面隐藏代替后端授权。

实际测试范围统一见 `implementation-status.md`。正常重启、测试故障与真实强杀/实物断电是不同证据，不能互相替代。
