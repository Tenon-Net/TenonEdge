- 决策编号：UP-D01；功能编号：GW-27。
- 确认日期：2026-09-29。
- 基线：总设计 V1.6、功能需求、后端 BE-D01 与前端 FE-D01；整理时仓库提交为 `e47cf1f08804537336104faaa7746ef527969c7f`。
- 状态：已确认规划，列为 G1 优先项；尚未实现、构建或验证。当前任务只写文档，不授权立即开发升级页面、执行器或更新服务。
- 目标：在支持的部署环境中，管理员通过网关网页完成获取升级包、检查、确认安装和查看结果，正常操作不需要每次登录主机执行命令。升级仍由管理员主动发起，不自动安装或自动定时重启。

## 2. 网页入口与用户操作

入口为“系统设置 → 软件升级”，与配置版本历史分开。升级应用程序不是回滚配置快照。未实现 GW-27 的版本不放置伪可用的升级按钮。

页面显示当前程序版本、构建标识、OS/架构、部署类型、执行器能力、最近升级结果及操作历史。所有角色可查看已有的当前版本信息；检查更新、上传、下载、预检、安装、取消及查看升级日志仅管理员可操作，后端逐项授权。

| 操作 | 网页行为与规则 |
|---|---|
| 检查更新 | 管理员主动查询已配置的可信源，显示版本、更新说明、兼容性和检查时间；网络失败显示“无法检查”，不能显示“已是最新”。默认不周期联网、不自动下载 |
| 下载升级包 | 按已验证的发布清单下载指定包，显示大小和进度；不开放任意 URL 下载器。下载不等于安装；网络中断不停止正在运行的网关 |
| 上传升级包 | 浏览器选择本地签名升级包；断网现场也可用。传输完成后由服务端和执行器验证，不信任前端传来的校验成功标记。备份文件、普通 ZIP 或任意 DLL 不能当作升级包 |
| 升级预检 | 展示当前/目标版本、变更说明、停采影响、缓存情况、所需空间、配置与队列兼容性、执行器状态、恢复条件及阻塞原因；预检失败不能安装 |
| 确认升级 | 管理员重新验证本地身份并二次确认，确认内容绑定包摘要、目标版本和本次预检；服务端重新检查权限、包和运行状态，登记唯一任务后执行。HTTP 超时或重复点击不能再次启动同一任务 |
| 进度与重连 | 显示下载、校验、准备、备份、切换、重启验证和最终结果。主进程停止时显示“服务重启中，等待重新连接”，不虚构百分比；恢复后重新认证并按任务编号查询真实结果 |
| 取消 | 上传、下载或待确认阶段可取消并清理暂存包；任务进入停机与切换后，不提供强制取消或任意打断，由执行器完成或恢复到安全状态 |
| 升级历史 | 显示任务编号、发起人、源版本、目标版本、阶段、时间、结果、是否恢复及原因；提供脱敏日志查看。已失败的安装不会自动无限重试 |

正常流程：打开页面 → 检查并下载，或上传离线包 → 查看预检 → 确认 → 等待服务重连 → 查看新版本和升级结果。已有未保存的浏览器编辑须先保存到草稿或明确放弃；已有服务端草稿不会自动应用，须连同配置数据保留。

更新源地址、签名密钥和更新服务当前都尚未部署，不能将某个 GitHub Releases 地址写成已经可用的产品更新源。G1 可以使用静态签名发布清单和安装包托管，不要求先建设专门的升级服务器。

## 3. 部署方式与执行边界

| 环境 | 网页操作的实现边界 |
|---|---|
| Linux x64 原生安装 | G1 优先支持；安装包预置受限升级执行器和必要的服务管理配置，负责切换版本、重启与失败恢复；初次部署可能需要主机权限，之后正常升级通过网页完成 |
| 预装整机 | 使用同一原生升级机制，出厂配置执行器；必须验证实际机型、存储与断电恢复，不能仅凭软件测试声明整机支持 |
| Docker，未安装宿主机执行器 | 页面可以按可用能力显示版本、检查和获取相应包，但“安装”不可用，并显示外部部署方式；不把只能查看按钮的页面称为一键升级 |
| Docker，已安装受限宿主机执行器 | 验证后支持网页发起；由宿主机侧按固定部署描述、可信镜像摘要重建本网关容器，保留既有数据卷，不修改其他服务或 Broker |
| ARM64 或其他平台 | 仅在对应升级包、部署方式与恢复测试均通过后声明支持；平台不匹配时拒绝安装 |

网页/API 只负责授权、包接收、预检和任务交接。执行器必须独立于即将停止或替换的 Host 生命周期，不能依赖一个未受监督的 Task.Run，也不能指望已停止的进程继续报告进度或恢复自己。

- 不让网关 Web 进程以 root 运行来获取升级权限；不挂载 docker.sock、开放 Docker daemon API 或授予任意 sudo/命令执行能力给网关容器。
- 执行器仅接受固定操作、任务编号和已验证包标识；受限本地 IPC/任务目录按部署配置授权，不接受任意脚本、命令、安装路径或容器配置。正常用户输入不能变成 Shell 命令。
- 执行器在自己控制、不可被 Web 进程改写的暂存区域再次校验签名和摘要，防止验证后替换文件；按最小权限访问本网关的程序、数据和服务。
- 网页安装是可选部署能力，不改变未启用 GW-27 时默认单 .NET 服务的约束。不提前为它增加空工程或常驻微服务。
- 初期不支持执行器自升级；包声明的执行器最低版本不满足时，预检阻止并说明需要维护升级，不能临时绕过权限边界。

## 4. 升级包、可信源与安全校验

两种包来源共用同一套验证与安装机制：离线上传不放宽签名要求，联网下载也不能只依赖 HTTPS 或文件名。

发布清单须绑定产品、发行版、版本/构建标识、OS/架构、部署类型、最低可升级版本、执行器最低版本、config.db 与 queue.db 的 schema 兼容范围、快照格式、文件长度和摘要、密钥标识及签名元数据。网页显示的更新说明作为纯文本或经过净化的内容，不执行其中的 HTML/脚本。

采用成熟的标准签名格式和验证实现，可信根来自安装包或受控的维护流程，不能接受升级包随附的任意公钥作为信任依据；私钥不进入设备、前端或公开仓库。G1 开发前锁定签名格式、密钥轮换/撤销与离线校验方法，先做篡改包测试。借鉴 TUF 的签名、版本与过期检查原则，不宣称已实现 TUF 全套安全保证。

- 摘要用于完整性，签名与可信密钥用于来源校验；两者都校验。拒绝篡改、来源不明、错误架构、错误产品及未授权发行版的包。
- 默认只提供稳定渠道，预发布包必须明确选择且显示风险；不提供任意旧版本降级。拒绝回退到已记录的最低安全版本以下，恢复只适用第 6 节的受控条件。
- 密钥/发布元数据有版本和有效期规则，版本高水位独立于可恢复的业务数据库保存；时钟不可信、离线无法确认撤销或元数据过期时明确阻止或显示规定的待处理状态，不静默关闭验证。
- 更新请求使用 HTTPS、正常证书校验和既有建立连接时的出站校验；受信任内网更新源由管理员配置。默认不跟随重定向；确需下载域跳转时，须显式登记并逐跳校验，不转发认证头到其他主机，不把更新下载变成 SSRF 通道。
- 上传、下载和解包都有字节、时间、文件数、解压总量与磁盘预算；拒绝路径穿越、绝对路径、逃逸的链接和危险文件类型。按发布包实测确定上限，保持管理和数据库恢复所需磁盘余量。
- 升级临时文件不能占用 queue.db 的缓存配额，也不能侵占存储保护余量；当前任务和最近可恢复版本不得因普通缓存清理被删除。
- 管理端仍沿用既有 HTTP/HTTPS 决策、Cookie 防 CSRF 和权限规则；HTTP 操作持续提示会话和页面可被截获或篡改，推荐在 HTTPS/隔离管理网使用。包签名不等于 HTTP 管理链路安全，不把本次规划写成已消除该风险。

## 5. 任务状态、运行隔离与结果

一次只允许一个升级任务。任务由执行器持久化，浏览器断开不撤销已接管的操作；前端和接口层不得自动重放安装请求。任务日志与恢复标记放在独立受限目录，不随程序目录切换或 config.db 恢复而丢失；记录结果后补记产品审计，失败时保留脱敏证据。

任务状态按已完成的步骤落盘，原子更新包含文件及目录的持久化处理；重启后先核对真实程序版本、数据库和标记，再继续或恢复，不能只依据“上一次接口返回成功”。

| 阶段 | 行为 | 对运行的影响 |
|---|---|---|
| 获取与校验 | 上传/下载、签名与兼容性校验 | 原版本继续运行；失败只清理本次未完成暂存数据 |
| 已预检、待确认 | 展示影响和恢复条件 | 不自动应用草稿、不安装、不重启 |
| 准备维护 | 重新校验确认绑定的包和状态；取得升级维护锁，阻止新的配置应用、恢复、队列迁移及其他可变管理操作，已有操作须先完成或拒绝本次升级 | 读状态可继续；不能抢占正在进行的恢复或应用 |
| 静默与备份 | 按既有停止顺序停止输入、排空处理并提交队列，再停止发送、关闭数据库连接 | 有明确的采集/发送暂停；不用等待外部目标把所有积压发完；停止超时则中止，不启动第二实例 |
| 切换与验证 | 执行器备份完整升级检查点，切换程序或镜像，运行迁移及受限启动验证 | 暂不放行新输入和输出，也不接受会改变业务状态的管理写操作 |
| 提交成功 | 验证通过，持久化升级成功与版本状态，然后放行业务运行 | 新版本开始采集与发送；页面重连后显示最终结果 |
| 恢复或需维护 | 成功提交前失败，按第 6 节尝试恢复一次；仍失败则停止重试 | 不在损坏或不匹配的数据上继续运行；能恢复管理服务时显示原因，否则使用主机侧救援 |

升级包包含后端与匹配的前端构建产物，作为同一版本切换；浏览器重连检测到版本变化后提示刷新，不让旧前端继续提交不兼容的请求。

启动验证不仅检查进程存活，还检查目标版本/包摘要、数据库迁移与完整性、NodeId/configStoreId、有效配置、凭证解密、管理 API 和运行计划本地准备。验证时输入、输出保持关闭，避免回退前已产生新数据。外部设备或平台离线不是升级失败的唯一理由。验证超时与短稳定观察窗口在 G1 用目标硬件测定；观察必须有上限。

升级期间的启动恢复由一个执行器协调，现有配置启动保护不得同时执行第二套回滚；成功提交后再交回既有运行时监督。提交后的设备或网络故障按运行诊断处理，不因一次连接失败回退整个软件。

## 6. 数据保护与失败恢复

这里的“升级检查点”不同于 functional-spec §10.3 的日常配置备份，后者不含 queue.db。需要恢复程序版本的升级，必须在输入、发送和全部数据库连接停止后，保存 config.db、queue.db、密钥环、身份/本地秘密文件、部署描述与当前版本；处理 SQLite 的 WAL 等附属文件，使用一致的备份或受控离线复制，不复制正在写入的数据库。空间不足、备份校验失败或不能保证一致性时拒绝切换。

- 程序安装目录与持久数据目录分离，保留旧程序或镜像及其校验信息；不把升级解压到正在运行的目录。不更改设备身份，不清空发送队列、草稿或账号。
- 升级检查点用于同一实例、同一次任务的受控恢复，不作为跨网关导入；普通备份恢复仍按总设计 §10.4 执行。
- 成功提交前，新版本不得采集、发送、签发新会话或接受其他管理写入；校验成功后提升会话代次，要求页面重新登录。失败恢复也提升会话代次，防止旧会话复活；代次下限在任务记录中保存。API 令牌不因升级而被重新签发或恢复已吊销状态。
- 成功提交前出现迁移失败、无法启动、凭证解密失败或校验失败时，停止候选版本，恢复同一检查点对应的程序和全部数据，再校验并启动原版本；恢复动作可重复执行但只自动尝试一轮，不无限切换版本。
- config.db 与 queue.db 迁移都需要版本与兼容性说明；不能让旧二进制读取不兼容的新 schema。版本切换、迁移和检查点恢复没有天然的跨文件事务，执行器按阶段标记和幂等步骤完成中断恢复。
- 一旦成功提交并放行新版本，可能已产生新队列数据及外部投递，不允许自动覆盖回升级前检查点。后续问题使用兼容修复包或受控维护，不能承诺任意时刻一键降级、撤回外部数据或绝对零丢失。
- 断电后由服务管理器先运行恢复协调，再允许 Host 打开数据目录；排他锁保证不并存两个网关实例。检查点和原程序均保留到成功验证之后，执行器任务记录不随恢复覆盖。
- 主进程重启期间网页与 API 会暂时不可用；旧版本成功恢复后在网页展示失败原因。若执行器、系统或存储损坏导致新旧版本都不能启动，网页也无法救援，必须提供主机侧命令与售后处理说明，不能宣称所有故障都能从网页修复。

升级期间不要求 Broker 与网关一起停机或升级。轮询来源会缺少维护期间的采样；MQTT 补收仍受既有 QoS、会话、Broker 队列和持久化条件约束，沿用总设计 §8.5 的可靠性口径。

## 7. 开发衔接与边界

| 阶段 | 应做的事 |
|---|---|
| T0—T2 | 继续既定后端工程、数据目录、schema 版本、停止与恢复机制；知道程序与数据分离，不创建升级工程、接口、任务表或空抽象 |
| T3 | 按原计划实现网关前端；不因本规划提前生成不可用的升级页面或按钮 |
| T5 | 完成已有升级脚本、版本清单、备份恢复和发布文档；记录程序与持久数据位置、外部停止/启动方式。网页升级不计入首版已完成项 |
| G1 第一批 | 原生/已验证整机：离线上传、校验、预检、网页确认、受控执行、结果与失败恢复；先通过篡改包和逐阶段进程终止测试 |
| G1 第二批 | 联网检查与下载，复用第一批的安装入口；具备实际需求与受限执行器后再验证 Docker 网页安装，不把它作为原生能力的阻塞条件 |

管理 API 沿用 BE-D01 的分组 Minimal API、ProblemDetails 和 OpenAPI。具体端点、任务模型、IPC 及发布格式在 G1 实施时统一固化，不把本文提及的操作视为已经存在的 API。前端沿用 FE-D01 的查询/操作分离与错误处理，不引入新 UI 框架。

精确签名实现、执行器权限与服务管理配置、检查点格式、保留/空间上限和健康验证阈值须在 G1 原型中确定并留测试证据；不将这些 G1 工作变成进入 T0 的前置条件。UP-D01 仅确认路线图和上述边界，不代表依赖、机型或自动恢复已经验证。

## 8. 升级专项验收

当前以下项目全部未验证，在 `implementation-status.md` 建立后按 UP-AT 索引证据，不另造第二套实现状态系统。

| 编号 | 场景 | 通过标准 |
|---|---|---|
| UP-AT-01 | 网页离线上传并升级 | 在无公网、支持执行器的原生环境，仅通过网页完成上传、预检、确认和结果查看；前后端版本一致，NodeId、凭证、草稿和既有待发数据保留 |
| UP-AT-02 | 检查与下载 | 可信源可用时显示正确版本，断网显示检查失败；下载失败/取消不影响采集；下载成功不自动安装 |
| UP-AT-03 | 包与元数据校验 | 篡改、错误产品/架构、未知签名、过期或回退元数据、路径穿越、超大包被拒；执行器再次验证能发现上传后替换文件 |
| UP-AT-04 | 权限与重复请求 | 非管理员、无效会话、防 CSRF 失败均不能执行；重复确认和浏览器超时不产生第二任务；不存在任意命令或 URL 执行入口 |
| UP-AT-05 | 维护互斥 | 配置应用/恢复/迁移与升级不并发；旧输入停止超时则不切换；下载时不停采，切换时有明确维护状态 |
| UP-AT-06 | 启动验证与自动恢复 | 新版本迁移失败或不能启动时，完整恢复程序、配置和队列并可在旧页面查看原因；未验证候选版本没有外部数据投递；外部设备离线不误触发恢复 |
| UP-AT-07 | 中途退出与断电 | 每个持久化阶段前后终止执行器/Host，重启后只完成或恢复同一任务，不重复实例；真实硬件另测断电，模拟终止不能算硬件测试 |
| UP-AT-08 | 成功后的数据边界 | 新版本开始采集后，不自动覆盖旧检查点；已生成新数据和旧队列编号不被静默清空或改写 |
| UP-AT-09 | 网页断开与审计 | 关闭浏览器不取消已接管任务；重连显示真实阶段；失败恢复后任务日志和审计仍在；新旧版本都无法启动时给出可执行的主机救援说明 |
| UP-AT-10 | Docker 能力隔离 | 未配置执行器时安装按钮不可用；配置后只更新允许的网关容器，保留数据卷且不重启 Broker；网关容器不能访问 docker.sock 或执行任意主机命令 |
| UP-AT-11 | 空间与日志保护 | 空间不足或检查点损坏在切换前被阻止；上传、解包和日志受限，不耗尽管理/队列余量；当前恢复资料不会被过期清理 |
| UP-AT-12 | 会话与管理安全 | 升级成功和失败恢复后旧会话失效，已吊销令牌不复活；沿用 HTTPS/HTTP、请求协议判定和出站访问规则，签名不能绕过这些校验 |
